07 · 代理与反反爬体系

单 IP 采集注定被封锁——这一章搭一套完整的"反反爬"体系：代理设置与验证、代理池的四大模块、隧道与拨号换 IP，最后汇成频率控制、指数退避、降级策略与"体面爬虫公约"。学完这一章，你的爬虫才配叫"体系"。

🔗 连接你已有的知识（考研 408 · 计算机网络）

· 频率控制 = 408 拥塞控制思想的移植：慢启动、加性增/乘性减（AIMD）、超时指数退避——把"对网络拥挤的礼貌"换成"对服务器负载的礼貌"，令牌桶正是计网流量整形里的老朋友；
· 代理 = 路由替换：让流量绕道走，目标看到的源地址变了，但请求—响应模型一点没变（第 01 章的模型原样成立）；
· 封禁排查 = 分层排查：从应用层（头/Cookie/签名）到网络层（IP）逐层定位——和你排查网络故障是同一个套路。

7.1 代理设置 对齐教材 9.1

第 01 章 1.5 讲清了代理的分类与原理（正向/反向、透明/匿名/高匿），这一节解决"怎么用"。requests 里代理就是一个 proxies 字典：键是协议，值是代理地址，三种常见写法一次给全：

proxy_setup.py
import requests

# ① 普通代理：协议://主机:端口
proxies = {
    "http":  "http://127.0.0.1:7890",
    "https": "http://127.0.0.1:7890",   # https 走的隧道也由 http 代理承载，写法不变
}
# ② 带认证的代理：协议://用户名:密码@主机:端口
auth_proxies = {
    "http":  "http://user:pass@proxy.example.com:3128",
    "https": "http://user:pass@proxy.example.com:3128",
}
# ③ SOCKS5：更底层、通吃流量。先装依赖：pip install "requests[socks]"
socks_proxies = {
    "http":  "socks5://127.0.0.1:1080",
    "https": "socks5://127.0.0.1:1080",
}

# ④ 验证生效：origin 显示"出口 IP"，不是你家的 IP 就说明代理在工作
resp = requests.get("https://httpbin.org/ip", proxies=auth_proxies, timeout=10)
print(resp.json())    # {'origin': '47.98.xxx.xxx'} ← 代理的 IP，不是 120.xx 你家的
验证是铁律：每批新代理必须先打 httpbin.org/ip 验一遍再上岗——你会在 7.2 看到，"验证"正是代理池检测器的核心动作。另外 timeout 必带：烂代理最常见的死法是"连上但不响应"，没有超时的爬虫会在它身上挂死整夜。

7.2 代理池的维护 对齐教材 9.2 本章重点

单发请求配 proxies 就够了，但要持续、稳定地采集，需要一批"随时可用、随坏随补"的代理——这就是代理池。它的经典架构是四大模块，数据流一句话：获取器抓来代理 → 存进 Redis 打分 → 检测器循环验活调分 → 调度接口随机吐出口：

获取器免费源 / 付费 API→ 存储器Redis zset 打分→ 检测器验活 +1 / −1（循环）→ 调度接口random 出口→ 你的爬虫每请求取一个
模块职责实现要点
获取器持续补充新代理抓免费代理站 + 调付费 API；新代理先入池"考察"，不直接上岗
存储器保存并给代理打分Redis zset：member=代理地址，score=健康分——成功 +1、失败 −1
检测器循环验活定时拿池里代理请求 httpbin；跌破阈值（如 −3）即 ZREM 剔除
调度接口对外提供出口Flask 暴露 /random：优先从高分代理随机挑一个返回

精简可运行实现：zset 打分制

proxy_pool.py
import random
import redis
import requests

r = redis.Redis(decode_responses=True)
ZSET = "proxy:pool"                                # 有序集合：member=代理，score=健康分

def fetch_new():
    """获取器：实际项目 = 爬免费代理站 + 调付费 API，这里返回示例演示接口约定"""
    return ["120.220.1.9:53281", "163.204.246.141:9999", "115.221.115.23:80"]

def check(proxy):
    """检测器：成功 +1，失败 -1，跌破 -3 剔除"""
    try:
        requests.get("https://httpbin.org/ip",
                     proxies={"http": f"http://{proxy}"}, timeout=5)
        r.zincrby(ZSET, 1, proxy)
        return True
    except Exception:
        if r.zincrby(ZSET, -1, proxy) < -3:      # 连挂 4 次：踢出池子
            r.zrem(ZSET, proxy)
        return False

def get_proxy():
    """调度接口：优先从高分代理随机挑一个出口"""
    good = r.zrangebyscore(ZSET, 3, "+inf")       # 3 分以上 = 久经考验
    pool = good or r.zrange(ZSET, 0, -1)          # 没有高分，全员顶上
    return random.choice(pool) if pool else None

if __name__ == "__main__":
    for p in fetch_new():
        r.zadd(ZSET, {p: 0})                       # 新代理 0 分入池，先考察
    print(get_proxy())
预期输出
120.220.1.9:53281        # 池中任意一个代理——分数高的被抽中概率由 zrangebyscore 保证

这套"打分制"的精髓：新代理 0 分起步不能立刻上岗（防止烂代理毒害采集主流程）；每次使用都是一次隐性检测（业务请求成功也 +1）；剔除靠连续失败而不是单次失败（网络抖动一两次不该判死刑）。

免费源的现实与付费建议

把丑话说在前面：免费代理站的可用率通常不到 10%，平均寿命以分钟计——这正是检测器必须存在的原因。免费源适合学习练手、搭池子跑通流程；生产采集请直接上付费代理（独享套餐或隧道，见 7.3），按"单次采集的账号/时间成本"算，付费代理几乎总是更便宜的选择。

7.3 付费代理与隧道代理 对齐教材 9.3

付费代理常见两种形态，选型前分清它们：

形态工作方式你的工作量适用
隧道代理给你一个固定网关地址，每次请求经过网关时自动换一个出口 IP零代码——配一次 proxies 就完事不想管 IP 调度的中小规模采集
抽取 API（IP 池）调接口一次拉一批 IP 回来，自己入池、验活、轮换要自己维护 7.2 那套池子大规模分布式、想自控质检与成本
tunnel_demo.py
# 隧道代理：网关地址永远不变，网关背后每次请求自动换 IP——requests 侧零额外代码
import requests

tunnel = {
    "http":  "http://user:pass@tunnel.provider.com:15818",
    "https": "http://user:pass@tunnel.provider.com:15818",
}
for i in range(1, 4):
    ip = requests.get("https://httpbin.org/ip", proxies=tunnel, timeout=10).json()["origin"]
    print(f"第 {i} 次：{ip}")
预期输出
第 1 次：113.120.35.42
第 2 次：223.74.102.9
第 3 次：183.62.51.201

三次请求三个不同 IP——换 IP 这件事被压缩进了"网关"这一个概念里。它和 7.2 自建池的关系：隧道 = 服务商替你跑代理池；你已经会自建，就能理解隧道的定价与边界（并发数、QPS 上限），也能在预算紧张时退回自建方案。

7.4 ADSL 拨号代理 对齐教材 9.4

ADSL 拨号是"穷人的代理池"：家庭/办公宽带走 PPPoE 拨号接入运营商，每次断线重拨，运营商就重新分配一个公网 IP。于是思路来了——找一台宽带机器做"拨号服务器"，装个代理服务（如 TinyProxy/3proxy）对外开放，爬虫所有请求都发给它；这台机器的 IP 被目标站封了？断线重拨，几秒后换一个新身份满血复活。池子只有一个成员，但成员会自己换脸。

adsl_daemon.py（拨号机上的守护脚本思路）
import subprocess
import time
import requests

def redial():
    """断线重拨：PPPoE 重新分配公网 IP，等于换了一个身份"""
    # Windows 用 rasdial；Linux 用 poff/pon（pppoe 配置文件名随发行版）
    subprocess.run("rasdial 宽带连接 /disconnect", shell=True)
    subprocess.run("rasdial 宽带连接 username password", shell=True)

while True:
    try:
        print(requests.get("https://httpbin.org/ip", timeout=5).json())
    except Exception:
        redial()                    # 出口挂了/被封？重拨换 IP，服务自愈
        time.sleep(5)
适用边界要心里有数：① 重拨窗口 = 服务中断——重拨的几秒到几十秒里代理不可用，任务要能容忍抖动；② 池子永远只有"当前这一个"IP——无法并发多 IP，只适合中小规模；③ 运营商政策变化大——不少地区的家宽已不发公网 IP（NAT 之内重拨也没用），动手前先验证重拨后 IP 是否真的变化；④ 云机房宽带默认不给你 PPPoE——这套方案的地盘在"有真实宽带线路"的场景。

7.5 反反爬体系总纲 本章灵魂

代理只解决"IP"这一件事。真实战场上，被封往往是多个维度同时露馅：UA 是 requests 默认的、Referer 是空的、Cookie 是死的、频率是每秒 20 发。把前几章的零散武器编成一张总纲表——每道盾都对应一支矛：

盾：网站的手段矛：你的对策一句话要点
UA / 请求头检测UA 池（fake-useragent）+ F12 抄全套头requests 默认 UA 一秒暴露；头要成套伪装
Referer 防盗链补来源页请求头从哪个页面发现接口，Referer 就填哪个页面
Cookie 考验 / 动态 tokenSession 管理 + Cookie 复用（第 06 章）Session 自动领证带证；登录态整包复用
频率限制随机延时 1~3s + 令牌桶控速慢就是快：不断流的爬虫总吞吐反而最高
IP 封禁代理池 / 隧道（7.2 / 7.3）换 IP ≠ 换身份：头和 Cookie 也要一起换
验证码第 06 章全套手段能绕则绕，打码是最后手段
字体 / 文本假字符映射表 / 逆向（第 08 章）假字符的尽头是一张对照表

重试退避：指数退避，绝不顶风重试

被限流时最坏的反应是"立即重试"——那是在给封禁升级加速。正确姿势是指数退避：第 n 次重试前等待 2n 秒（再乘随机抖动，防止所有爬虫同节奏共振）。这正是 408 拥塞控制里"超时退避"的翻版：

backoff.py
import random
import time
import requests

def fetch_with_backoff(url, max_retries=5, base=1.0, cap=60):
    """指数退避：第 n 次重试等 base * 2^n 秒（加抖动），绝不连发猛冲"""
    for attempt in range(max_retries):
        try:
            resp = requests.get(url, timeout=10)
            resp.raise_for_status()
            return resp                      # 成功：原样返回
        except requests.RequestException:
            if attempt == max_retries - 1:
                raise                        # 额度用尽：向上抛，交给上层换代理/降级
            wait = min(cap, base * (2 ** attempt)) * random.uniform(0.5, 1.0)
            print(f"第 {attempt + 1} 次失败，等 {wait:.1f}s 再试")
            time.sleep(wait)

resp = fetch_with_backoff("https://httpbin.org/status/503,200")
print(resp.status_code)
预期输出（503 时才会看到重试行）
第 1 次失败，等 0.7s 再试
第 2 次失败，等 1.3s 再试
200

频率控制与令牌桶

随机延时的进阶版是令牌桶：桶里最多装 N 个令牌，按固定速率补充；每个请求先取一枚令牌才放行。它把"平均速率"和"突发容量"分开控制——桶满时允许小突发（像人一样偶尔连点几下），桶空时强制排队（绝不超速）。比起裸的 sleep(uniform(1, 3))，令牌桶让"礼貌"变成可配置的参数：限速阈值、突发容忍度都是拧旋钮的事。

降级策略：宁可慢和少，不可停和死

体系化的最后一层是想好每条路的退路：接口被限流 → 降速 / 切渲染路（5.4）；IP 池枯竭 → 自动降频并告警，而不是用空 IP 硬冲；账号 Cookie 失效 → 切换下一个账号（6.6 的池子）；数据源被封 → 找镜像或替代源。降级不是认输，是把"被封"从事故变成日常调度的一部分。

体面爬虫公约（背下来）：① 只采公开数据，尊重 robots.txt 与服务条款；② 频率 ≥1~3 秒/请求，带头伪装、带随机延时；③ 大批量任务放深夜，错峰出行；④ 收到 429 主动退避，绝不顶风重试；⑤ 不碰个人隐私与非公开数据；⑥ 逆向与攻防练习只在授权平台（Scrape Center / 猿人学）进行。体面不是软弱——被封少的爬虫，采集量反而最大。

User-Agent / 请求头检测

原理：校验 UA、Referer、Accept 等头是否像真浏览器。requests 默认 UA 是 python-requests/2.x，一秒暴露。

识别：requests 直连返回 403，浏览器打开正常 —— 八成是它。

破解：从浏览器 F12 抄全套请求头；用 fake-useragent 库随机轮换。

频率限制与 IP 封禁

原理：同一 IP 单位时间请求超阈值 → 先 429 警告，再拉黑。是最古老也最有效的反爬。

识别：前几十次正常，之后集体失败；换个网络环境（手机热点）又活了。

破解：随机延时 1~3 秒 + 控制并发；代理池轮换 IP（自建拨号池或买代理）；大批量任务放深夜。

Cookie 考验 / 动态 Token

原理：先访问首页领 Cookie（可能带 JS 计算的 acw_sc__v2 / __jsl_clearance 等），带着它才能访问数据接口。

识别：直接请求接口返回一段加密 JS 或 521/412 状态码。

破解：用 Session 先 GET 首页再访问接口；JS 生成的 Cookie 进第 08 章逆向，或用 execjs 跑官方 JS。

动态渲染（数据不在 HTML 里）

原理：页面由 JS 拼装，源代码只有空壳（第 05 章已学）。

破解：首选接口直连；接口难拿时用 Playwright/Selenium 渲染。注意 navigator.webdriver 检测，用 undetected-chromedriver 或 Playwright 隐身方案绕过。

字体反爬 / 文本假字符

原理：自定义字体文件把 Unicode 映射打乱——页面上渲染出"8"，HTML 里其实是""。点评、招聘网站爱用。

识别：复制页面文字到别处变乱码；HTML 里出现大量 &#x 开头的实体。

破解：下载 woff 文件用 fontTools 解析字形，和标准字形比对建映射表；或 OCR 识别渲染后的字符。

CSS 偏移 / 图片替代文本

原理：数字用 background-position 从一张雪碧图上"裁"出来，HTML 里根本没有文本。

识别：价格/评分在 Elements 里是一堆空 span + 背景图。

破解：解析 CSS 的偏移规则算出真实数字；或直接对图片区域 OCR。

验证码（图形 / 点选 / 滑块）

原理：区分人机的终极手段，强度阶梯：数字字母码 → 点选文字 → 滑块轨迹 → 行为验证。

破解：数字码用 ddddocr；点选/滑块要么接打码平台，要么研究轨迹模拟；能 Cookie 复用就别碰它。

本章五大坑：① 透明代理白用——带 X-Forwarded-For 暴露真实 IP，目标既知道你用代理又知道你是谁，先验匿名度再上量；② 免费代理超时连坐——免费源平均寿命几分钟，不配 timeout + 打分剔除，一个死代理能卡死整条请求队列；③ 重试风暴——无退避的立即重试会把 429 升级成永久封禁，重试必须指数退避 + 设上限；④ Cookie 与 IP 只换一个——只换 IP 不清 Cookie，服务器照样凭 Cookie 认出你，排查封禁时两者要一起换；⑤ 大批量任务放白天高峰——深夜跑既是体面也是生存：负载低、风控松、投诉少。

Q1动手：实现 fetch_with_retry(url, max_retries=5)——只对 429 和 5xx 重试；404 等其他客户端错误立即抛错；重试采用指数退避 + 随机抖动；额度用尽向上抛。动手

考点：7.5 指数退避的完整落地，重点是"按状态码分流"。

参考代码： 
import random, time, requests

def fetch_with_retry(url, max_retries=5):
    for attempt in range(max_retries):
        resp = requests.get(url, timeout=10)
        if resp.status_code == 200:
            return resp
        if resp.status_code == 404:
            resp.raise_for_status()          # 资源不存在：重试没有意义，立即抛
        if resp.status_code == 429 or resp.status_code >= 500:
            if attempt == max_retries - 1:
                resp.raise_for_status()      # 额度用尽：向上抛，交给上层换代理/降级
            wait = min(60, 2 ** attempt) * random.uniform(0.5, 1.0)
            print(f"{resp.status_code}，等 {wait:.1f}s 再试")
            time.sleep(wait)
            continue
        resp.raise_for_status()              # 其余 4xx（401/403…）：换头换 Cookie，不是重试能救的
设计要点：404/401/403 属于"重试也解决不了"的错误，重试只会浪费时间并加剧风控画像；只有 429（限流）和 5xx（临时故障）值得退避等待。抖动系数 uniform(0.5, 1.0) 防止多任务同步共振，上限 cap 防止等待无限膨胀。
Q2设计题：为什么代理池用 Redis zset 打分，而不是 set 存一堆代理 + 轮询使用？写出打分、剔除、调度三步对应的具体 Redis 命令。设计

考点：7.2 核心设计 + Redis 数据结构选型（呼应第 04 章）。

参考解析：set 只回答"在不在"，回答不了"好不好"——而代理池的全部价值就在质量分级：新代理要隔离考察、好代理要优先调度、坏代理要及时剔除。zset 让每个代理带一个健康分，天然支持"按分数段取用"（ZRANGEBYSCORE），且增删查都是 O(log N)。三步命令： 
ZADD proxy:pool 0 "1.2.3.4:8080"          # 入池：新代理 0 分考察
ZINCRBY proxy:pool 1 "1.2.3.4:8080"       # 打分：成功 +1 / 失败 -1（负数传 -1）
ZREM  proxy:pool "1.2.3.4:8080"           # 剔除：分数跌破 -3 时执行
ZRANGEBYSCORE proxy:pool 3 +inf           # 调度：先从 3 分以上挑，池冷时退回 ZRANGE 0 -1
再加一个工程细节：zset 分数是 double，可以顺手把"最近一次成功时间"编码进小数位，或另用 hash 存元数据（归属运营商、协议），让调度接口支持"指定地区出口"这类进阶需求。
Q3选型分析：场景 A——三人小团队，每天要抓 5 万页，不想维护任何 IP 调度代码；场景 B——成熟的分布式采集系统，已有调度框架与质检流程。两场景分别选隧道代理还是抽取 API？说明理由。分析

考点：7.2/7.3 的选型判断——按团队规模与运维成本决策，而不是按"哪个高级"。

参考解析：场景 A 选隧道代理：5 万页/天的量级付费隧道完全够用，requests 侧零代码、零运维，团队的人力应该花在解析和数据质量上，而不是维护代理池；隧道的溢价买的正是"省心"。场景 B 选抽取 API + 自建池：大规模下按 IP 计费的抽取 API 单价更低，且团队已有调度框架——把拉取的 IP 接入 7.2 的 zset 池子做质检分级，坏代理提前剔除、好代理优先调度，成本与稳定性都优于隧道的一刀切；分布式多机场景下，隧道网关的并发/QPS 上限反而会成为瓶颈。一句话总结：小团队买省心（隧道），大团队买原料（抽取）自己炼。
Q4分析题：你的代理池跑着跑着，请求开始大面积返回 403。给出一个排查决策树：先看什么、后看什么、每一步分别怎么验证。分析

考点：7.5 总纲的实战应用——分层排查思想。

参考决策树：
① 定性：单个代理 403 还是全池 403？——分别用池内不同代理打目标站首页验证。
② 若全池 403：问题多半不在 IP。
　　a. 最近改过代码吗？→ 用浏览器对比请求头，查 UA/Referer 是否丢失（图鉴第 1 条）；
　　b. Session Cookie 过期了吗？→ 换新 Cookie 重放一条，看是否恢复（第 06 章）；
　　c. 浏览器直接访问目标站也异常吗？→ 是则目标站升级了风控（如新增签名校验），排进第 08 章清单。
③ 若仅部分代理 403：
　　a. 403 的代理是不是透明代理？→ 用 httpbin.org/headers 查 X-Forwarded-For 是否暴露真身；
　　b. 这些代理是否已被目标站拉黑？→ 换一个目标站测试同一代理：A 站 403、B 站 200 = 被 A 拉黑，检测器扣分剔除即可；
　　c. 这些代理是否共享同一 C 段/机房？→ 目标站可能按 IP 段封禁，获取器要增加来源多样性。
④ 仍无法定位 → 用"对照实验"收尾：同一请求分别走 {真浏览器 / 直连 / 单代理} 三种方式，diff 三份完整请求头与 Cookie，差异点即答案。决策树的核心：先分离变量（IP 与身份），再逐层验证（头 → Cookie → 签名），最后才怀疑"对方升级了"。
