04 · 数据存储：文件 / MySQL / MongoDB

抓得到、解析得出，最后要"落得下"。这一章补齐爬虫三段式的最后一环：文件存储（TXT / JSON / CSV）、关系型数据库（SQLite 单机零配置、MySQL 参数化与事务）、非关系型数据库（MongoDB 文档库、Redis 三大结构），最后给你一张"数据形态 × 规模 × 消费方式"的选型决策表——从此拿到任何需求都能立刻回答"往哪儿存"。

🔗 连接你已有的知识（考研 408 · 数据库 × 数据结构）

· 408 数据库的关系模型（表 / 键 / 完整性约束）就是建表的依据：SQLite 的 PRIMARY KEY / UNIQUE 是你背过的实体完整性，它直接决定你能不能写对"去重入库"；
· 事务 ACID（原子性、一致性、隔离性、持久性）对应 commit / rollback：爬虫爬到一半崩溃，回滚保证库里不残留半批脏数据——这是 408 经典考点第一次真正帮你写对代码；
· 索引：408 里 B+ 树加速查询，数据库里 WHERE score > 9.6 快不快就看它——去重键上建 UNIQUE 索引，一石二鸟；
· Redis 的三大结构全是 408 数据结构常客：set = 集合（判重 O(1)）、zset = 有序集合（底层跳表，408 拓展考点）、list = 队列（FIFO）——第 07 章代理池与第 10 章分布式队列全靠它们。

4.1 文件存储 对齐教材 5.1

数据量小、一次性任务，文件就是最诚实的答案。三种格式各有脾气：

TXT：追加写日志

最朴素，适合做原始数据留底、调试日志。关键是 "a" 追加模式（"w" 会整文件覆盖，爬虫跑第二次就清空第一次的成果）：

txt_save.py
with open("movies.txt", "a", encoding="utf-8") as f:
    f.write(f"肖申克的救赎\t9.7\n")     # 制表符分列、每条一行，pandas 随时可 read_csv 读回来

JSON 与 JSON Lines：结构化的程序友好格式

3.5 已打下基础，这里补齐参数全家福：ensure_ascii=False 中文原样、indent 美化（人看时加，机器读时不加省体积）。日常爬虫首选 JSON Lines（一行一个对象、追加安全）：

json_save.py
import json

item = {"title": "三体", "score": 9.3}

# 整文件写（小数据、配置类）；ensure_ascii=False 保证中文不转义
with open("books.json", "w", encoding="utf-8") as f:
    json.dump([item], f, ensure_ascii=False, indent=2)

# JSON Lines：追加写，断点续爬友好（爬虫首选）
with open("books.jsonl", "a", encoding="utf-8") as f:
    f.write(json.dumps(item, ensure_ascii=False) + "\n")

CSV：给 Excel 用户和业务方

用 csv.DictWriter，字典列表直接写。两个保命参数：newline="" 防 Windows 下每行之间空一行（csv 模块自己管换行，别让 open 再插一手）；encoding="utf-8-sig" 带上 BOM 头，Excel 双击打开不乱码：

csv_save.py
import csv

rows = [
    {"rank": 1, "title": "肖申克的救赎", "score": 9.7},
    {"rank": 2, "title": "霸王别姬", "score": 9.6},
]
with open("movies.csv", "w", newline="", encoding="utf-8-sig") as f:
    writer = csv.DictWriter(f, fieldnames=["rank", "title", "score"])
    writer.writeheader()          # 表头只写一次
    writer.writerows(rows)
# 追加模式续写时：open(..., "a", ...)，不要再 writeheader，用 writer.writerow(row)

三者选型对比

格式优点缺点适用
TXT零依赖、人能看、最抗造无结构、难查询难过滤日志、原始留底
JSON / JSON Lines结构化、嵌套照收、程序友好、追加安全Excel 打不开、体积偏大接口数据、给下游程序消费
CSVExcel 直开、通用交换格式表达不了嵌套、类型全退化成字符串表格型数据、交付给业务方

4.2 关系型存储 对齐教材 5.2

数据要查询、去重、增量更新时，文件就不够了——该上数据库。关系型的两条路：SQLite（单机文件库）与 MySQL（服务端库）。

① SQLite：零配置的单机首选

import sqlite3 即用——整个数据库就是一个文件，无安装、无服务、无账号密码。爬虫单机项目（几十万行以内）的默认答案。核心看点是 UNIQUE 约束 + INSERT OR IGNORE 实现去重入库：

sqlite_demo.py
import sqlite3

conn = sqlite3.connect("movies.db")        # 文件不存在自动创建，即"整库"
cur = conn.cursor()

# 建表：rank 加 UNIQUE 约束 —— 数据库层帮你挡重复，比代码里 if 判断可靠
cur.execute("""
CREATE TABLE IF NOT EXISTS movie (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    rank         INTEGER UNIQUE,
    title        TEXT NOT NULL,
    score        REAL,
    release_time TEXT
)
""")

rows = [
    (1, "肖申克的救赎", 9.7, "1994-09-10"),
    (1, "肖申克的救赎", 9.5, "1994-09-10"),   # rank 重复：被 IGNORE 静默跳过
    (2, "霸王别姬", 9.6, "1994-01-01"),
]
cur.executemany(
    "INSERT OR IGNORE INTO movie (rank, title, score, release_time) VALUES (?, ?, ?, ?)",
    rows,                                    # ? 占位符 = 参数化，自动转义
)
conn.commit()                                # 不 commit 等于白写！

for title, score in cur.execute(
        "SELECT title, score FROM movie WHERE score >= 9.6 ORDER BY score DESC"):
    print(title, score)
# 肖申克的救赎 9.7
# 霸王别姬 9.6

conn.close()

三个 408 对应点：UNIQUE 是实体完整性约束（重复插入直接被拒，IGNORE 是"拒绝但不报错"）；? 占位符是参数化查询（防注入，MySQL 节展开讲）；commit 是事务提交（ACID 的持久性）。

② MySQL：参数化与事务

数据要长期迭代、多端共享时上 MySQL（pip install pymysql）。四个要点：连接参数化、execute 的参数化占位符（%s）防 SQL 注入、事务 commit/rollback、连接复用（连接是昂贵资源，别每条数据建一个）：

mysql_demo.py
import pymysql

conn = pymysql.connect(
    host="127.0.0.1", port=3306,
    user="spider", password="你的密码",
    database="spider_db", charset="utf8mb4",   # utf8mb4 才收 emoji，utf8 收不全
    autocommit=False,                          # 手动管事务
)
cur = conn.cursor()

sql = "INSERT INTO movie (rank, title, score) VALUES (%s, %s, %s)"   # 占位符，不是 f-string！
try:
    cur.execute(sql, (1, "肖申克的救赎", 9.7))     # 数据永远作为"参数"传入
    cur.executemany(sql, [(2, "霸王别姬", 9.6), (3, "活着", 9.4)])
    conn.commit()                            # 全部成功才提交 —— 原子性
except Exception:
    conn.rollback()                          # 任一步失败，整批回滚 —— 半批脏数据不存在
    raise
finally:
    cur.close()
    conn.close()
SQL 注入：一条警告 Worth 一整节。把用户数据 f-string 进 SQL：f"SELECT * FROM users WHERE name = '{name}'"，当 name 是 ' OR '1'='1 时，引号闭合、条件恒真，语句被改写——别人的输入变成了你的 SQL 语法。参数化的原理：SQL 模板先预编译成语法树，参数只作为数据绑定进去，永远没有机会被当成语法执行。SQLite 用 ?、PyMySQL 用 %s，本质相同。铁律：任何来自外部（网页、接口、你爬来的数据）的值，只许走占位符。

4.3 非关系型存储 对齐教材 5.3

① MongoDB：文档型，字段不固定就找它

网页数据的字段经常"缺胳膊少腿"（有的电影没有评分，有的商品没有副标题），关系型建表会被 NULL 灌满；MongoDB 存的是 BSON 文档，字段随写随有（pip install pymongo）：

mongo_demo.py
from pymongo import MongoClient, ASCENDING

client = MongoClient("mongodb://127.0.0.1:27017/", serverSelectionTimeoutMS=5000)
col = client["spider_db"]["movie"]          # 库和集合都不存在？插入时自动创建

# 增
col.insert_one({"rank": 1, "title": "肖申克的救赎", "score": 9.7, "tags": ["犯罪", "剧情"]})
col.insert_many([{"rank": 2, "title": "霸王别姬", "score": 9.6},
                 {"rank": 3, "title": "活着"}])   # 字段不齐？没关系 —— 文档型的底气

# 查：条件 + 排序
for doc in col.find({"score": {"$gte": 9.6}}).sort("rank", ASCENDING):
    print(doc["title"])

# 改 + 去重：upsert —— 存在则更新、不存在则插入，增量爬取的标配
col.update_one(
    {"rank": 1},                                        # 查找条件（相当于主键）
    {"$set": {"title": "肖申克的救赎", "score": 9.7}},  # 只改这些字段
    upsert=True,                                        # 没找到就插入
)
# 查询慢？给常用条件建索引：col.create_index([("rank", ASCENDING)], unique=True)

② Redis：不只是缓存，是爬虫的调度中枢

Redis 是内存键值库（pip install redis），爬虫用它的三大结构干三件事——去重集合、评分排行、待爬队列，为第 07 章（代理池）与第 10 章（分布式）埋下伏笔：

redis_demo.py
import redis

r = redis.Redis(host="127.0.0.1", port=6379, db=0, decode_responses=True)
# decode_responses=True：返回 str 而不是 bytes

# ① set 去重集合：sadd 添加成功返回 1（新）、0（已存在）—— O(1) 判重
if r.sadd("seen_urls", "https://example.com/page/1"):
    print("新 URL，去爬")
else:
    print("爬过了，跳过")

# ② zset 有序集合：按 score 排行 —— 代理池打分、热点榜单
r.zadd("hot_movies", {"肖申克的救赎": 9.7, "霸王别姬": 9.6})
print(r.zrevrange("hot_movies", 0, 2, withscores=True))   # Top3：按分从高到低

# ③ list 队列：lpush 进队 + rpop 出队 = FIFO 待爬队列（第 10 章分布式的基础）
r.lpush("queue", "https://example.com/page/2")
print(r.rpop("queue"))                        # https://example.com/page/2

4.4 存储选型决策 方法论

选型不看"哪个高级"，看三个变量：数据形态（表格还是嵌套文档？）、规模（千行还是亿行？）、消费方式（人看？程序读？多端查询？）。对着下表走一遍就有答案：

数据形态规模消费方式推荐
表格型、字段整齐< 1 万行Excel 打开给业务看CSV（utf-8-sig）
结构化/嵌套 JSON任意程序继续处理、断点续爬JSON Lines
结构化、要查询去重< 百万行单机脚本本地读SQLite（零配置）
结构化、长期迭代百万行以上多端并发读写、事务保证MySQL
文档型、字段不齐、嵌套深百万行以上服务端灵活查询MongoDB
（中间件）URL 判重 / 排行 / 待爬队列任意爬虫自身调度Redis set / zset / list
先问给谁用？→ 人看CSV / 文本→ 程序读JSONL → 入库→ 要查询？SQLite→MySQL/MongoDB→ 要调度？Redis

实战组合拳：第 02 章的猫眼 TOP100（表格型、百行、要看）→ CSV；名句整站爬取（要增量去重）→ SQLite + UNIQUE；第 05 章起的接口数据（嵌套 JSON）→ MongoDB + upsert；第 07 章代理池 → Redis zset 打分。把第 03 章《解析器的艺术》动画里那句"落库三兄弟，按需选择"真正落地。

本章避坑清单：① CSV 用 utf-8 写、Excel 打开全是乱码——Excel 不认无 BOM 的 UTF-8，写盘一律 utf-8-sig；② csv 写文件漏了 newline=""——Windows 下每行之间多一个空行，pandas 读回来全是 NaN；③ f-string 拼 SQL 是注入温床（f"…'{value}'"）——任何外部值只许走占位符 ? / %s；④ 忘了 commit——SQLite/MySQL 默认走事务，程序跑完没提交，数据根本没落盘，"爬了一晚上库是空的"多半是它；⑤ MongoDB 的 update_one 修改器写错：不用 $set 会整文档替换；增量去重要记得 upsert=True，光用 insert_one 每天重爬只会堆积重复。

📝 本章练习

先自己想，再展开参考解析。做完到练习场刷综合题。

Q1同事生成的 movies.csv 在记事本里中文正常，Excel 双击打开却全是乱码。原因是什么？给出两种修复方案。分析

考点：4.1 CSV 编码细节，最经典的"交付事故"。

参考解析：文件是无 BOM 的 UTF-8。记事本会尝试多种编码（能认出 UTF-8），而 Excel 双击打开 CSV 时按系统默认 ANSI（中文 Windows 是 GBK）解码，UTF-8 的中文字节被 GBK 误读成乱码。修复方案：① 治本——写文件时用 open("movies.csv", "w", newline="", encoding="utf-8-sig")，utf-8-sig 会在文件头写入 BOM（EF BB BF），Excel 看到 BOM 就按 UTF-8 解码；② 治标——Excel 里走"数据 → 从文本/CSV 导入"，手动指定编码为 UTF-8（65001）。另外两个 CSV 高频坑一并复查：open 少了 newline=""（空行问题）、DictWriter 的 fieldnames 与字典键不一致（ValueError 或丢列）。
Q2动手：为"每天重爬猫眼 TOP100"设计 SQLite 去重入库方案——同一 rank 绝不能出现两行，重复数据来了要安静跳过。写出建表与插入代码，并说明它和 MongoDB 的 upsert 是什么关系。动手

考点：4.2 UNIQUE 约束 + INSERT OR IGNORE，实体完整性的落地。

参考解析：去重键（rank，或真实场景的影片 id）上加 UNIQUE 约束，让数据库而不是 Python 代码负责判重： 
import sqlite3

conn = sqlite3.connect("movies.db")
cur = conn.cursor()
cur.execute("""
CREATE TABLE IF NOT EXISTS movie (
    rank  INTEGER UNIQUE,          -- 去重键：实体完整性约束
    title TEXT NOT NULL,
    score REAL
)""")

rows = [(1, "肖申克的救赎", 9.7), (1, "肖申克的救赎", 9.5)]  # 第二条 rank 重复
cur.executemany("INSERT OR IGNORE INTO movie (rank, title, score) VALUES (?, ?, ?)", rows)
conn.commit()
print(cur.execute("SELECT COUNT(*) FROM movie").fetchone())   # (1,) —— 重复行被安静挡掉
INSERT OR IGNORE 语义是"冲突就不插、不报错"；若要"重复时更新成新值"，换 INSERT … ON CONFLICT(rank) DO UPDATE SET score=excluded.score（UPSERT 语义）。它与 MongoDB 的 update_one(..., upsert=True) 是同一种思想的两种方言：都把"存在即更新、不存在即插入"交给存储引擎原子完成——比自己先 SELECT 再 INSERT 更安全（并发下不会竞态重复），这也是第 10 章分布式去重的地基。
Q3分析：要求每天增量爬取电影数据进 MongoDB——新片插入、老片字段更新、绝不产生重复文档。为什么光用 insert_one 做不到？写出正确实现。分析

考点：4.3 upsert 增量模式，爬虫长期运行的核心设计。

参考解析：insert_one 是纯追加：每天重爬同一榜单，同一 rank 会插入 N 份文档，集合里堆满"同片不同日"的重复——查询时还要自己挑最新。正确姿势是以业务唯一键为条件做 upsert： 
col.update_one(
    {"rank": rank},                          # 唯一键：先按它找
    {"$set": {"title": title, "score": score, "updated_at": now}},  # 只更新这些字段
    upsert=True,                              # 找不到就整条插入
)
要点：① 查找条件必须是业务唯一键（rank / 影片 id / 详情页 URL），别用会变的字段；② 用 $set 只更新需要的字段，保留首次采集的 created_at 等历史字段；③ 再给唯一键建唯一索引 col.create_index([("rank", 1)], unique=True) 兜底，并发写入也不会插出重复；④ 配合 $currentDate 或自填时间戳，天然得到"数据最后更新日"。这套"唯一键 + upsert + 时间戳"就是增量爬取存储的标准范式。
Q4下面这段登录查询代码有致命漏洞。指出漏洞名称、构造一个能绕过密码校验的输入，并用参数化修复。动手

考点：4.2 SQL 注入成因 + 参数化原理（408 安全高频延伸）。

name = input("用户名: ")
pwd  = input("密码: ")
sql = f"SELECT * FROM users WHERE name = '{name}' AND pwd = '{pwd}'"   # 漏洞在这
cur.execute(sql)
参考解析：漏洞是 SQL 注入：外部输入被 f-string 直接拼进 SQL，输入中的单引号会闭合字符串并注入新的 SQL 语法。构造绕过：用户名输 ' OR '1'='1，密码随便输 x，拼接后变成：SELECT * FROM users WHERE name = '' OR '1'='1' AND pwd = 'x'——由于 OR 优先级与恒真条件，全表命中，密码校验形同虚设；更狠的输入甚至能 ; DROP TABLE。修复（参数化）： 
cur.execute("SELECT * FROM users WHERE name = %s AND pwd = %s", (name, pwd))
原理：SQL 模板先由数据库预编译成执行计划（语法树），参数在编译之后作为纯数据绑定——引号、分号都只是普通字符，永远不能改变语句结构。工程上再补两层：数据库账号只授最小权限（爬虫账号不给 DROP）、对 Web 层输入做白名单校验。一句话总结：语法归模板，数据归参数，两者永不相遇。
