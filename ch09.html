09 · App 爬取：抓包与自动化

数据不只在网页上——App 的接口往往比网页更干净，但风控更"硬件化"。这一章打通四层能力：装证书抓 HTTPS、mitmproxy 脚本化自动采集、Appium 让 App 自己跑、Frida 在运行时拿到加密前的明文。

🔗 连接你已有的知识（考研 408 · 网络安全）

· mitmproxy 抓包 = 408 安全章节 TLS / CA 证书体系的直接应用：中间人之所以能解密 HTTPS，完全依赖"设备信任了你的根证书"——你在 01 章见过的握手流程，这里要亲手操作一遍；
· 会话密钥：抓包工具替两端各协商一把对称密钥（数字信封的原理），所以才能既骗过 App 又骗过服务器；
· Frida Hook = 运行时函数调用拦截：在"调用"与"实现"之间插一层，本质是对函数入口地址/虚表的改写——理解成"给函数装了个代理"；
· Appium 控件树 = 你已经会的 DOM 定位思想：树换成了 uiautomator 的控件树，定位器语法换了，思路一模一样。

9.1 抓包基础设施 对齐教材 11.1

手机抓包的原理和网页抓包完全一样：都是中间人。手机的全部流量先经过电脑上的抓包工具，工具装一张自己的 CA 证书替两边加解密。区别在于手机不归你写代码控制，所以要先搭好三件基础设施：电脑开代理服务 → 手机 WiFi 代理指向电脑 → 手机安装并信任工具的 CA 证书。任何一步缺失，表现都是"抓不到包"或"抓到一堆看不懂的密文"。

Charles 证书安装（两大平台流程）

平台证书安装信任设置代理指向
AndroidCharles：Help → SSL Proxying → Save Root Certificate 导出 pem/crt → 设置里"从存储设备安装证书"Android 7+ 的坑：App 默认只信系统证书，用户证书不生效——需 Root 后用 Magisk 模块把用户证书移入系统分区，或用 Android ≤ 6.0 的测试机长按已连 WiFi → 修改网络 → 手动代理 → 服务器填电脑局域网 IP，端口 8888
iOSSafari 访问 chls.pro/ssl 下载描述文件 → 设置 → 已下载的描述文件 → 安装必须再去 设置 → 通用 → 关于本机 → 证书信任设置 → 打开对 Charles 根证书的"完全信任"（这步漏掉 = 白装）WiFi → 配置代理 → 手动 → 电脑 IP:8888

装好证书只是第一步，Charles 还要开启 HTTPS 解密：Proxy → SSL Proxying Settings → 勾选 Enable SSL Proxying → 在 include 列表添加 *:443（或只加目标域名）。之后 App 的 HTTPS 响应在 Charles 里才是明文 JSON。验证方法：手机随便打开一个 App，Charles 里能看到请求列表且 Response 可读，基础设施就算搭好了。

搭好了还抓不到？先分两种情况：① Charles 里有这条请求但内容乱码/显示 SSL 错误 → 大概率是 9.3 的 SSL Pinning 证书锁定，不是你操作错了；② Charles 里连请求都没有 → 检查手机与电脑是否同一网段、防火墙是否放行 8888 端口。

9.2 mitmproxy 对齐教材 11.2~11.3

Charles 适合人肉翻看，但爬虫工程师真正的主力是 mitmproxy：它开源、跨平台，最重要的是支持命令行与脚本化——抓包过程可以写成 Python 代码自动落库，这才叫"采集"而不是"查看"。它有三种运行模式，对应三种场景：

模式启动命令形态适用场景
mitmproxymitmproxy -p 8080终端交互式界面现场翻看分析，快捷键浏览
mitmwebmitmweb -p 8080浏览器界面（127.0.0.1:8081）喜欢图形界面的人肉分析
mitmdumpmitmdump -s addon.py -p 8080无界面、纯脚本工程化采集主力：边抓边过滤边落库

mitmdump addon 脚本（重点）

addon 就是一个普通 Python 文件：mitmproxy 是事件驱动的，每收到一个请求、一个响应，就触发你定义的对应函数。教材 11.3 用"得到 App"演示的抓包落库方法，通用化后就是这个模板——def request 做请求期处理，def response 做响应期过滤与保存：

app_capture.py —— mitmdump addon 完整示例
# 运行：mitmdump -s app_capture.py -p 8080
import json, time
from mitmproxy import http

TARGET = "api.example.com"          # 只关心这个域名的流量
OUT    = "app_capture.jsonl"

def request(flow: http.HTTPFlow) -> None:
    if TARGET in flow.request.host:
        print(f"[→] {flow.request.method} {flow.request.pretty_url}")

def response(flow: http.HTTPFlow) -> None:
    if TARGET not in flow.request.host:
        return                       # 不是目标域名直接放行
    try:
        body = flow.response.get_text()
        data = json.loads(body) if body else {}
    except Exception:
        return                       # 非 JSON 响应跳过
    item = {
        "url": flow.request.pretty_url,
        "method": flow.request.method,
        "req_headers": dict(flow.request.headers),
        "req_body": flow.request.get_text() or "",
        "status": flow.response.status_code,
        "resp": data,
        "ts": time.time(),
    }
    with open(OUT, "a", encoding="utf-8") as f:
        f.write(json.dumps(item, ensure_ascii=False) + "\n")
工程化提示：落盘用 JSONL（每行一个 JSON 对象）——手机一直产生数据，追加写不会损坏旧数据；后续 pandas.read_json(..., lines=True) 一行读入，直接接第 04 章的存储体系。人在 App 里正常点屏幕，数据就源源不断进文件——这就是教材 11.3 方法的通用化。

9.3 App 请求分析的特殊性 拓展

App 抓包不是"网页抓包换个小屏幕"。App 与服务器的关系更紧密，因此多了两道网页爬虫不会遇到的门槛：SSL Pinning 和 so 层加密。认识它们的边界，比多背几个工具更重要。

SSL Pinning 证书锁定

概念：普通程序校验证书走系统证书链（你的中间人证书装进系统就生效）；但 App 可以在代码里内置服务器证书或公钥指纹，每次握手时额外校验"对面给的证书和我内置的是不是同一张"——不是就直接断开。这叫 SSL Pinning（证书锁定）。表现：证书装好了、代理也通了，浏览器能抓，唯独这个 App 一打开就断网/全部请求失败。

应对思路：① Frida 反钉扎——用 Frida hook 住 App 的证书校验函数（如 OkHttp 的 CertificatePinner），让校验永远返回"通过"，社区有现成的通用 unpinning 脚本（9.5 给出 hook 最小模板）；② 换测试对象——有些 App 的低版本未启用 pinning，或存在关闭校验的调试包；③ 换数据源——看看有没有 Web 端、小程序端提供同源接口，绕开整个 App。思路 ③ 往往是性价比最高的。

so 层加密的边界

更深的门槛是参数在 so 库（C/C++ 编译的动态库）里计算：Java 层只是调个 JNI 接口，真正的加密逻辑在汇编级。逆向 so 需要 IDA/Ghidra 的静态分析功底，属于 App 逆向的另一门功课，投入产出比要冷静评估。务实的边界判断：遇到 so 层加密，先估算还原成本；成本过高就换数据源——Web 端接口、官方开放 API、或合规的数据采购。爬虫工程师的核心能力是判断"这条路值不值"，而不是头铁硬啃。

成本排序（从低到高）：直连接口 < 浏览器自动化（05 章）< Appium（9.4）< Frida Hook（9.5）< so 层逆向。永远先从最左边试起，每上一级之前问一句：这个数据值不值这个价。

9.4 Appium 自动化 对齐教材 11.4~11.6

当接口加密太深、还原成本过高时，有一条"降维"路线：让 App 自己跑。Appium 用代码模拟人点屏幕、读屏幕上的控件数据（UI 自动化）——请求是 App 自己发出的，签名自然是合法的，参数加密问题整个被绕开。代价是速度慢、脚本脆（UI 改版就要修），所以它是"接口打不动时"的选择，而不是第一选择。

Capabilities 模板代码

Capabilities 是一段"启动说明书"：告诉 Appium Server 连哪台设备、启动哪个 App、用哪个自动化引擎。下面是 Android 最常用的模板：

appium_demo.py —— 启动会话
from appium import webdriver
from appium.options.android import UiAutomator2Options
from appium.webdriver.common.appiumby import AppiumBy

options = UiAutomator2Options()
options.platform_name = "Android"

options.app_package   = "com.example.app"        # 目标 App 包名（adb shell pm list packages 查）

何时选 Appium

① 接口参数被 so 层加密或深度风控，还原成本明显过高 → Appium；② 数据直接显示在 UI 上且采集量不大 → Appium 简单直接；③ 量大、要求长期稳定跑几万次 → 先想接口方案，Appium 是最后手段；④ 登录有验证码/扫码等人工环节 → 半自动：人登录一次，no_reset=True 保住登录态，脚本接管后续。

上手成本：Appium 本质是 WebDriver 协议——和你在 05 章用过的 Selenium 是同一套协议思想。会 Selenium 的人学 Appium，成本只有半天：换一套定位器和 Capabilities 而已。

9.5 Frida 入门 拓展

Frida 是动态插桩框架：把一段 JS 注入目标进程，在运行时改写任意函数的行为。对爬虫的意义有两点：hook 加密函数——明文输入和密文输出直接打印出来，还原算法变成"抄答案"；绕证书锁定——hook 住校验点让它永远通过（9.3 的应对①）。它站在比 Appium 更深的一层：不看 UI，直接看函数调用。

attach 与 spawn

姿势命令区别与适用
attachfrida -U -F -l hook.js挂到已在运行的进程；适合启动后才调用的函数
spawnfrida -U -f com.example.app -l hook.js --no-pause由 Frida 重启并注入；要在启动早期（如应用初始化阶段）拦截时必须用它

最小 hook 模板：Java.perform

hook.js —— hook 一个方法，打印输入与输出
// 目标类名/方法名从哪来：用 jadx 反编译 apk，全局搜加密参数名
Java.perform(function () {                          // 进入 Android Java 运行时
  var SignUtil = Java.use("com.example.app.SignUtil");  // 定位目标类
  SignUtil.sign.implementation = function (input) {     // 重写 sign 方法
    var result = this.sign(input);                  // 先照常执行原逻辑
    console.log("[sign] in =", input, "out =", result);
    return result;                                   // 明文与密文全拿到，再原样返回
  };
});
终端用法
adb devices                          # 确认设备已连接（真机开 USB 调试 / 模拟器）
pip install frida-tools              # 电脑侧工具
# 设备上需运行对应版本的 frida-server：adb push 后 ./frida-server &
frida -U -f com.example.app -l hook.js --no-pause    # spawn：重启并注入
frida -U -F -l hook.js                               # attach：挂到前台应用

两大典型用途：① hook 加密函数拿明文——配合 jadx 反编译定位到类与方法，一次 hook，参数明文与签名结果全部打印，比扣 so 层代码便宜一个数量级；② 绕证书锁定——hook OkHttp CertificatePinner 等校验类，社区有现成通用脚本（如 objection 自带的 android sslpinning disable）。提醒一句：Frida 的版本管理是出名的坑——pip 装的 frida 版本必须与设备上 frida-server 版本完全一致，报错先查版本。

9.6 合规特别提醒 红线

App 爬取直接运行在真实设备与真实账号环境上，触碰的敏感面比网页爬虫大得多。以下红线不是"建议"，是"底线"：

⚠️ 合规红线：① 只在自有设备与授权环境（自己的测试机、公司明确授权的项目）上操作，不动他人设备与账号；② 不破解付费内容、不绕过版权保护；③ 不碰支付、账号隐私、个人通信数据——这类数据看一眼都可能构成违法；④ 抓到的数据同样要遵守第 01 章合规自查：公开数据、频率礼仪、用途合法；⑤ 《刑法》第 285、286 条对非法获取计算机信息系统数据、破坏计算机信息系统有明确规定——技术无罪，用法有界。
App 爬取五大坑：① Android 7+ 用户证书不被 App 信任——要么 Root 后用 Magisk 模块装成系统证书，要么换 Android ≤ 6.0 的测试机，别对着"抓不到"干瞪眼；② App 检测代理/Root 后拒绝运行——先关代理启动 App、再挂代理刷新，或用隐藏 Root 的方案；③ WebView 混合页抓不到——H5 走了另一套网络栈，先用 chrome://inspect 分清请求来自 native 还是 WebView 再对症下药；④ Frida 报错先查版本——pip 的 frida 与设备上的 frida-server 必须版本完全一致，其次查 frida-server 是否已启动、USB 是否授权；⑤ mitmproxy 挂上没流量——手机与电脑不在同一网段、或电脑防火墙拦了 8080 端口，先 ping 通再说。

Q1动手：改造 9.2 的 addon 脚本——只保存目标 App 的 JSON 响应，并写入 SQLite（表结构含 url、method、resp、ts 四列），启动命令写出来。动手

考点：9.2 mitmdump addon 事件模型 + 第 04 章 SQLite 落库的衔接。

参考解析：核心改动：把 open(OUT, "a") 换成 sqlite3 连接，并在脚本顶部建表一次（addon 被 mitmdump 加载时执行一次即可）：
import sqlite3, json
from mitmproxy import http

db = sqlite3.connect("app.db")
db.execute("CREATE TABLE IF NOT EXISTS cap"
           "(id INTEGER PRIMARY KEY, url TEXT, method TEXT, resp TEXT, ts REAL)")

def response(flow: http.HTTPFlow):
    if "api.example.com" not in flow.request.host: return
    db.execute("INSERT INTO cap(url, method, resp, ts) VALUES(?,?,?,?)",
               (flow.request.pretty_url, flow.request.method,
                flow.response.get_text(), time.time()))
    db.commit()
启动：mitmdump -s app_capture.py -p 8080。要点：addon 模块级代码只执行一次，适合建表；每条 insert 后 commit 防止异常丢数据。

考点：9.3 SSL Pinning 的概念与应对决策。

参考解析：这是 SSL Pinning 证书锁定：App 在代码里内置了服务器证书/公钥指纹，握手时额外校验，发现是抓包工具的中间人证书就主动断开——所以浏览器能抓、这个 App 抓不到。应对：① Frida 反钉扎（hook 校验类如 OkHttp CertificatePinner 使其恒通过）——适合需要长期稳定抓取、且愿意搭 Frida 环境的场景；② 换测试对象（低版本 App/未启用 pinning 的调试包）——零额外工具，最快见效，但版本可能缺新接口；③ 换数据源（Web 端/小程序端同源接口）——当目标数据有其他渠道时性价比最高，应优先评估。决策原则回到 9.3 成本排序：先试便宜的路线。
Q3决策：你要采集某 App 的 10 万条商品数据，发现接口参数由 so 层加密、团队没有逆向经验、工期两周。直连接口、Appium、Frida Hook、so 层逆向四条路，你怎么选？给出决策依据与风险。设计

考点：9.3/9.4 的成本排序思想与 9.4"何时选 Appium"。

参考解析：按成本排序逐级评估：① 直连接口——so 层加密+无逆向经验+两周工期 → 排除（还原成本远超工期）；② Frida Hook——有希望（hook 加密函数拿明文），但需要 jadx 逆向定位+真机环境，对新手有学习曲线，可作为备选路线并行试一周；③ Appium——最符合约束：无需理解加密，让 App 自己跑。10 万条数据量对 Appium 偏大（每屏几十条、要滑几万次），预计单机要跑数天，风险是 UI 改版与 App 崩溃；缓解：no_reset 保登录态、显式等待、失败重试、断点续采。④ so 层逆向——排除（经验与工期都不支持）。结论：主攻 Appium，同时用一周业余时间验证 Frida 路线；若数据源存在 Web 端，立刻切换直连。这题没有唯一答案，考的是"成本—工期—风险"的权衡表达。
