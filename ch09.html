09 · App 爬取：抓包与自动化

数据不只在网页上——App 的接口往往比网页更干净，但风控更"硬件化"。这一章打通四层能力：装证书抓 HTTPS、mitmproxy 脚本化自动采集、Appium 让 App 自己跑、Frida 在运行时拿到加密前的明文。

🔗 连接你已有的知识（考研 408 · 网络安全）

· mitmproxy 抓包 = 408 安全章节 TLS / CA 证书体系的直接应用：中间人之所以能解密 HTTPS，完全依赖"设备信任了你的根证书"——你在 01 章见过的握手流程，这里要亲手操作一遍；
· 会话密钥：抓包工具替两端各协商一把对称密钥（数字信封的原理），所以才能既骗过 App 又骗过服务器；
· Frida Hook = 运行时函数调用拦截：在"调用"与"实现"之间插一层，本质是对函数入口地址/虚表的改写——理解成"给函数装了个代理"；
· Appium 控件树 = 你已经会的 DOM 定位思想：树换成了 uiautomator 的控件树，定位器语法换了，思路一模一样。

9.1 抓包基础设施 对齐教材 11.1

手机抓包的原理和网页抓包完全一样：都是中间人。手机的全部流量先经过电脑上的抓包工具，工具装一张自己的 CA 证书替两边加解密。区别在于手机不归你写代码控制，所以要先搭好三件基础设施：电脑开代理服务 → 手机 WiFi 代理指向电脑 → 手机安装并信任工具的 CA 证书。任何一步缺失，表现都是"抓不到包"或"抓到一堆看不懂的密文"。

Charles 证书安装（两大平台流程）

平台证书安装信任设置代理指向
AndroidCharles：Help → SSL Proxying → Save Root Certificate 导出 pem/crt → 设置里"从存储设备安装证书"Android 7+ 的坑：App 默认只信系统证书，用户证书不生效——需 Root 后用 Magisk 模块把用户证书移入系统分区，或用 Android ≤ 6.0 的测试机长按已连 WiFi → 修改网络 → 手动代理 → 服务器填电脑局域网 IP，端口 8888
iOSSafari 访问 chls.pro/ssl 下载描述文件 → 设置 → 已下载的描述文件 → 安装必须再去 设置 → 通用 → 关于本机 → 证书信任设置 → 打开对 Charles 根证书的"完全信任"（这步漏掉 = 白装）WiFi → 配置代理 → 手动 → 电脑 IP:8888

装好证书只是第一步，Charles 还要开启 HTTPS 解密：Proxy → SSL Proxying Settings → 勾选 Enable SSL Proxying → 在 include 列表添加 *:443（或只加目标域名）。之后 App 的 HTTPS 响应在 Charles 里才是明文 JSON。验证方法：手机随便打开一个 App，Charles 里能看到请求列表且 Response 可读，基础设施就算搭好了。

搭好了还抓不到？先分两种情况：① Charles 里有这条请求但内容乱码/显示 SSL 错误 → 大概率是 9.3 的 SSL Pinning 证书锁定，不是你操作错了；② Charles 里连请求都没有 → 检查手机与电脑是否同一网段、防火墙是否放行 8888 端口。

Charles 适合人肉翻看，但爬虫工程师真正的主力是 mitmproxy：它开源、跨平台，最重要的是支持命令行与脚本化——抓包过程可以写成 Python 代码自动落库，这才叫"采集"而不是"查看"。它有三种运行模式，对应三种场景：

mitmdump addon 脚本（重点）

addon 就是一个普通 Python 文件：mitmproxy 是事件驱动的，每收到一个请求、一个响应，就触发你定义的对应函数。教材 11.3 用"得到 App"演示的抓包落库方法，通用化后就是这个模板——def request 做请求期处理，def response 做响应期过滤与保存：

app_capture.py —— mitmdump addon 完整示例
# 运行：mitmdump -s app_capture.py -p 8080
import json, time
from mitmproxy import http

TARGET = "api.example.com"          # 只关心这个域名的流量
OUT    = "app_capture.jsonl"

def request(flow: http.HTTPFlow) -> None:
    if TARGET in flow.request.host:
        print(f"[→] {flow.request.method} {flow.request.pretty_url}")

def response(flow: http.HTTPFlow) -> None:
    if TARGET not in flow.request.host:
        return                       # 不是目标域名直接放行
    try:
        body = flow.response.get_text()
        data = json.loads(body) if body else {}
    except Exception:
        return                       # 非 JSON 响应跳过
    item = {
        "url": flow.request.pretty_url,
        "method": flow.request.method,
        "req_headers": dict(flow.request.headers),
        "req_body": flow.request.get_text() or "",
        "status": flow.response.status_code,
        "resp": data,
        "ts": time.time(),
    }
    with open(OUT, "a", encoding="utf-8") as f:
        f.write(json.dumps(item, ensure_ascii=False) + "\n")
工程化提示：落盘用 JSONL（每行一个 JSON 对象）——手机一直产生数据，追加写不会损坏旧数据；后续 pandas.read_json(..., lines=True) 一行读入，直接接第 04 章的存储体系。人在 App 里正常点屏幕，数据就源源不断进文件——这就是教材 11.3 方法的通用化。

mitmdump 进阶：只抓目标域 + 直接入库

上面的模板存 JSONL 适合离线处理，工程里更常见的做法是边抓边入库。思路：request 事件里把目标域名的流量打上标记（这就是"过滤"），response 事件里只处理带标记的响应——解析 JSON 后直接写入 SQLite。注意 addon 的模块级代码只执行一次（被 mitmdump 加载时），建连接、建表放在这里正合适。另外别在 request 里粗暴丢弃非目标流量——那会把 App 的图片、CDN 请求全杀掉，页面加载不出来，你也就点不到目标页了：

app_to_db.py —— 只抓目标域并写入 SQLite
# 运行：mitmdump -s app_to_db.py -p 8080（手机代理照 9.1 指向电脑 8080）
import json, sqlite3, time
from mitmproxy import http

TARGET = "api.example.com"
db = sqlite3.connect("app_log.db")            # 模块级：加载时执行一次
db.execute("CREATE TABLE IF NOT EXISTS app_log"
           "(ts REAL, host TEXT, path TEXT, status INTEGER, body_snippet TEXT)")

def request(flow: http.HTTPFlow) -> None:
    # 请求期过滤：目标域打标记，其余流量原样放行（不影响 App 正常使用）
    flow.metadata["is_target"] = TARGET in flow.request.host

def response(flow: http.HTTPFlow) -> None:
    if not flow.metadata.get("is_target"):
        return                            # 非目标域：不解析、不落库
    try:
        body = flow.response.get_text()
        json.loads(body)                  # 只收 JSON：解析失败直接跳过
    except (ValueError, TypeError):
        return
    db.execute("INSERT INTO app_log(ts, host, path, status, body_snippet)"
               "VALUES(?,?,?,?,?)",
               (time.time(), flow.request.host, flow.request.path,
                flow.response.status_code, body[:500]))   # 正文截断 500 字符防膨胀
    db.commit()                           # 每条一提交：中途崩了不丢已抓数据
两处细节：① flow.metadata 是挂在 flow 上的字典，用来在 request 与 response 两个事件之间传状态；② body_snippet 只存前 500 字符——完整响应体让数据库快速膨胀，排查阶段够用，确需全量再单开一列。验证入库：sqlite3 app_log.db "SELECT * FROM app_log LIMIT 5"。

9.3 App 请求分析的特殊性 拓展

App 抓包不是"网页抓包换个小屏幕"。App 与服务器的关系更紧密，因此多了两道网页爬虫不会遇到的门槛：SSL Pinning 和 so 层加密。认识它们的边界，比多背几个工具更重要。

SSL Pinning 证书锁定

概念：普通程序校验证书走系统证书链（你的中间人证书装进系统就生效）；但 App 可以在代码里内置服务器证书或公钥指纹，每次握手时额外校验"对面给的证书和我内置的是不是同一张"——不是就直接断开。这叫 SSL Pinning（证书锁定）。表现：证书装好了、代理也通了，浏览器能抓，唯独这个 App 一打开就断网/全部请求失败。

应对思路：① Frida 反钉扎——用 Frida hook 住 App 的证书校验函数（如 OkHttp 的 CertificatePinner），让校验永远返回"通过"，社区有现成的通用 unpinning 脚本（9.5 给出 hook 最小模板）；② 换测试对象——有些 App 的低版本未启用 pinning，或存在关闭校验的调试包；③ 换数据源——看看有没有 Web 端、小程序端提供同源接口，绕开整个 App。思路 ③ 往往是性价比最高的。

so 层加密的边界

更深的门槛是参数在 so 库（C/C++ 编译的动态库）里计算：Java 层只是调个 JNI 接口，真正的加密逻辑在汇编级。逆向 so 需要 IDA/Ghidra 的静态分析功底，属于 App 逆向的另一门功课，投入产出比要冷静评估。务实的边界判断：遇到 so 层加密，先估算还原成本；成本过高就换数据源——Web 端接口、官方开放 API、或合规的数据采购。爬虫工程师的核心能力是判断"这条路值不值"，而不是头铁硬啃。

成本排序（从低到高）：直连接口 < 浏览器自动化（05 章）< Appium（9.4）< Frida Hook（9.5）< so 层逆向。永远先从最左边试起，每上一级之前问一句：这个数据值不值这个价。

9.4 Appium 自动化 对齐教材 11.4~11.6

当接口加密太深、还原成本过高时，有一条"降维"路线：让 App 自己跑。Appium 用代码模拟人点屏幕、读屏幕上的控件数据（UI 自动化）——请求是 App 自己发出的，签名自然是合法的，参数加密问题整个被绕开。代价是速度慢、脚本脆（UI 改版就要修），所以它是"接口打不动时"的选择，而不是第一选择。

Capabilities 模板代码

Capabilities 是一段"启动说明书"：告诉 Appium Server 连哪台设备、启动哪个 App、用哪个自动化引擎。下面是 Android 最常用的模板：

appium_demo.py —— 启动会话
from appium import webdriver
from appium.options.android import UiAutomator2Options
from appium.webdriver.common.appiumby import AppiumBy

options = UiAutomator2Options()
options.platform_name = "Android"
options.device_name   = "emulator-5554"          # adb devices 查到的设备名

options.app_activity  = ".MainActivity"          # 启动 Activity

options.no_reset      = True                     # 不清数据：保留已登录状态

何时选 Appium

① 接口参数被 so 层加密或深度风控，还原成本明显过高 → Appium；② 数据直接显示在 UI 上且采集量不大 → Appium 简单直接；③ 量大、要求长期稳定跑几万次 → 先想接口方案，Appium 是最后手段；④ 登录有验证码/扫码等人工环节 → 半自动：人登录一次，no_reset=True 保住登录态，脚本接管后续。

上手成本：Appium 本质是 WebDriver 协议——和你在 05 章用过的 Selenium 是同一套协议思想。会 Selenium 的人学 Appium，成本只有半天：换一套定位器和 Capabilities 而已。

Appium 补充：混合应用（WebView）的坑

现在大量 App 页面其实是 WebView 套壳：原生壳里嵌一个浏览器内核渲染 H5。这种页面在 NATIVE 层只能看到一个 android.webkit.WebView 大控件——里面的按钮、文本对 uiautomator 完全不可见。于是出现经典症状：Inspector 里怎么都定位不到页面元素，find_element 永远报 NotFound。九成原因就一个：没切 context。Appium 把页面分成两层容器：NATIVE_APP 是原生层，WEBVIEW_xxx 是每个 WebView 页面对应的网页层——定位器只在"当前层"里找元素：

webview_demo.py —— 切换 context 操作 H5 部分
# 进入 WebView 页面后，先列出所有可用上下文
print(driver.contexts)
# → ['NATIVE_APP', 'WEBVIEW_com.example.app']

driver.switch_to.context("WEBVIEW_com.example.app")   # 切进网页层
# 此后定位走网页那套（CSS/XPath/id），与 03、05 章完全一致：
from selenium.webdriver.common.by import By
driver.find_element(By.CSS_SELECTOR, ".article-title").click()

driver.switch_to.context("NATIVE_APP")               # 干完切回原生层
driver.find_element(AppiumBy.ID, "com.example.app:id/back").click()

第二个坑是 chromedriver 版本：UiAutomator2 驱动是借 chromedriver 操作 WebView 的，chromedriver 大版本必须与 WebView 内核（Chromium 版本）匹配，否则切 context 时报 chromedriver 相关错误。排查路径：电脑 Chrome 打开 chrome://inspect（手机开 USB 调试、App 需开启 WebView 调试，测试包才行）看内核版本 → 下载对应 chromedriver → 在 Capabilities 里指定路径：

Capabilities 指定 chromedriver
options.set_capability("appium:chromedriverExecutable",
                      r"C:\tools\chromedriver\chromedriver.exe")
判断该不该切 context：用 Appium Inspector 看页面源码——满屏 android.webkit.WebView 包着一个巨大节点、内部元素全看不到 → 该切了。也可以在 Capabilities 里设 "appium:autoWebview": True，会话启动后自动切进检测到的 WebView，但页面中途跳转仍要手动切。

9.5 Frida 入门 拓展

Frida 是动态插桩框架：把一段 JS 注入目标进程，在运行时改写任意函数的行为。对爬虫的意义有两点：hook 加密函数——明文输入和密文输出直接打印出来，还原算法变成"抄答案"；绕证书锁定——hook 住校验点让它永远通过（9.3 的应对①）。它站在比 Appium 更深的一层：不看 UI，直接看函数调用。

attach 与 spawn

姿势命令区别与适用
attachfrida -U -F -l hook.js挂到已在运行的进程；适合启动后才调用的函数
spawnfrida -U -f com.example.app -l hook.js --no-pause由 Frida 重启并注入；要在启动早期（如应用初始化阶段）拦截时必须用它

最小 hook 模板：Java.perform

hook.js —— hook 一个方法，打印输入与输出
// 目标类名/方法名从哪来：用 jadx 反编译 apk，全局搜加密参数名
Java.perform(function () {                          // 进入 Android Java 运行时
  var SignUtil = Java.use("com.example.app.SignUtil");  // 定位目标类
  SignUtil.sign.implementation = function (input) {     // 重写 sign 方法
    var result = this.sign(input);                  // 先照常执行原逻辑
    console.log("[sign] in =", input, "out =", result);
    return result;                                   // 明文与密文全拿到，再原样返回
  };
});
终端用法
adb devices                          # 确认设备已连接（真机开 USB 调试 / 模拟器）
pip install frida-tools              # 电脑侧工具
# 设备上需运行对应版本的 frida-server：adb push 后 ./frida-server &
frida -U -f com.example.app -l hook.js --no-pause    # spawn：重启并注入
frida -U -F -l hook.js                               # attach：挂到前台应用

两大典型用途：① hook 加密函数拿明文——配合 jadx 反编译定位到类与方法，一次 hook，参数明文与签名结果全部打印，比扣 so 层代码便宜一个数量级；② 绕证书锁定——hook OkHttp CertificatePinner 等校验类，社区有现成通用脚本（如 objection 自带的 android sslpinning disable）。提醒一句：Frida 的版本管理是出名的坑——pip 装的 frida 版本必须与设备上 frida-server 版本完全一致，报错先查版本。

Frida 从不是孤军奋战，围绕它形成了三层 hook 生态：Frida 是底座——动态插桩框架，能力最强但要自己写 JS 脚本；objection 站在 Frida 之上，把高频操作（枚举类、绕证书锁定、搜内存）封装成现成命令，不写一行脚本就能开工；Xposed / LSPosed 则是另一条技术路线——系统级模块框架，刷进系统后模块常驻生效，开机即 hook，不依赖电脑连线。三者的定位与取舍：

四个易错点，每个都能耗掉半天

① 成员变量必须加 .value

字段与方法可能同名，.value 明确表示取字段
console.log(this.m.value);   // ✓ 对
console.log(this.m);         // ✗ 错：打印的是方法对象

② 打印时机决定你拿到的是哪个值——这是最容易得出错误结论的一条。Hook 是在原方法执行前插入的，所以顺序反了就会永远拿到默认值或上一局的旧值：

先跑原逻辑，再打印
MainActivity.onClick.implementation = function (v) {
    this.onClick(v);                    // ← 先执行，m/n 在这一步被赋值
    console.log("M = " + this.m.value);   // 再打印 → 当前这一局的值
    console.log("N = " + this.n.value);
};

先打印的典型症状："点石头永远打印 0"，而且值总是滞后一局——因为打的是上一局留下的值。

③ 匿名类不在外部类里，要写 $1。new Runnable(){...} 这种匿名类编译后是独立类 MainActivity$1，去 MainActivity 里找 run 会报 implementation undefined：

匿名类的正确写法
var Inner = Java.use("com.example.app.MainActivity$1");
Inner.run.implementation = function () {
    this.run();
};

怎么确定编号：jadx 里能直接看到嵌套的类；或者反编译成 smali，在 MainActivity.smali 同级目录找 MainActivity$1.smali——一个 smali 文件就是一个类。

④ 内部类访问外部类字段要走 this$0。内部类持有外部类实例的引用，字段名就叫 this$0：

通过 this$0 拿到外部类实例
var Inner = Java.use("com.example.app.MainActivity$1");
Inner.run.implementation = function () {
    var outer = this.this$0.value;   // 外部类实例
    outer.n.value = 2;               // 篡改外部类字段
    outer.m.value = 1;
    this.run();
};

run.py

9.6 反编译与重打包：静态分析那条路 新 · 工程实战

9.5 的 Frida 是动态的路：让 App 跑起来，在运行时看值。这一节讲静态的路：把安装包拆开，读它的代码和配置。两条路不是二选一——实际工作中永远是静态定位候选、动态验证猜测，来回切换。

一、APK 就是一个 zip

把 xxx.apk 改名成 xxx.rar 直接解压，看到的目录结构就是它的真身：

解压后的目录
app/
├── AndroidManifest.xml     # 二进制，直接打开是乱码
├── classes.dex             # Java/Kotlin 编译产物，地位等于 Windows 的 exe
├── resources.arsc          # 资源索引表：把 R.id.xxx 映射到实际文件
├── res/                    # 编译后的资源，xml 已被压成二进制
├── assets/                 # 原样存放的静态资源，不编译
└── lib/
    ├── arm64-v8a/          # 真机主流
    ├── armeabi-v7a/
    ├── x86/                # 模拟器
    └── x86_64/

四个要点：

① classes.dex 是所有业务代码，被 ART 虚拟机加载执行。Dalvik 是老安卓（4.x 及以前）的虚拟机，现在全是 ART。

② assets/ 是最常藏东西的地方——App 内置的证书（抓包找证书先翻这里）、动态加载的 dex（加固和插件化的常见落点）。它不参与编译，原样存放。

③ lib/ 下的 so 不跨平台，按 CPU 架构分别编译。分析 so 前先确认自己手机的架构（getprop ro.product.cpu.abi），否则会对着一份根本不会被加载的文件分析半天。

④ AndroidManifest.xml 是二进制的，直接打开是乱码不代表文件坏了，只是没反编译。

日常就这几条

三、反编译三件套，各有各的活

工具形态能干什么独有能力
apktool命令行dex → smali，二进制 xml → 明文唯一能重打包的
jadx图形化dex → Java 源码，全局搜索、方法跳转、导出 gradle 工程日常主力，搜索最快
JEB图形化反编译 + 静态分析能读 so 里的字符串、合并多个 dex、自动解 base64
apktool 三条命令
apktool d app.apk          # 反编译：dex 消失，多了 smali/ 目录
apktool d -s app.apk       # 跳过 dex：assets 里有不规范 dex 报错时用
apktool b app目录           # 改完 smali 重打包，产物在 dist/

JEB 的三个补位场景很实用：jadx 搜不到的字符串，JEB 可能搜得到（它会解静态编码）；脱壳后产出几十个 dex，JEB 能合并后一次搜索；so 里的静态字符串只有它能读。

三者都有 bug。jadx 打不开就换 JEB，apktool 报错就换 jadx 看代码——别花半天去修工具，那不是逆向工作。apktool 只在需要重打包时才必须用。

四、重打包、签名，以及为什么一启动就闪退

改包四步
apktool b app_dir                    # 1. 重打包 → app_dir/dist/app.apk

keytool -genkey -alias demo -keyalg RSA -keysize 2048 -validity 36500 \
        -keystore demo.keystore -storepass 你的密码 -keypass 你的密码 \
        -dname "CN=demo, OU=demo, O=demo, L=demo, ST=demo, C=CN"      # 2. 生成自签名证书

jarsigner -verbose -keystore demo.keystore -storepass 你的密码 \
          -signedjar app_signed.apk app_dir/dist/app.apk demo         # 3. 签名

adb install -r app_signed.apk        # 4. 安装

两条硬规则：

① 未签名的 APK 装不上——这是 Android 系统机制，不是可选步骤。

② 签名能装上 ≠ 能打开。开发者在自己代码里内置了原签名的指纹（MD5 或 SHA），启动时比对；你重新签名后指纹对不上，App 直接闪退。这就是签名校验。

所以改包的第一步不是改逻辑，是先判断它有没有签名校验、校验放在 Java 还是 so 里。现在越来越多放在 so 层，过校验的难度在上升。判断依据看下一节的启动流程——看不到任何界面就闪退 = 问题在启动阶段，优先怀疑签名校验 / root 检测 / 反调试这三件事。

9.7 Frida 定位实战：三个案例 新 · 案例复盘

9.5 给了模板，但真到现场，最难的从来不是写 hook，是不知道该 hook 谁。这一节把三个真实案例的定位过程走一遍：签名校验、请求签名、RSA 登录。三个案例用的是同一套流程，走熟一套就能通吃。

一、定位总纲：五步法

抓包，找出
看不懂的参数→ 关键字搜索
sign / enc→ 搜不到就
hook 系统类→ 打调用堆栈

复刻验证

搜得到关键字是最省事的情况，直接读代码。真正考验人的是搜不到——三种原因：被放到 native 层了、被加固了、被混淆手法藏起来了。下面第一个案例就是第三种。

整节最重要的一条判断：业务代码的方法名可以随便改、可以被混淆成 a.a.a，但系统类的方法名一个字都不能改。getPackageManager 改了就调不到了。所以系统类是永远稳定的锚点——这是所有定位手法的物理基础。

二、三种调用姿势

姿势什么时候用关键写法
被动 hook程序自己执行到那行才触发.implementation = function(){}
主动调用不想读代码，直接调它拿返回值静态方法 类.方法()；非静态 类.$new().方法()
造对象需要传对象进去类.$new(参数)
被动 hook 的三个"必须"
Java.perform(function () {
    var DD = Java.use("com.example.app.util.DD");

    // ① 有重载必须 overload，参数写完整类型名
    DD.a.overload("java.lang.String", "java.lang.String").implementation = function (p1, p2) {
        // ② 第一行先打 enter —— 这是唯一的"有没有进来"判据
        console.log("[enter] DD.a p1=" + p1);

        var ret = this.a(p1, p2);
        console.log("[ret] " + ret);

        return ret;   // ③ 有返回值必须 return，否则原逻辑被破坏
    };
});

只打 ret 不打 enter 是最常见的坏习惯：没打印时你分不清是"没进这个方法"还是"进了但打印失败"，等于白跑。

三、通用武器：打调用堆栈

这段代码整组课出现频率最高，复制即用：

showStacks() —— 借系统类现成的能力打堆栈
function showStacks() {
    console.log(
        Java.use("android.util.Log").getStackTraceString(
            Java.use("java.lang.Throwable").$new()
        )
    );
}

怎么读：从上往下扫，跳过 java.*、android.*、com.android.* 这些系统帧，第一个 com.<目标包名>.* 的帧就是调用点。

四、案例一：签名校验藏在哪

现象：只重打包、不改任何代码，装上去启动就弹"检测到软件被修改"，点确定退出。回 jadx 搜 signatures——一条都搜不到。

必修的前提知识：Java 层的签名校验是一串固定写法，任何实现都绕不开这三个方法：

原始形态，一共就这几行
PackageManager pm = ctx.getPackageManager();          // Context → PackageManager
PackageInfo pi = pm.getPackageInfo(ctx.getPackageName(), 64);
Signature[] sigs = pi.signatures;                     // → Signature[]
int cur = sigs[0].hashCode();                       // 或 toByteArray()
if (cur != 0x1a2b3c4d) {                             // 与写死的值比对
    android.os.Process.killProcess(android.os.Process.myPid());
}

所以反过来，这三个方法名就是 hook 锚点。

第一枪打偏了：hook Signature.hashCode()，用 spawn 启动（校验在启动阶段），结果毫无打印。这里有个极易误判的点——没打印 ≠ 没做校验。获取签名值的方式不止一种，还有 toByteArray()、toCharsString()。hook 系统类时要把同族方法都 hook 一遍。

第二枪命中
Java.perform(function () {
    var Signature = Java.use("android.content.pm.Signature");

    Signature.toByteArray.implementation = function () {
        var ret = this.toByteArray();
        console.log("[toByteArray] len=" + ret.length);
        showStacks();        // ← 打完这一枪，定位成功
        return ret;
    };
});

堆栈里只有一个业务帧，直接指到 com.controller.text.widget.a.a。

但进去一看，整个类里没有任何一处出现 toByteArray 字样。只有一堆长得像 Base64 的常量：

方法名被 Base64 编码后藏起来了
a("c2lnbmF0dXJl")              // = "signature"
a("Z2V0UGFja2FnZU1hbmFnZXI=")  // = "getPackageManager"
a("dG9CeXRlQXJyYXk=")         // = "toByteArray"

static String a(String s) {
    return new String(Base64.decode(s, 0));   // 只做解码
}

然后通过反射调用。还原时的固定套路：

① getMethod 是取方法，getField 是取成员变量——signatures 是字段不是方法，所以走 getField。② 从最内层括号往外还原，因为代码是里面先执行，找最深一层括号拆开、展开、再上一层。③ 全靠括号对齐，少一个括号整段就串了。

落地：要脱机永久生效只能改 smali。注意三个坑——smali 不能直接 return true，必须先 const/4 v0, 0x1 再 return v0；.registers 的数量要和实际用的寄存器对得上；改完必须保存再编译。

五、案例二：请求里的 sign 怎么来的

先分两堆：看得懂的（User-Agent、Accept、Cookie）原样抄；看不懂的（sign、enc、udid）逐个还原。已知字段还能反推量级：13 位数字 = 毫秒时间戳。

本节最实用的一个小技巧：搜关键字时只搜左边的引号。
不要搜 "sign"（带右引号），只搜 "sign。因为拼接有两种写法：sb.append("sign=") 带右引号能搜到，但 sb.append("sign" + "=") 带右引号就搜不到了。只搜左引号，两种都能命中。

搜完还要过滤：包名要和目标 App 一致。搜出来一堆 com.alipay.*、com.baidu.* 的全是第三方 SDK，跳过。

读代码的方向：短代码正着读，代码一长必须从 return 往回读。本例顺出来是这样一条链：

从 return 往回倒推
sign = a(String.format("%s##%s##%s", A, B, C))   // ← 先看最外层
         ↓
      MessageDigest.getInstance("MD5")
         ↓
      md.update(src.getBytes())  →  byte[] digest = md.digest()
         ↓
      for (byte b : digest) { 高位 & 低位各转一个十六进制字符 }   // → 32 位小写

## 这种分隔符是逆向时的强特征——一旦看到，基本就锁定了签名原文的拼装点。

整组课最该记住的工作习惯：每走两三步就复刻一次。
不要一口气分析到底。每分析两三个方法就复刻一次、打印一次、跟抓包值比对一次。分析太远之后一旦走偏，你回头根本不知道错在哪一步。第一次复刻只做两件事：打印入参（验证拼接分析对不对）、打印返回值（验证是不是抓包里的那个 sign）。两串一致 → 分析成立，可以往下推。

六、frida-rpc：不还原，直接调

前面所有脚本只能"看"，不能跟 Python 交互。RPC 让 Python 直接调用 App 里的方法——像 enc 那种要手写一大段字节处理的，用 RPC 拿真值成本低得多。

代价也要清楚：依赖手机在线、单线程、慢。所以原则是：能离线还原就离线还原，RPC 是兜底方案。

JS 侧
rpc.exports = {
    // 方法名别用大写开头，会报找不到方法
    getenc: function (plain) {
        var result = "";              // ★ 必须声明在 Java.perform 外面
        Java.perform(function () {
            result = Java.use("com.example.app.util.E").d(plain);
        });
        return result;
    }
};
Python 侧

四个必须注意的点：① rpc.exports 是固定关键字；② 参数只能是基本类型或 JSON 字符串，复杂对象跨语言传不了；③ 返回值变量必须声明在 Java.perform 外面，写在里面就是局部变量，return 出去是 undefined；④ 用 RPC 时要去掉脚本尾部的保活代码（setInterval 那句），否则会卡住不返回。

稳定性：RPC 和爬虫一个道理——不做容错一定活不长。请求卡住要加超时重试，手机跑久了无响应要定时重启 App，ADB 断了要 adb reconnect。另外，本地 USB 直连只是开发态，爬虫最终跑在云服务器上、手机在本地，中间要靠内网穿透把 ADB 端口暴露出去。

五个坑：① hook 系统类只 hook 一个方法就下结论——同族方法（hashCode / toByteArray / toCharsString）要全试；② 搜关键字带右引号，漏掉字符串拼接的写法；③ 一口气分析到底，走偏了不知道错在哪一步；④ RPC 里把返回值变量声明在 Java.perform 内部，拿不到值；⑤ 用 frida-rpc 时忘了注释掉 setInterval 保活代码，脚本卡死不返回。

9.8 加密还原：RSA 与响应解密 新 · 原理 + 实战

9.7 讲的是"怎么找到它"，这一节讲"找到之后怎么在 Python 里复现"。核心只有两块：RSA 的那几个必知参数，以及响应加密为什么比请求加密难找。

一、RSA：我们只需要用到其中一小块

为什么客户端能用公钥加密，我们也能复现：非对称加密是一对密钥，客户端只放公钥，服务端留私钥。公钥是公开的、写在 App 里的——所以"用公钥加密"这一侧，我们完全能自己复现，不需要私钥。

这一句决定了难度分布：逆向 RSA 请求参数容易（公钥在手，照着加密就行），逆向 RSA 响应解密难（那需要私钥，而私钥永远不会下发到客户端）。所以看到 App 用 RSA 加密请求，说明设计者只防了"篡改"，没防"抓包复现"。

数学上：私钥是 (N, D)，公钥是 (N, E)，N = p × q（两个超大素数之积），E 几乎永远是 65537。两者都含 N，区别只在 E 和 D——D 不泄露，私钥就安全。安全性来自大数分解的算力壁垒，不是算法保密。

二、padding：为什么同一个密码每次密文都不同

这是一个让很多人困惑的现象：抓包看登录请求，同样的密码，每次的密文完全不一样。**不是加密算法变了，是 padding 在变。**

padding 有两个作用，第二个是后来演化的：

作用为什么需要
对齐RSA 的数学公式要求明文长度是固定块的整数倍，业务数据不可能刚好凑上，要补字节
随机化如果只补固定的 0，同一明文 + 同一公钥，加密 100 次结果完全一样——攻击者可以逐字节试探。所以演化为每次填随机值

只要填充模式一致，服务端用私钥依然能正确解出。跨语言解密失败，90% 是填充模式对不上：

模式说明
NoPadding补 0，密文固定不变（不安全，很多新库已不支持）
PKCS#1 v1.5代码里常写 PKCS1Padding / PKCS1v15，现在最常用
OAEP更安全，安卓少见

三、两个能一眼认出 RSA 的特征

特征一：MIG 开头的长字符串。RSA 公钥在代码里不是两个数字，而是一段 MIGfMA0GCSq...。三层关系是：

N, E→ ASN.1 结构→ DER（二进制）→ base64→ PEM
带 BEGIN/END

所以"代码里有一段 MIG 开头的长字符串 + 一段 base64 解码逻辑"≈ 这里在做 RSA 公钥处理。想验证：把 PEM 中间那段丢进任意 base64 解码器，出来的二进制就是 DER。

特征二：−11 这个数字。RSA 不能加密任意长度的数据，超了直接抛 Plaintext is too long：

密钥长度密文长度明文最大长度
1024 位128 字节117 字节（128 − 11）
2048 位256 字节245 字节（256 − 11）

那 11 个字节是给 padding 预留的。这个数字是反推的强依据：so 里方法名被混淆成 a.b.c 看不出来，但如果代码里出现 128 - 11、key_len - 11、或者常量 117 / 245，基本可以钉死是 RSA。

明文超过上限怎么办？两条路：分组加密（少见）、混合加密（最常见）——先用 AES 把长明文压成 100 多字节，再用 RSA 加密那把 AES 密钥。看到"先 AES 再 RSA"不要奇怪，是被长度逼的。

四、安卓的 NoPadding 坑（整个第二章最隐蔽的坑）

现象：Python 用标准 PKCS1_v1_5 加密，密文长度或结果跟 App 对不上，服务端解不开，也不告诉你为什么。

根因：Cipher.getInstance("RSA") 这个"最普通"的写法，在安卓和标准 JDK 上默认填充不一样：

运行环境Cipher.getInstance("RSA") 的默认
标准 JDK / 大多数语言RSA/ECB/PKCS1Padding
Android（Conscrypt / OpenSSL 实现）RSA/ECB/NoPadding

也就是说，App 里那行看起来最普通的 RSA 调用，在安卓上其实是不填充的。Python 侧要手搓：

NoPadding 的裸 RSA
def rsa_encrypt_nopadding(plain: str, n: int, e: int) -> bytes:
    k = (n.bit_length() + 7) // 8          # 密钥字节长度
    m = int.from_bytes(plain.encode(), "big")
    c = pow(m, e, n)                       # 就这一行是 RSA 本体
    return c.to_bytes(k, "big")          # 左补 0 到密钥长度

一秒判定的方法：拿同一个明文加密两次——密文相同 = NoPadding，密文不同 = 有随机填充。这个测试比读代码快。

五、响应加密：为什么搜不到，怎么找

请求参数加密好定位：sign、token 这些关键字就在代码里，jadx 直接搜。

响应解密难：响应是服务器下发的，App 里根本没有这个字符串，搜不到。

突破口：安卓的网络请求是回调式的。request 发出时必然同时注册了回调（onSuccess / onResponse）。所以找到发请求的地方，下面紧跟的就是处理响应的地方。request 和 response 是成对的。

锚点说明
URL（最稳）URL 必须被提交，一定在代码里。搜的时候越短越好，先搜 host 的一部分——太长容易被字符串拼接断开
路径关键字sendcode、login 这类
请求头的固定字段—

搜 URL 还是搜不到？先怀疑三条路：字符串藏在 res/values/strings.xml（加固不加密资源）、反射 + 自定义 base64 编码、或者拼在 so 里。strings.xml 那条最好解决——jadx 里看到 getString(2131886xxx)，把十进制 ID 转成十六进制，然后对解包目录 grep -rin "转成的hex" ./res --include=*.xml。

六、通用武器：复刻一个类的所有方法

这是整章最有价值的通用技能。思路：既然定位到某个类专管网络请求，那就把它所有方法都 hook 一遍，打印所有入参和返回值，靠打印反推。不用猜、不用逐个读。

replicateClass —— 五步法
function replicateClass(className) {
    var Cls = Java.use(className);
    var methods = Cls.class.getDeclaredMethods();   // ① 拿 Method[]

    methods.forEach(function (m) {
        var name = m.getName();                    // ② 方法名
        var overloads = Cls[name].overloads;          // ③ 拿该名全部重载

        overloads.forEach(function (ov) {
            ov.implementation = function () {          // ④ 逐个替换实现
                // 组装 "类名.方法名(参数类型)"，重载靠类型区分
                var sig = className + "." + name + "(";
                for (var i = 0; i < ov.argumentTypes.length; i++) {
                    sig += ov.argumentTypes[i].className;
                    if (i < ov.argumentTypes.length - 1) sig += ",";
                }
                console.log(sig + ")");

                for (var i = 0; i < arguments.length; i++) {
                    console.log("  arg[" + i + "] = " + arguments[i]);
                }

                // ⑤ 免写形参列表地调原方法
                var ret = this[name].apply(this, arguments);
                console.log("  return = " + ret);
                return ret;
            };
        });
    });
}

关键在最后那句 this[name].apply(this, arguments)——不用写形参列表就能调用原方法，所以同一段代码能适配任意方法签名。

七、盲狙：不脱壳也能拿到 Key 和 IV

如果目标用的是安卓或 Java 系统自带的加密 API（绝大多数情况），还有一个更粗暴但极其有效的办法：把这些系统类全部 hook 一遍。

为什么这个办法成立：App 自己实现加密很难，通常直接调 JDK 类；而这些类的类名和方法名无法混淆（混淆了就调不到）。

类方法能抓到什么
javax.crypto.CiphergetInstance / init / doFinalAES / DES / RSA 加解密总入口
java.security.MessageDigestgetInstance / update / digestMD5 / SHA 摘要
javax.crypto.spec.SecretKeySpec构造方法Key 明文
javax.crypto.spec.IvParameterSpec构造方法IV 明文

优势：不需要脱壳、不需要读 so、甚至不需要反编译——命中后直接拿 Key / IV / 明文 / 密文，用 Python 就能复现。缺点：打印量巨大（第三方 SDK 也在调同一个 API），要靠抓包值比对筛选；如果加密是自己实现的或写在 so 里，就什么都 hook 不到。

两个打印技巧：① byte[] 直接打是乱码，必须先转 base64 或 hex 才能跟抓包里的字符串对上；② 打印顺序是先调用栈 → 再方法签名 → 再参数值 → 最后返回值，否则你不知道每个返回值属于哪个方法。

八、AES 三要素与那个 unpad 坑

要素要求
Key16 / 24 / 32 字节（对应 128 / 192 / 256 位）
IVCBC 模式必需，长度必须等于 block size（16 字节）
ModeCBC / ECB 等，两端必须一致
Python 复现
import base64
from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad

key = b"................"      # 16 字节
iv  = b"................"      # 16 字节

cipher = AES.new(key, AES.MODE_CBC, iv)
raw = cipher.decrypt(base64.b64decode(cipher_text))
plain = unpad(raw, 16)             # ★ 必须去补齐
print(plain.decode("unicode_escape"))

漏了 unpad 会导致后续解析报错——明文长度必须是 16 的倍数，不足补 0，解密后要还原。这是下一节 protobuf 解析失败的头号原因：解密后末尾带着一堆 \x00，protobuf 解析器会在那里崩掉。

unicode_escape 那一步也很实用：很多 App 把中文以 \u4e2d\u6587 形式存进 JSON 再加密，直接 decode 出来还是转义串，要再 unescape 一次。

五个坑：① 安卓 Cipher.getInstance("RSA") 默认 NoPadding，照抄 JDK 的 PKCS1 必失败；② 明文超过 密钥长度−11 直接抛错，要改用混合加密；③ AES 解密后忘了 unpad，导致后续 protobuf 解析崩；④ 盲狙打印 byte[] 不转 base64/hex，看到的全是乱码，无法跟抓包比对；⑤ 搜 URL 用了完整路径——太长容易被字符串拼接断开，先搜 host。

9.9 协议层：protobuf 与 native so 新 · 进阶

当 App 的接口既不是 JSON、也不是表单，而是一坨二进制时，多数人第一反应是"加密了"。但很可能根本没有加密——只是换了一种序列化方式。这一节讲两种情况：protobuf（不是加密，是序列化）和 .so（真的把逻辑藏到 C 层了）。

一、protobuf 不是加密，是序列化

protobuf（Protocol Buffers）是 Google 的数据序列化协议，和 JSON 是同一层级的东西，只是输出为二进制。因为没有密钥，只要有结构定义（或者猜出结构），谁都能解。

它体积只有 JSON 的 1/10 左右，原因很简单：JSON 每个字段都要重复写 "phoneNumber":，protobuf 只写字段编号，字段名完全不传——靠两端约定好的 .proto 对齐。

二、四个特征，一眼认出是 protobuf

特征怎么看
① 首字节 0x0a十六进制视图里以 0A 开头，基本可以怀疑（field 1, wire type 2）
② \x0a 分隔的"面条"文本视图里大量"\x0a + 一个长度字节 + 内容"的片段；纯 ASCII 部分能看到英文数字
③ 字段只有编号没有名字这就是它小的原因，也是解出来"字段名居然不存在"的原因
④ 代码痕迹jadx 里看到 Proto、ParseFrom、SerializeToString、CodedInputStream，或 import 里有 com.google.protobuf.*
抓包时的第一判断：看响应头。如果是 Content-Type: application/octet-stream，意思是"二进制，格式未知"——这时候先试 base64 解一次，还是乱的再考虑 protobuf 或加密。别一上来就往加密上想。

三、没有 .proto 怎么办（实战最常遇到）

逆向场景里，你既没有 .proto，也没有编译好的 _pb2.py。两条路。

路线 A：protoc --decode_raw——先把结构看出来，再手工还原 .proto。

不需要 .proto 就能看结构
protoc --decode_raw < response.bin
输出长这样
1 {
  1: "张三"
  2: 1001
  3: "a@b.com"
}
1 {
  1: "李四"
  ...
}
4 {
  1: "13800138000"
  2: 1
}

能解出所有值和层级，但解不出字段名——因为字段名压根不在数据里。还原规则：缩进层级 = message 嵌套；同一编号出现多次 = repeated；像可读字符串 → string，纯数字 → int32。字段名随便起（叫 name 还是 a1 都无所谓），只要编号和层级对，解析结果就一样。

缺点很实在：字段一多（二三十个）就非常痛苦，错一个类型或层级要排查很久，纯体力活。

路线 B：blackboxprotobuf（首选）——不需要 .proto、不需要 protoc、不需要编译，直接硬解。

装一个库，省掉手工还原的全过程
pip install blackboxprotobuf
import blackboxprotobuf as bbpb

# ① 直接解成 dict（msg）+ 自动推断的类型定义（typedef）
msg, typedef = bbpb.decode(proto_bytes)
print(msg)

# ② 或者直接输出 JSON
print(bbpb.decode_message_to_json(proto_bytes))

# ③ 改完之后编码回去（发请求时必须）
new_data = bbpb.encode_message(msg, typedef)

两个注意：改 dict 之后必须带着 typedef 一起编码回去，否则类型信息丢失、编不回去；字段名是数字编号（{'1': {...}}），这不影响使用——层级关系才是关键。

完整链路
抓包拿到 hex
  → bytes.fromhex()              # 16 进制转 bytes
  → AES-CBC 解密 + unpad        # 见 9.8 第八节
  → 得到 protobuf 二进制
  → bbpb.decode()              # 或者 protoc --decode_raw
  → dict / JSON，可读

发请求是反着来：encode_message → AES 加密 → base64 → 发出。注意请求体常常是 base64(AES(protobuf)) 三层套娃，少剥一层都解不出来。

四、.so：当逻辑被藏到 C 层

jadx 里看到方法体是空的、前面带 native 关键字，就是这种情况：

public native byte[] decodeTwo(byte[] data);

native 表示实现在 C/C++ 里，被编译成了 .so，放在 lib/<架构>/ 下。先确认架构（getprop ro.product.cpu.abi），否则会对着一份根本不会被加载的文件分析半天。

静态看：用 IDA Pro 打开 .so。JNI 导出函数的命名是有规律的——Java_包名_类名_方法名（包名里的点变下划线），所以能在函数列表里直接搜到对应 Java native 方法的实现。按 F5 反编译成伪 C 代码。

动态看：Frida 也能 hook native 函数，用 Interceptor.attach：

hook 一个 so 里的导出函数
var addr = Module.getExportByName("libnative.so", "Java_com_example_App_decode");

Interceptor.attach(addr, {
    onEnter: function (args) {
        // args[0] = JNIEnv*，args[1] = jobject/jclass
        // ★ 真正的 Java 参数从 args[2] 开始
        console.log("[enter] arg=" + args[2]);
        // 读一段内存（长度按需：AES 的 IV 是 16 字节）
        console.log(hexdump(args[2], { length: 16 }));
    },
    onLeave: function (retval) {
        console.log("[leave] ret=" + retval);
    }
});
最容易卡住的地方：hook 了但什么都不打印。三个原因按概率排——函数名拼错（导出名要和 nm -D 或 IDA 导出表里的一字不差）、so 还没加载（要等 dlopen，或改用 Module.load 之后再加 hook）、参数偏移搞错（JNI 的 args[0]/args[1] 是环境指针，不是你的第一个参数）。

readByteArray(16) 里的 16 是哪来的：AES 的 IV 和 block 长度都是 16 字节，Key 是 16/24/32。看到代码里读 16 字节，基本就是在拿 IV。常量本身就是线索——和 9.8 里 −11 是同一个思路。

五个坑：① 看到二进制就认定"加密了"——很可能只是 protobuf，先 base64 解一次再判断；② 解密后忘了 unpad，末尾一堆 \x00 让 protobuf 解析器直接崩；③ 手工还原 .proto 时内层 message 沿用了外层编号——内层编号从 1 重新开始；④ blackboxprotobuf 编码回去时丢了 typedef，类型信息没了；⑤ hook native 时从 args[0] 开始读参数，其实前两个是 JNIEnv* 和 jobject。

9.10 合规特别提醒 红线

App 爬取直接运行在真实设备与真实账号环境上，触碰的敏感面比网页爬虫大得多。以下红线不是"建议"，是"底线"：

⚠️ 合规红线：① 只在自有设备与授权环境（自己的测试机、公司明确授权的项目）上操作，不动他人设备与账号；② 不破解付费内容、不绕过版权保护；③ 不碰支付、账号隐私、个人通信数据——这类数据看一眼都可能构成违法；④ 抓到的数据同样要遵守第 01 章合规自查：公开数据、频率礼仪、用途合法；⑤ 《刑法》第 285、286 条对非法获取计算机信息系统数据、破坏计算机信息系统有明确规定——技术无罪，用法有界。
App 爬取五大坑：① Android 7+ 用户证书不被 App 信任——要么 Root 后用 Magisk 模块装成系统证书，要么换 Android ≤ 6.0 的测试机，别对着"抓不到"干瞪眼；② App 检测代理/Root 后拒绝运行——先关代理启动 App、再挂代理刷新，或用隐藏 Root 的方案；③ WebView 混合页抓不到——H5 走了另一套网络栈，先用 chrome://inspect 分清请求来自 native 还是 WebView 再对症下药；④ Frida 报错先查版本——pip 的 frida 与设备上的 frida-server 必须版本完全一致，其次查 frida-server 是否已启动、USB 是否授权；⑤ mitmproxy 挂上没流量——手机与电脑不在同一网段、或电脑防火墙拦了 8080 端口，先 ping 通再说。

参考解析：核心改动：把 open(OUT, "a") 换成 sqlite3 连接，并在脚本顶部建表一次（addon 被 mitmdump 加载时执行一次即可）：
import sqlite3, json
from mitmproxy import http

db = sqlite3.connect("app.db")
db.execute("CREATE TABLE IF NOT EXISTS cap"
           "(id INTEGER PRIMARY KEY, url TEXT, method TEXT, resp TEXT, ts REAL)")

def response(flow: http.HTTPFlow):
    if "api.example.com" not in flow.request.host: return
    db.execute("INSERT INTO cap(url, method, resp, ts) VALUES(?,?,?,?)",
               (flow.request.pretty_url, flow.request.method,
                flow.response.get_text(), time.time()))
    db.commit()

Q3决策：你要采集某 App 的 10 万条商品数据，发现接口参数由 so 层加密、团队没有逆向经验、工期两周。直连接口、Appium、Frida Hook、so 层逆向四条路，你怎么选？给出决策依据与风险。设计

考点：9.3/9.4 的成本排序思想与 9.4"何时选 Appium"。

参考解析：按成本排序逐级评估：① 直连接口——so 层加密+无逆向经验+两周工期 → 排除（还原成本远超工期）；② Frida Hook——有希望（hook 加密函数拿明文），但需要 jadx 逆向定位+真机环境，对新手有学习曲线，可作为备选路线并行试一周；③ Appium——最符合约束：无需理解加密，让 App 自己跑。10 万条数据量对 Appium 偏大（每屏几十条、要滑几万次），预计单机要跑数天，风险是 UI 改版与 App 崩溃；缓解：no_reset 保登录态、显式等待、失败重试、断点续采。④ so 层逆向——排除（经验与工期都不支持）。结论：主攻 Appium，同时用一周业余时间验证 Frida 路线；若数据源存在 Web 端，立刻切换直连。这题没有唯一答案，考的是"成本—工期—风险"的权衡表达。
