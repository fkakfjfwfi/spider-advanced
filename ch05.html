05 · Ajax 分析与动态渲染

右键"查看源代码"里没有的数据，怎么抓？这一章给你两条路：把 Ajax 分析到一根参数都不剩（接口直连，快），或者让真浏览器替你把页面渲染出来（Selenium / Playwright，稳）。学完这一章，"动态页面"不再是一道墙。

🔗 连接你已有的知识（考研 408 · 计算机网络 + 操作系统）

· AJAX = 408 计网"异步 + HTTP"的组合应用：异步 JS 在不重载页面的前提下向服务器发 HTTP 请求——你学过的请求/响应模型原样成立，只是发起者从"地址栏"换成了"JS 引擎"；
· Playwright 的自动等待 = 操作系统"同步原语"的思想：等条件就绪，而不是等固定时间——"轮询忙等 vs 条件阻塞"这道 408 经典选择题，在爬虫等待策略里原题重演；
· 本章没有新协议、新魔法：动态渲染只是把第 01 章"数据总在某个响应里"的结论，藏得更深了一层。找到那条请求，一切照旧。

5.1 什么是 Ajax 对齐教材 6.1

Ajax（Asynchronous JavaScript and XML）不是协议、不是库，而是一种技术组合：页面里的 JS 在不刷新、不跳转的前提下，自己在后台向服务器发起 HTTP 请求，拿到数据后只更新页面的某一块区域。今天 Ajax 背的早就不只是 XML，主流是 JSON；发请求的 API 也从老派的 XMLHttpRequest 进化到了现代的 fetch，但"异步 + HTTP + 局部更新"这个骨架二十年没变过。

页面里的 JS 是怎么要数据的

页面里的 JS（简化示意）
// 现代写法：fetch——页面加载后，JS 悄悄向接口要数据
const resp = await fetch("/api/movies?page=1");
const json = await resp.json();
document.querySelector("#list").innerHTML =
  json.data.map(m => `<li>${m.name} ${m.score}</li>`).join("");   // 局部更新，页面不刷新

// 老一辈的写法：XMLHttpRequest（老站仍在用，逻辑一模一样）
var xhr = new XMLHttpRequest();
xhr.open("GET", "/api/movies?page=1");
xhr.onload = function () { /* 数据到手，改 DOM */ };
xhr.send();

为什么"源代码里没有"

把网页想象成一场演出：服务器返回的原始 HTML 是"开播前的空舞台"——标题、骨架、脚本引用都在，但列表是空的。页面加载完成后，JS 才向 /api/movies 发起 XHR，把 JSON 数据搬回来，塞进 DOM——这就是局部更新。而右键"查看网页源代码"看到的，永远是开播前的那份原始 HTML；数据不在里面，在后来那条 XHR 响应里。

三层定位法（第 01 章 1.3 的结论回收）：源代码里有 → requests 直接抓；源代码没有但 Elements 有 → 数据是 JS 事后塞的，真正的源头是某条 XHR/Fetch 接口；接口都要带算不出的加密参数 → 逆向（第 08 章）或浏览器自动化（本章 5.4）。F12 的 Network 面板就是看穿这一切的透视镜。

5.2 Ajax 分析方法论 对齐教材 6.2 本章重点

接口分析是爬虫工程师的核心肌肉记忆，五步走，一步都不要省。目标只有一个：找到那条能被 requests 原样重放的数据请求。

① 筛选Network 勾 XHR/Fetch→ ② 清空🚫 清掉历史请求→ ③ 触发翻页 / 滚动 / 搜索→ ④ 对比Payload 找参数规律→ ⑤ 确认重放Preview + Copy as cURL

第 ① 步：打开 Network 面板，筛出 XHR / Fetch

F12 → Network 标签 → 点筛选栏的 Fetch/XHR 按钮。这一步是把 document、图片、CSS、JS 等噪音全部滤掉，只看"数据请求"——Ajax 拉的数据几乎必然走这两类。顺手勾上顶部的 Preserve log（保留日志），防止页面跳转把请求记录清空。

第 ② 步：清空列表，留一块干净画布

点左上角的 🚫（Clear）图标，把页面加载时的几十条历史请求全部清掉。为什么？因为接下来要看的是"哪个请求是在我做了动作之后新出现的"——画布越干净，新增的请求越显眼。这一步是新手最容易省略、老手绝不会省的一步。

第 ③ 步：触发动作，看谁冒出来了

在页面上点"下一页"、往下滚动、输关键词点搜索——页面哪里更新了，就触发哪里。此时 Network 里新冒出来的那几条请求，就是嫌疑人。把鼠标移上去看名字：/api/list?page=2 这种一看就是；track.gif、report 这种多半是埋点统计，别追错人。

第 ④ 步：对比载荷，找翻页参数的规律

连点三次"下一页"，得到三条同路径的请求。逐条点开 Payload（旧版叫 Params/Query String Parameters）标签，把三次的参数摆在一起对比——哪个参数变了，哪个参数就是控制翻页的开关。参数家族基本逃不出这张表：

参数家族载荷里的长相规律循环策略
page 型page=1 → 2 → 3整数自增，最直白while 循环 +1，空列表停（5.3）
游标型 cursor / offsetcursor=AbC123…下一页的"门票"藏在上一页响应里从响应取 next_cursor，空/null 停
时间戳型 timestamp1730000000000毫秒级当前时间，防重放代码现生成当前毫秒时间戳
签名型 sign32/64 位十六进制串由参数 + 密钥算出，删掉就 403先试直连；真校验就上第 08 章或 5.4 自动化

第 ⑤ 步：Preview 确认数据，Copy as cURL 重放

选中目标请求 → Preview 标签页，JSON 会折叠展开成一棵树——确认目标字段真的在这里、看清它的层级路径（比如 data.list）。然后右键这条请求 → Copy → Copy as cURL (bash)，粘到终端回车：终端里能吐出数据，说明这条请求是"自包含"的（Cookie、headers、参数全齐），可以直接转成 requests 代码（curlconverter.com 能自动转换）。转不出来（缺签名/Cookie）也别慌，记下缺什么——那是第 08 章或 5.4 要解决的问题。

肌肉记忆口诀：筛选 → 清空 → 触发 → 对比 → 确认重放。十分钟内分析不出翻页规律，九成是漏了"清空"或没对比 Payload。

5.3 Ajax 结果提取 对齐教材 6.3

      
接口找到了，接下来是把它变成代码。接口返回的是 JSON——比 HTML 好解析得多，不需要 XPath，只要按层级取数。先看一眼真实接口的返回长什么样：

      
接口返回的 JSON（典型双层封装）


{
  "code": 0,                        ← 业务状态码，0 表示成功（不是 HTTP 状态码！）
  "msg": "success",
  "data": {                          ← 业务数据包在 data 里，有时还更深：data.list
    "total": 52,
    "list": [
      {"name": "肖申克的救赎", "score": 9.7},
      {"name": "霸王别姬",     "score": 9.6}
    ]
  }
}

      
resp.json() 把响应体解析成 Python 字典，之后就是普通的字典操作：先看清楚真实层级，再一层层往下取——上面这个例子要写 resp.json()["data"]["list"]，直接取 ["list"] 就会 KeyError。


      
接口翻页循环：while 直到空列表

      
ajax_pager.py


import random
import time
import requests

s = requests.Session()
s.headers.update({
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 Chrome/126.0 Safari/537.36",
    "Referer": "https://demo-movies.site/hot",   # 从哪条页面发现接口，就填哪个页面
    "X-Requested-With": "XMLHttpRequest",        # 部分老站校验"这是不是 Ajax 请求"
})

page, movies = 1, []
while True:                                        # ① 循环翻页
    resp = s.get("https://demo-movies.site/api/movies",
                 params={"page": page, "size": 20}, timeout=10)
    resp.raise_for_status()
    items = resp.json()["data"]["list"]            # ② 按层级取数
    if not items:                                  # ③ 空列表 = 翻到头了，跳出
        break
    movies.extend(items)
    print(f"第 {page} 页拿到 {len(items)} 条")
    page += 1
    time.sleep(random.uniform(1, 2))               # ④ 体面：随机延时（第 07 章展开）

print(f"共 {len(movies)} 条，前 2 条：{movies[:2]}")


      
预期输出


第 1 页拿到 20 条
第 2 页拿到 20 条
第 3 页拿到 12 条
共 52 条，前 2 条：[{'name': '肖申克的救赎', 'score': 9.7}, {'name': '霸王别姬', 'score': 9.6}]


      
三个必要 headers 别省：User-Agent（冒充浏览器，requests 默认 UA 一秒暴露）、Referer（接口常校验来源页）、X-Requested-With（老站用来确认"你是 Ajax"）。游标型接口同理，只是把 page + 1 换成 cursor = 上一页响应里的 next_cursor，停止条件换成游标为空。另外注意有些接口把"有没有更多"放在 data.has_more 字段里，拿它当 while 条件更稳。


      
      
5.4 动态渲染处理：两条路 对齐教材 7.1 ~ 7.4

      
什么时候放弃接口直连、改走"浏览器自动化"？三个信号：接口带算不出的加密参数（sign/token）、数据只在登录/点击/滚动之后出现、接口层层套娃找不到源头。自动化的本质是：用代码驾驶一台真浏览器——它该渲染渲染、该执行 JS 执行 JS，你在旁边收割结果。代价是慢（一次渲染抵几十次直连），所以口诀永远是：先 A 后 B，A 快 B 稳。


      
路 ①：Selenium（老牌经典，对齐教材 7.1）

      
安装就两行：pip install selenium——新版内置 Selenium Manager，会自动下载匹配的浏览器驱动，不用再手动对版本号。Selenium 的全部招式可以浓缩成"八要素"：

      

        
#要素代码

        
1驱动管理webdriver.Chrome(options)，Manager 自动配 ChromeDriver

        
2启动浏览器options.add_argument("--headless=new") 无头模式

        
3打开页面driver.get(url)

        
4定位元素find_element(By.CSS_SELECTOR, …) / find_elements（复数）

        
5交互send_keys() 输入 / click() 点击 / clear() 清空

        
6执行 JSdriver.execute_script("window.scrollTo(0, …)")

        
7显式等待WebDriverWait + expected_conditions（等条件，不等人）

        
8收尾driver.get_cookies() 拿登录态 → driver.quit() 必须退出

      


      
selenium_render.py


from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support.ui import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

options = webdriver.ChromeOptions()
options.add_argument("--headless=new")                                # 无窗口运行
options.add_argument("--disable-blink-features=AutomationControlled") # 抹掉最显眼的 webdriver 特征
driver = webdriver.Chrome(options=options)

try:
    driver.get("https://spa.demo-movies.site/hot")        # ① 打开页面，浏览器自己渲染

    wait = WebDriverWait(driver, 10)                     # ② 显式等待：最多 10 秒，条件满足立即放行
    wait.until(EC.presence_of_element_located((By.CSS_SELECTOR, ".movie-item")))

    for item in driver.find_elements(By.CSS_SELECTOR, ".movie-item"):   # ③ 从渲染好的 DOM 提取
        print(item.find_element(By.CSS_SELECTOR, ".name").text,
              item.find_element(By.CSS_SELECTOR, ".score").text)

    driver.execute_script("window.scrollTo(0, document.body.scrollHeight)")  # ④ 执行 JS：滚到底触发加载

    cookies = {c["name"]: c["value"] for c in driver.get_cookies()}          # ⑤ 拿走 Cookie 交给 requests
    print(f"拿到 {len(cookies)} 枚 Cookie")
finally:
    driver.quit()                                        # ⑥ 不 quit 会残留进程占内存


      
预期输出


肖申克的救赎 9.7
霸王别姬 9.6
千与千寻 9.4
星际穿越 9.4
拿到 7 枚 Cookie


      
Selenium 补充四件套（对齐教材 7.1 的其余要点）

      
八要素之外，教材 7.1 还点名了四个高频场景。它们的共同症状是"元素明明在页面上，代码却够不着"——先认出场景，再对症下药：


      
① iframe 切换：很多站把播放器、编辑器、正文塞进 <iframe>（页中页）里。Selenium 的 find_element 只在当前 frame 里找，不先切进去，就永远 NoSuchElementException——这就是"明明看得见却抓不到 iframe 内元素"的全部原因：

      
selenium_frame.py


driver.get("https://demo-movies.site/player")
driver.switch_to.frame("player-iframe")           # 按 id/name 切入；也可传元素对象或第几个下标
print(driver.find_element(By.CSS_SELECTOR, ".video-title").text)   # 切入后才能看见
driver.switch_to.default_content()                 # 用完切回主文档，否则主页面元素又找不到了


      
② 多窗口句柄切换：点"在新窗口打开"后，新标签页开了，driver 却还停在旧页面——电视换了台，遥控器没换。用 window_handles 拿到全部句柄再切换：

      
selenium_windows.py


driver.find_element(By.LINK_TEXT, "查看详情").click()      # 新标签页打开
handles = driver.window_handles                        # 句柄列表：顺序 = 标签页开启顺序
driver.switch_to.window(handles[-1])                   # 切到最新开的标签页
# ……在新页面里提取数据……
driver.close()                                         # 关掉当前标签页
driver.switch_to.window(handles[0])                    # 切回主窗口继续干活


      
③ 原生弹窗处理：confirm / alert / prompt 这类弹窗不是 DOM 元素，find_element 定位不到，必须用 switch_to.alert 接管：

      
selenium_alert.py


driver.find_element(By.ID, "delete-btn").click()
alert = WebDriverWait(driver, 5).until(EC.alert_is_present())    # 显式等待弹窗出现
print(alert.text)          # 弹窗文案，如"确定删除吗？"
alert.accept()             # 点"确定"；dismiss() 是"取消"；prompt 弹窗先 send_keys() 输入


      
④ 执行 JS：有些操作原生 API 做不到或做不好——滚动到底触发懒加载、点击被遮挡的元素、直接改前端状态——交给 execute_script 在页面里跑一段 JS，它就是你的"浏览器后门"：

      
selenium_js.py


driver.execute_script("window.scrollTo(0, document.body.scrollHeight)")   # 滚到底触发懒加载
btn = driver.find_element(By.CSS_SELECTOR, ".hidden-trigger")
driver.execute_script("arguments[0].click();", btn)    # JS 直点：元素被遮挡也能点中
driver.execute_script("localStorage.setItem('page','3')")   # 直接改前端状态再刷新


      
路 ②：Playwright（现代首选，重点掌握）

      
Selenium 能做的 Playwright 都能做，而且更顺手：locator 操作前自动等待元素出现（天然少一半等待代码）、API 更现代、支持 Chrome/Firefox/WebKit 三内核。安装：pip install playwright 然后 playwright install chromium。但真正的杀手锏是响应监听：page.on("response") 让你挂在浏览器旁边，接口数据一到就直接截走 JSON——页面照常渲染，你却根本不用解析 DOM，"渲染"与"提取"两条需求一次满足：


      
playwright_direct.py


from playwright.sync_api import sync_playwright

results = []                                          # 截获的数据都进这里

def catch_api(response):                            # 杀手锏：监听每一张响应
    if "/api/movies" in response.url and response.status == 200:
        results.extend(response.json()["data"])       # 直接截获 JSON，绕过 DOM 解析

with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    page = browser.new_page()
    page.on("response", catch_api)                    # 先挂监听，再开页面

    page.goto("https://spa.demo-movies.site/hot")
    page.wait_for_selector(".movie-item")             # 自动等待：条件不满足就一直等
    page.screenshot(path="hot.png", full_page=True)   # 顺手截图存档

    page.locator(".movie-item").first.click()         # locator 交互前自动等待，不用手写 wait
    browser.close()

print(results[:2])


      
预期输出


[{'name': '肖申克的救赎', 'score': 9.7}, {'name': '霸王别姬', 'score': 9.6}]


      
为什么响应监听是杀手锏：遇到"参数算不出来"的接口，常规思路是两条——花三天逆向 sign（第 08 章），或者花三秒让浏览器自己算。Playwright 选后者：浏览器替你执行全部 JS，接口响应回来时你在 page.on("response") 里半路截胡，拿到的是浏览器"亲口"承认的 JSON。逆向保证"拿得漂亮"，自动化保证"先拿得到"，两条腿走路。


      
Playwright 补充：登录态复用与移动端模拟

      
渲染方案最贵的开销是"每次都从零开始"——重新登录、重新过验证码、重新等首屏。Playwright 给了两件省钱装备，正好与第 06 章的 Cookie 复用思想打通。


      
① storage_state 登录态复用：把整个登录态（Cookie + localStorage + sessionStorage）存成一个 JSON 文件，下次启动直接注入——登录一次，长期复用。它和 6.5 手抄 Cookie 是同一个思想，只是由浏览器替你保管、且保得更全：

      
pw_storage_state.py


# 第一次：手动或自动化完成登录后，把登录态整体落盘
context = browser.new_context()
# ……登录流程……
context.storage_state(path="auth.json")

# 以后每次：启动即带登录态，跳过登录与验证码
context = browser.new_context(storage_state="auth.json")
page = context.new_page()                     # 打开即是已登录状态


      
② 设备模拟：很多站移动端与桌面端是两套页面、两套接口，移动版往往风控更松、结构更简单。Playwright 内置官方设备档案，一行换装：

      
pw_mobile.py


iphone = p.devices["iPhone 13"]               # 官方档案：UA/视口/触屏/像素比一次配齐
context = browser.new_context(**iphone, locale="zh-CN")
page = context.new_page()
page.goto("https://m.demo-movies.site/hot")   # 同一域名，移动版接口常是另一条


      
③ 反检测现状：Playwright 驱动的浏览器仍带自动化痕迹（navigator.webdriver === true 等），社区有 playwright-stealth 等补丁包可抹掉大部分特征，Selenium 阵营对应的是 undetected-chromedriver。反检测的本质是"让自动化流量不被误伤"——请只在授权平台与自己有权的账号上使用：拿它对抗真实站点的风控既不合规，也赢不了持续升级的检测。

      
pw_stealth.py（社区方案示意）


# pip install playwright-stealth
from playwright.sync_api import sync_playwright
from playwright_stealth import stealth_sync

with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    page = browser.new_page()
    stealth_sync(page)                        # 抹掉 webdriver 等常见自动化指纹
    page.goto("https://bot.sannysoft.com/")   # 经典自动化特征检测页，自查抹掉了多少
    page.wait_for_timeout(3000)


      
路 ③：Splash（了解即可）

      
一句话定位（对齐教材 7.2/7.3）：Splash 是一个带 JavaScript 渲染引擎的"无头浏览器即服务"，用 Lua 脚本描述"打开页面→等渲染→返回 HTML"，可配合 Scrapy 批量渲染。教材成书时它是主流方案之一，如今 Playwright/Selenium 已全面覆盖它的场景且生态更活跃——知道它是"渲染服务"这个角色即可，新项目不必选它。


      

        
🌐 多源视角 · 《Python3反爬虫原理与绕过实战》：先走完四步排除法，再谈渲染

        
韦世东在书里把"要不要上渲染方案"写成了一条排除链：源代码里没有数据 → 切到 Elements 面板能看到 → 说明数据是 JS 事后塞进 DOM 的，去 Network 找那条 XHR → 用 requests 直连试试 → 直连也失败（接口带加密参数或校验）——四步全部走完，才轮到本章的渲染方案。新手最常见的浪费，是第二步就直接开 Selenium：慢十倍不说，还错过了"接口其实根本不用逆向"的可能。

        

          
方案速度资源占用稳定性定位

          
接口直连（requests）毫秒级极低接口一改就挂，但好排查、好修复默认首选

          
渲染方案（Selenium / Playwright）秒级，慢 10~50 倍高：一个任务一个浏览器实例抗改版能力强，但怕弹窗、怕检测、怕内存膨胀接口死活拿不下时兜底

        

        
决策底线一句话：能用接口直连就别渲染。渲染是"全能的慢方案"，直连是"偏科的快方案"——先用 5.2 的五步法证明接口确实不可得，再心安理得地开浏览器。

      


      
本章五大坑：① 只看 Elements 不看 Network——Elements 是 JS 改过的实时 DOM，源代码里没有的数据要找的是那条 XHR；② iframe 没切入——iframe 里的元素必须先 driver.switch_to.frame(...)，否则 find_element 永远扑空；③ 把显式等待写成固定 sleep——time.sleep(5) 网快时白等、网慢时崩，WebDriverWait 等条件不等人；④ json 多包一层 data——{"code":0,"data":{"list":[…]}} 直接取 ["list"] 必 KeyError，先在 Preview 看清真实层级；⑤ 翻页参数双重编码——requests 的 params= 会自动 URL 编码，自己拼 URL 又手动 quote 一次，中文就变成 %25 双重编码，接口装聋作哑。

Q1一个瀑布流图片站，往下滚动才加载新图。如何把它"接口化"，变成一个纯 requests 的翻页爬虫？写出判断依据和循环代码。分析
        

          
考点：5.2 方法论 + 5.3 翻页循环，"滚动的本质是 XHR"的转化能力。

          
参考解析：判断依据：F12 → Network → 筛 XHR → 清空 → 慢慢往下滚，观察每次滚动新增一条 /api/photos?page=N 类请求 → Preview 确认图片数据在 JSON 里。既然"滚动到底 = 触发 page 自增的 XHR"，滚动加载就完全可以翻译成 while 循环：

import random, time, requests

s = requests.Session()
s.headers.update({"User-Agent": "Mozilla/5.0", "Referer": "https://gallery.demo.site/"})

page, photos = 1, []
while True:
    data = s.get("https://gallery.demo.site/api/photos",
                 params={"page": page}, timeout=10).json().get("data", [])
    if not data:        # 空列表 = 没有更多了
        break
    photos.extend(data)
    page += 1
    time.sleep(random.uniform(1, 2))
print(f"共 {len(photos)} 张")

          注意事项：首屏数据可能是 page=1，避免重复请求；若是游标型（cursor 在响应里），停止条件是 next_cursor 为空；直连被拒先补 Referer/UA，再考虑 5.4 自动化兜底。

        

      


      
Q2动手：目标站列表数据来自 /api/movies，但每次请求都带一个你算不出来的 sign 参数。写出用 Playwright 打开页面、截获该接口全部 JSON 并落盘 books.json 的完整代码。动手
        

          
考点：5.4 杀手锏 page.on("response")，"让浏览器替你算签名"。

          
参考代码：

from playwright.sync_api import sync_playwright
import json

data = []

def catch(resp):
    if "/api/movies" in resp.url and resp.status == 200:
        data.extend(resp.json()["data"]["list"])

with sync_playwright() as p:
    browser = p.chromium.launch(headless=True)
    page = browser.new_page()
    page.on("response", catch)              # 必须在 goto 之前挂监听
    page.goto("https://spa.demo-movies.site/hot")
    page.wait_for_selector(".movie-item")   # 等首屏渲染，保证 XHR 已发出
    # 翻页触发更多请求：点下一页直到按钮变灰，或滚动到底
    while page.locator("a.next:not(.disabled)").count():
        page.locator("a.next").click()
        page.wait_for_timeout(1500)
    browser.close()

with open("books.json", "w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False, indent=2)
print(f"共截获 {len(data)} 条")

          两个易错点：监听必须在 goto 之前挂上，否则首屏那一条 XHR 会漏掉；截获回调里只做"收数据"，别做重活（它是浏览器的事件循环在调你）。长期方案是把 sign 的算法排进第 08 章逆向清单。

        

      


      
Q3设计一个实验：同一列表抓 10 页，对比"Playwright 渲染提取"与"接口直连"的耗时。说明测量口径、要控制的变量、预期差距和结论怎么写。设计
        

          
考点：工程化实验设计能力——"自动化慢一个数量级"要靠实验说出口，而不是背结论。

          
参考解析：测量口径：用 time.perf_counter() 包住"从第一次请求到 10 页数据全部入库"的全过程（含等待与解析），两边各跑 3 轮取中位数，排除网络抖动。控制变量：同一网络环境、同一时间窗、同一 10 页范围、直连侧不加人为延时（或两边加同样的体面延时）。实验骨架：

import time

t0 = time.perf_counter()
# ……跑完 10 页（两条路各封装成一个函数）
print(f"耗时 {time.perf_counter() - t0:.2f}s")

          预期差距：渲染路每页要等图片/JS/CSS 全加载，10 页通常几十秒；直连路每轮几十毫秒，10 页往往 1~2 秒（其中大半还是你自己的延时）——10~50 倍很正常。结论写法："在数据可通过接口稳定获取的前提下，接口直连应作为默认路径；仅当接口不可得时降级到自动化"，并给出本实验的实测倍数作为依据。

        

      


      
Q4某接口每次请求都带 timestamp=1730000000000，删掉它返回 412。观察这个参数有什么规律？它和 sign 参数是什么关系？现阶段你怎么处理？分析
        

          
考点：5.2 第 ④ 步"对比载荷"的实战应用，参数家族识别。

          
参考解析：连续发几次请求对比载荷：timestamp 的值每次都变，且等于当前毫秒级 Unix 时间戳（13 位数字 ÷1000 ≈ datetime.now()）——它不是秘密，是"防重放"：服务器拒绝时间偏移过大的旧请求。与 sign 的关系：很多站把 timestamp 拼进签名串一起算，改了 timestamp 就必须重算 sign，所以它常是 sign 的"盐"。处理策略分级：① 如果服务端只校验时间偏移不校验签名 → 代码里 int(time.time() * 1000) 现生成即可直连；② 如果连 sign 一起校验 → 短期用 Playwright 让浏览器自己算（5.4），长期排进第 08 章逆向清单。判断属于哪种情况的方法：只改 timestamp 发请求，看返回 412 还是 200。
