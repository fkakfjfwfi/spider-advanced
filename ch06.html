06 · 验证码识别与模拟登录

验证码的本质是"证明你是人"，而我们的目标不是硬刚：能绕则绕（Cookie 复用），该打则打（OCR / 打码平台）。这一章还顺带解决爬虫的另一大命门——登录态的获取与批量维持，这是工程化采集绕不开的一关。

🔗 连接你已有的知识（考研 408 · 网络安全）

· 验证码 = 408 安全里的"人机证明"：CAPTCHA 的全称是"全自动区分计算机和人类的图灵测试"——它考的不是密码学，而是"区分主体是人还是程序"这一认证学命题；
· Cookie 复用 = 身份认证机制的攻防视角：你学过"证明身份靠凭证（口令/令牌/证书）"，而 Cookie 冒充正是绕过"重新认证"直接持凭准入场——合法与否只取决于目标站的服务条款与数据授权，本章从技术讲清它，红线自己守；
· CSRF token（登录表单里的 authenticity_token）正是 408 安全章节里"防跨站请求伪造"的手段——爬虫只是把它当成"必须一起提交的隐藏字段"。

6.1 图形验证码识别 对齐教材 8.1

先建立全景：验证码是一个强度阶梯，越往上机器成本越高。本章的策略分配也在这张表里——低强度直接识别，中强度识别+模拟，高强度能绕则绕：

类型强度机器怎么破本章策略
图形数字/字母码★OCR 识别ddddocr 直接识别（6.1）
滑动验证码★★缺口识别 + 轨迹模拟识别 + 轨迹（6.2）
点触（按语序点文字）★★★需要语义理解打码平台接入（6.3）
宫格 / 图标选择★★★需要语义理解打码平台接入（6.3）
行为验证（无感）★★★★环境指纹 + 行为模型Cookie 复用绕开（6.5）

ddddocr：一行装好，两招吃遍低强度验证码

老牌方案是 Tesseract OCR（pip install pytesseract 还要另装系统引擎），对扭曲彩底图形码准确率一般、环境配置繁琐——知道即可，不必再上手。如今 Python 生态的事实标准是 ddddocr（带带弟弟 OCR）：纯 pip 安装、开箱即用，对常见数字字母码识别率可观。它有两种核心用法：

用法方法输入返回适用
① 文字识别classification(img)图片二进制 bytes识别出的字符串图形数字/字母码
② 目标检测detection(img)图片二进制 bytes（构造时 det=True）[[x1,y1,x2,y2], …] 坐标框列表点选码的文字坐标
ocr_basic.py
# pip install ddddocr
import ddddocr

ocr = ddddocr.DdddOcr(show_ad=False)        # 关掉启动提示
with open("captcha.png", "rb") as f:          # 注意：吃的是图片二进制 bytes，不是路径
    code = ocr.classification(f.read())
print(code)                                   # 例如：'x7kd'

用法②是给点选验证码准备的：题目往往要求"按顺序点击'王、芳、好'"，OCR 只知道图上有字、不知道字在哪——det=True 的检测模式把每个文字的外接框坐标报出来，交给打码平台排序或自行匹配：

ocr_detect.py
import ddddocr

det = ddddocr.DdddOcr(det=True, show_ad=False)
with open("click.png", "rb") as f:
    boxes = det.detection(f.read())
print(boxes)   # 例如 [[46, 55, 92, 101], [188, 62, 233, 108], [303, 48, 350, 95]]
               # 每个元素是一个文字的外接框 [x1, y1, x2, y2]，点选码的坐标来源

"失败就刷新重试"的成本账

识别率不是 100%，工程上常见做法是"识别错了 → 刷新换一张 → 再识别"。这套循环的隐性成本要算清楚：平均尝试次数 = 1/p（p 为单次识别率），而每一次失败重试，都在给对方的风控计数器加一：

单次识别率 p平均尝试次数 1/p每千页额外请求量建议
95%1.05 次+50放心自动重试
85%1.18 次+180自动重试，但设失败上限
60%1.67 次+670认真考虑打码平台
40%2.5 次+1500别硬刚：绕开或换平台
成本账的另一半：重试循环必须配三道保险——失败就刷新换图（同一张图反复 OCR 没有意义）、设连续失败上限（如 3 次就告警/换号）、重试之间加随机间隔。识别率低于五成的图形码，硬刚的期望成本已经超过打码平台按条计费的价格——这笔账要在动手前算。

6.2 滑动验证码 对齐教材 8.2

滑动验证码把"拖动滑块到缺口"包装成小游戏，实际上是一道两步合成题：第一步知道缺口在哪（视觉问题），第二步让滑块像人一样滑过去（行为问题）。两步都要对，缺一不可。

第一步：缺口位置识别

常规做法是 OpenCV：对背景大图做 Canny 边缘检测 + 模板匹配，缺口边缘的位置就是答案。更省事的路径是 ddddocr 自带的 slide_match——传入"滑块小图"和"背景大图"两张 bytes，直接返回缺口坐标：

slide_gap.py
import ddddocr

det = ddddocr.DdddOcr(det=False, ocr=False, show_ad=False)   # 只要滑块匹配功能
with open("slider.png", "rb") as f1, open("bg.png", "rb") as f2:
    res = det.slide_match(f1.read(), f2.read(), simple_target=True)
print(res)      # {'target': [180, 32, 258, 110]} → 缺口左上角 x 就是目标距离
                # 实际滑动距离 = 缺口 x − 滑块初始偏移（各站实现不同，测一次就知）

第二步：轨迹模拟——先快后慢 + 回拉

拿到距离就可以让 Selenium/Playwright 的 ActionChains/mouse.move 分段移动过去。但匀速直线移动 = 机器人自首：真人的手是先加速冲、临近目标减速、最后还带一点过冲回拉的抖动——服务端校验的不是终点坐标，而是整条时间序列的行为特征：

阶段行为为什么像人
加速段（前 ~70%）步长大、间隔短，快速冲过中点人手起手快，目标远时出手果断
减速段（后 ~30%）步长按比例衰减，缓慢逼近缺口临近目标人眼会校准，速度自然下降
回拉段（结尾）滑过头 1~2px，再弹回修正过冲-修正是人手最典型的微动作
gen_tracks.py（可直接运行的轨迹生成器）
import random

def gen_tracks(distance):
    """"先快后慢 + 回拉"的滑动轨迹：返回每一步的位移列表"""
    tracks, moved, v = [], 0.0, 0.0
    while moved < distance:
        remain = distance - moved
        if remain > distance * 0.3:                 # 前 70%：加速冲
            v += random.uniform(2, 4)
        else:                                       # 后 30%：减速逼近
            v = max(1.0, v * random.uniform(0.55, 0.8))
        step = min(v * 0.1, remain)                 # 每一小步不超过剩余距离
        tracks.append(round(step, 2))
        moved += step
    tracks[-1] -= random.uniform(1, 2)              # 回拉：多滑一点
    tracks.append(1.5)                              # 再弹回修正
    return tracks

print(gen_tracks(200))
预期输出（每次随机不同，形态一致）
[3.55, 6.93, 9.7, 11.8, 9.9, 7.4, 5.6, 3.2, 2.4, 1.9, 1.4, 1.1, 0.4, -1.62, 1.5]

把这份轨迹喂给自动化框架逐段移动（每步之间 time.sleep(random.uniform(0.005, 0.02)) 加抖动），就是一次完整的滑动。注意三点：总位移要与缺口距离吻合（回拉已包含在内）；步数别太少（少于 10 步的轨迹一眼假）；别复制粘贴网上的固定轨迹数组——固定轨迹被风控端拿去当特征库，一抓一个准。

6.3 点触 / 宫格验证码 对齐教材 8.3 / 8.4

点触（按语序点击图中的文字）和宫格（点击符合描述的图标）把难度从"看得清"升级到了"看得懂"——需要语义理解，OCR 搞不定，自研模型性价比极低。现实的标准答案只有一个：打码平台——你把截图传上去，平台的真人/AI 混合队列把坐标传回来，按条计费。

打码平台接入思路

步骤内容注意
① 截图截取验证码区域（点选要连题目一起截或分两次传）截图坐标系与页面点击坐标系必须一致，注意缩放比
② 上传图片 base64 + 题型编号（typeid）POST 给平台各平台编号表不同：数字码/点选/滑块各占一个号
③ 等结果平台返回坐标串或文字序列设置 30s 超时；有的平台要轮询取结果
④ 还原按返回的顺序依次点击对应坐标点选类顺序错 = 全盘失败
solver_click.py（通用接入骨架，接口名以所选平台文档为准）
import base64
import requests

def solve_click(img_bytes):
    """把验证码截图交给打码平台，返回点击坐标序列 [[x, y], …]"""
    resp = requests.post(
        "https://api.dama-platform.com/create",
        json={
            "username": "你的账号",
            "password": "你的密码",
            "typeid": 7,                                   # 7 = 点选类（查平台编号表）
            "image": base64.b64encode(img_bytes).decode(),
        },
        timeout=30,
    )
    result = resp.json()        # {'id': ..., 'result': '[[46,78],[192,64],[305,90]]'}
    return eval(result["result"])   # 生产环境请用 json.loads 并做好异常兜底
本站立场：优先绕开，打码是最后手段。点触/宫格的破解成本（按条计费 + 秒级延迟 + 质量不稳）远高于"绕开它"的成本——人肉过一次验证码，Cookie 复用跑一整周（6.5）。打码平台留给"登录频次高、账号多、必须全自动化"的场景。此外提醒：打码服务同样要用于合规目标，只碰你有权采集的数据。

6.4 模拟登录 GitHub：方法论 对齐教材 10.1

模拟登录的通用方法论是五步，核心动作是"字段溯源"——载荷里的每个字段，都要能在登录页里找到出处。拿 GitHub 演示（方法论对任何站点通用）：

第 ① 步：抓登录请求

打开 github.com/login → F12 → Network → 勾选 Preserve log → 用测试账号手动登录一次 → 在 Network 里找到 POST /session，看它的 Payload：login（用户名）、password（密码）、authenticity_token（一长串会变的东西）、commit（"Sign in"）。

第 ② 步：表单字段溯源

逐个字段问"你从哪来"——在登录页右键查看源代码，Ctrl+F 搜索字段名，答案一目了然：

载荷字段出处说明
login你输入的用户名明文
password你输入的密码注意：有的站前端先加密再提交（见避坑②）
authenticity_token登录页 HTML 里 <form> 的隐藏 <input>CSRF 防护令牌，每次刷新页面都变——所以必须先 GET 登录页
commit提交按钮的固定文字照抄抓包值
其他杂项字段隐藏 input 或 JS 注入抓包看到什么就带上什么，宁多勿少

第 ③~⑤ 步：Session 收证 → POST → 校验

字段来源清楚了，代码就是三件事：用 Session GET 登录页（自动收下第一批 Cookie，并从 HTML 里提取 token）→ POST 表单（Session 自动带 Cookie）→ 访问"个人中心"类页面校验登录态（登录成功通常伴随 302 跳转和新的 logged_in=yes Cookie；失败则回到登录页）。

login_github.py
import requests
from bs4 import BeautifulSoup

s = requests.Session()
s.headers.update({"User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64)"})

# ① GET 登录页：Session 自动收 Cookie，顺便拿 HTML
html = s.get("https://github.com/login", timeout=10).text

# ② 字段溯源：token 就藏在 form 的隐藏 input 里
soup = BeautifulSoup(html, "html.parser")
token = soup.select_one('input[name="authenticity_token"]')["value"]

# ③ 按抓包看到的载荷逐字段对齐
data = {
    "commit": "Sign in",
    "authenticity_token": token,
    "login": "your_username",        # 换成你的测试账号
    "password": "your_password",
}
s.post("https://github.com/session", data=data, timeout=10)   # ④ POST：Session 自动带 Cookie

# ⑤ 校验登录态：访问需要登录的页面，看是否返回你的信息
me = s.get("https://github.com/settings/profile", timeout=10)
print("登录成功" if "your_username" in me.text else "登录失败")
预期输出
登录成功

现代站点的字段套路：难度阶梯

梯度套路破法
1隐藏 token 字段（CSRF）从登录页 HTML 提取（本节做法）
2密码字段前端 RSA/AES 加密引页面 JS 执行，或逆向算法（第 08 章）
3JSON 接口登录 + sign 签名逆向（第 08 章）或浏览器自动化（5.4）
4短信验证 / 扫码 / OAuth浏览器人工登录一次 + Cookie 复用（6.5）
方法论不变，难度在变：从最老套的表单提交到最现代的加密接口，"抓包 → 字段溯源 → 复刻请求"这五步永远成立——变的只是"溯源"的深度。字段全在 HTML 里（本节）→ 复刻请求即可；字段藏在 JS 加密里 → 第 08 章；字段靠扫码/短信 → 人工登录 + 6.5。另外 GitHub 对自动登录风控较强，本节代码用于理解方法论，练手请用授权练习站（如 Scrape Center login 系列）或自己的小号。

6.5 Cookie 复用：本章最实用技 必会

回头看 6.1~6.4 的成本表，你会发现一个事实：绝大多数验证码困境，最优解是"根本不再遇到它"。登录一次（无论人肉还是自动化）拿到的登录态就是一枚 Cookie，只要不主动退出、Cookie 不过期，之后的采集根本不需要再登录——这就是第 01 章 1.4 那句"保命技"的完整展开：

步骤操作在哪里
① 登录浏览器手动登录目标站（验证码人肉过）一次人工，几十秒
② 抄 CookieF12 → Application → Cookies → 目标域名 → 复制全部键值开发者工具
③ 注入整包塞进 requests.Session 的 cookies代码
④ 探活任务开始前请求"个人中心"类页面，确认登录态还在代码
⑤ 补货失效后重抄一次，或触发自动重登（6.6 的登录器）人工/定时
cookie_reuse.py
import requests

# ① 浏览器登录 → F12 → Application → Cookies → 全部抄下来
cookies = {
    "sessionid": "从浏览器抄来的会话凭证",
    "csrftoken": "……",
    "uid": "……",                    # 有几个抄几个，宁多勿少
}
s = requests.Session()
s.headers.update({
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64)",
    "Referer": "https://target.site/",
})
s.cookies.update(cookies)                          # ② 整包注入：之后每个请求自动带

# ③ 探活：访问一个"只有登录才看得到"的页面
resp = s.get("https://target.site/user/orders", timeout=10)
print("登录态有效" if "退出登录" in resp.text else "Cookie 过期了，重新抄一次")

有效期管理：让"抄"变成一套机制

Cookie 是有寿命的（Expires/Max-Age，第 01 章的属性表），工程上要把它当资源管理：探活前置——每次任务开始先访问特征页判断登录态；失效告警——探测失败立即通知补货，别让爬虫带着死 Cookie 空跑两小时；记录失效时间——多观察几次就能总结出"这个站 Cookie 大约活 7 天"的规律，到期前主动更换；多账号轮换——单账号 Cookie 撑不起采集量时，就该上 6.6 的 Cookies 池了。

6.6 Cookies 池搭建 对齐教材 10.2

当采集量需要多个账号分摊、单个 Cookie 又会过期时，把 6.1~6.5 的全部零件组装起来，就是 Cookies 池——一个"自动登录、自动验活、按需分发登录态"的小型生产系统。数据流一句话：账号队列喂给登录器，登录器产出 Cookie 存进 Redis，检测器定期验活，调度接口对外吐活 Cookie：

账号队列待用账号密码→ 登录器自动登录（含打码）→ Redis 存储账号 → Cookie→ 检测器定时探活/重登→ 调度接口/random 吐 Cookie
模块职责实现要点
账号队列存待用账号，按需取号Redis list/set；登录前先取号，防止重复登录同一账号
登录器自动登录产出 Cookie6.4 的五步 + 6.1~6.3 的验证码手段；登录太难的站允许"人工登录 + 自动收集"混合
存储（Redis）保存登录态hash：HSET cookies:site 账号 Cookie串；key 唯一，天然去重
检测器定时探活周期请求特征页；失效则剔除/触发重登；记录更新时间
调度接口对外服务Flask 暴露 /random：随机吐一个"探活通过"的 Cookie
cookies_pool_api.py（调度接口最小实现）
import random
from flask import Flask, jsonify
import redis

app = Flask(__name__)
r = redis.Redis(decode_responses=True)

@app.route("/random")
def random_cookie():
    keys = r.hkeys("cookies:target")        # hash：field=账号，value=Cookie 串
    if not keys:
        return jsonify({"error": "池子空了，等登录器补货"}), 503
    return jsonify({"cookie": r.hget("cookies:target", random.choice(keys))})

if __name__ == "__main__":
    app.run(port=5000)
预期输出（GET http://127.0.0.1:5000/random）
{"cookie": "sessionid=8f3ka9; uid=10086; csrftoken=…"}
# 池空时返回 503：{"error": "池子空了，等登录器补货"}
闭环达成：这个池子把本章所有零件串成生产线——登录器用 6.4 复刻登录、用 6.1~6.3 过验证码；检测器复用 6.5 的探活逻辑；业务爬虫只管调 /random 拿 Cookie 干活，完全不知道验证码的存在。第 07 章的代理池是同一套架构思想换了个被池化的资源。
本章五大坑：① 验证码连败风控——失败重试不设上限等于自爆，失败 3~5 次就应告警/换号/换 IP，重试间隔要拉开；② 密码字段前端加密——抓包看到的是 RSA/AES 密文，明文加密发生在 JS 里，复刻登录前先确认字段有没有加密，有就先去第 08 章报到；③ HttpOnly 不影响抓包——HttpOnly 只禁 JS 读取，F12 Application 面板和抓包工具照样看得到、抄得走，别被它唬住；④ Cookie 跨域失联——Cookie 绑定 Domain，a.com 的 Cookie 发给 b.com 的接口不会生效，整包注入时确认域名一致（含二级域名范围）；⑤ 拿生产账号练打码——多次失败触发账号风控，轻则锁号重则拉黑，练手请用小号或授权练习站。

📝 本章练习

先自己想，再展开参考解析。做完到练习场刷综合题。

Q1计算题：ddddocr 对某站图形码的单次识别率是 85%，目标采集 1 万个页面、每页都要过一次验证码。求平均总请求量；若风控规则是"单会话 1 分钟内失败 10 次锁定 30 分钟"，给出重试节奏设计。分析

考点：6.1 成本账的应用——把识别率换算成请求量与风控约束下的节奏。

参考解析：几何分布的期望：平均尝试次数 = 1/p = 1/0.85 ≈ 1.18 次/页，总请求量 ≈ 11800 次（比理想多约 1800 次失败请求）。节奏设计：① 每次失败先刷新换图再重试（同一张图重复 OCR 无意义且浪费风控额度）；② 重试间隔取随机 8~15 秒——1 分钟窗口内最多失败 6~7 次，始终低于"10 次锁定"红线，留出安全余量；③ 单会话连续失败 3 次说明可能触发了更难的验证码（强度升级），应休眠 60 秒或切换账号/IP；④ 全局层面把失败率写进监控：一旦实际失败率显著高于 15%（即识别率跌破 85%），说明对方换了验证码体系，人工介入而不是加大重试。
Q2动手：打开 github.com/login（或任意一个传统表单登录站），F12 完成一次登录抓包，列出登录 POST 请求的表单字段，并给每个字段找出它在登录页 HTML 中的出处。动手

考点：6.4 字段溯源法——模拟登录方法论的核心动作。

操作路径与预期发现：F12 → Network → 勾 Preserve log → 填表登录 → 找到 POST /session → Payload 逐字段对照源代码：以 GitHub 为例，authenticity_token 能在登录页 HTML 的 <form> 里找到隐藏 <input>（每次刷新页面值都变，这解释了为什么代码必须先 GET 登录页再 POST）；login / password 是你输入的明文；commit 是按钮固定值 "Sign in"；时间戳等杂项来自其他隐藏 input。练习注意：用测试小号操作，完成后在目标站退出会话；若你在别的站发现 password 抓包值是一长串乱码而非明文——恭喜，撞上了"前端加密"套路（避坑②），那是第 08 章的入场券。
Q3设计题：Cookies 池用多个登录器并发向 Redis 写 Cookie。可能产生哪些一致性问题？如何用 Redis 的数据结构设计去重与探活机制？设计

考点：6.6 架构能力 + Redis 数据结构选型（呼应第 04 章）。

参考解析：三个典型问题与对策：① 同一账号重复登录——两个登录器同时拿到同一账号，触发风控还浪费打码费。对策：取号用 SPOP（set 弹出即移除），或登录前 SETNX lock:账号 抢占 10 分钟的登录锁；② 重复写 Cookie——用 hash 存储 HSET cookies:site 账号 Cookie，field（账号名）唯一，覆盖写天然去重；③ 失效 Cookie 被调度出去——加一个 zset 记录探活状态：ZADD alive:site 时间戳 账号，检测器周期探活、失效即 HDEL + ZREM；调度接口只从 alive 里 ZRANGEBYSCORE alive:site (now-3600) +inf 取最近一小时验活过的账号随机吐出。再加一条：写库操作用 pipeline 批量提交，检测器用定时任务（APScheduler/cron）独立进程跑，与登录器解耦。
Q4设计题：为一个点选验证码设计函数接口 solve_click(img_bytes) -> [(x, y), ...]，要求覆盖：上传、超时、失败重试一次、余额不足告警。写出伪代码并说明每个分支的设计理由。设计

考点：6.3 打码平台接入的工程化封装——外部依赖必须有兜底。

参考设计： 
def solve_click(img_bytes, timeout=30):
    try:
        task_id = upload(img_bytes)             # ① 上传，立刻拿到任务 id（异步平台）
    except requests.RequestException:
        raise CaptchaError("平台不可达")       # 网络 fail-fast，不重试（重试也是不可达）
    for _ in range(6):                         # ② 每 5 秒轮询一次，共 30s
        r = query(task_id)
        if r.state == "done":
            return parse_coords(r.result)       # ③ 成功：解析坐标
        if r.state == "failed":
            break
        time.sleep(5)
    return solve_click_once_more(img_bytes)     # ④ 失败重试一次（平台误判很常见）
                                                # 再失败就抛异常，由上层决定换图/换号
设计理由：上传与取结果分离（点选类平台多为异步队列，同步接口也要设 30s 硬超时防挂死）；重试只做一次且重试前换图（同一张图再报一次大概率还是错）；每次调用前查平台余额，低于阈值发告警——打码平台欠费导致的批量失败是最冤枉的爬虫事故；坐标解析后按页面缩放比换算（截图 2x 缩放时坐标要除以 2，这是点选最常见的"明明点对了却判失败"）。
