01 · 爬虫基础与抓包分析

爬虫的全部秘密都在 HTTP 里。这一章把"请求—响应"这条主线彻底吃透：报文结构、Cookie 会话、代理原理、F12 抓包——后面所有章节都建立在这一章之上。

🔗 连接你已有的知识（考研 408 · 计算机网络）

· HTTP 是 408 计网应用层的核心协议——你学过的"请求/响应模式、无状态、持久连接（HTTP/1.1 keep-alive）"在这里全部用上；
· DNS 解析 = 计网的应用层服务；TCP 三次握手 = 运输层知识，requests 建立连接时真实发生；
· Cookie/Session 解决的正是"HTTP 无状态"问题——这是 408 的经典考点，也是爬虫登录态的全部秘密；
· 你会发现在 Python 里发一个请求 = 用套接字 API 之上封装好的库帮你拼报文。四十8的底子在这一章是降维打击。

1.1 HTTP 深入 对齐教材 2.1

HTTP（HyperText Transfer Protocol，超文本传输协议）是一个基于 TCP 的应用层协议，采用请求—响应模型：客户端发一个 Request，服务器回一个 Response，一次交互结束。爬虫的全部工作，就是用代码精确复刻一条"服务器愿意理睬"的请求，然后把响应里的数据抠出来。

一条原始的 HTTP 请求长什么样

Request
GET /hot?page=1 HTTP/1.1          ← 请求行：方法 + 路径 + 版本
Host: demo-movies.site            ← 以下都是请求头（Headers）
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Referer: https://demo-movies.site/
Cookie: sessionid=8f3ka9; tz=Asia/Shanghai
Accept: text/html,application/xhtml+xml
                                  ← 空行（CRLF），标志头部结束
page=1&size=20                    ← 请求体（GET 一般为空，POST 在这里放数据）
Response
HTTP/1.1 200 OK                   ← 状态行：版本 + 状态码 + 短语
Content-Type: application/json; charset=utf-8
Set-Cookie: sessionid=8f3ka9; Path=/; HttpOnly
Server: nginx
                                  ← 空行
{"code":0,"data":[…]}             ← 响应体：真正的数据

常见请求方法

方法语义爬虫场景
GET获取资源，参数在 URL 里抓页面、抓接口，占爬虫请求的绝大多数
POST提交数据，参数在请求体里登录、搜索、翻页接口（很多站翻页也用 POST）
HEAD只要响应头不要体探测 URL 是否有效、拿文件大小
PUT / DELETE替换 / 删除资源（RESTful）调用开放 API 时会遇到

状态码：服务器的"表情包"

状态码含义爬虫遇到时怎么办
200成功照单全收，直接解析
301/302重定向requests 默认自动跟随；注意登录跳转常伴随新 Cookie
403Forbidden，拒绝执行请求头不全 / IP 被封 / 签名错误——第 07、08 章专门解决
404资源不存在检查 URL 与参数边界（翻页翻过头常见）
429请求过于频繁限流警告：加随机延时、降并发、上代理（第 07 章）
5xx服务器错误可能真故障，也可能是 JS 挑战（如 CF 503），配合重试与第 08 章手段

爬虫最该吃透的六个请求头

请求头作用爬虫意义
User-Agent自报浏览器/系统身份第一层人机识别；requests 默认 UA 一秒暴露（第 07 章化解）
Referer请求来源页面防盗链就查它——直连接口被拒先补它
Cookie携带身份凭证登录态 = 一枚有效 session Cookie（见 1.4）
Content-Type请求体/响应体格式application/json 接口最爱；x-www-form-urlencoded 是表单
Accept能接收的格式/语言严格风控会校验这组头是否像真浏览器
Authorization认证令牌（Bearer/JWT）现代站点登录态越来越多放在这里而非 Cookie
HTTPS 与 TLS（连接 408）：HTTPS = HTTP over TLS。握手阶段用非对称加密协商出对称会话密钥，之后全程对称加密——所以抓包工具（如 Fiddler/Charles）要做中间人：装自己的根证书替两边加解密（第 09 章 App 抓包会实际操作）。

1.2 Web 网页基础 对齐教材 2.2

网页由三种技术构成，爬虫视角下各有含义：

技术角色爬虫视角
HTML骨架（结构 + 内容）静态数据的载体，第 03 章解析它的主战场
CSS皮肉（样式）选择器语法顺带是解析定位利器；字体反爬也藏在 CSS 里（第 07 章）
JavaScript灵魂（行为 + 动态数据）Ajax 拉数据、加密参数都在 JS 里——第 05 章分析它、第 08 章逆向它

页面渲染流水线（连接 408"从 URL 到页面"）：解析 HTML 构建 DOM 树 → 解析 CSS 构建 CSSOM → 合成渲染树 → 布局 → 绘制。JS 可以随时修改 DOM——这就是"数据是事后塞进去的"（动态页面）的根源，也是第 05 章要解决的问题。

1.3 爬虫的基本原理 对齐教材 2.3

所有爬虫，无论多复杂，都是这个循环：

① 获取下载页面/接口→ ② 解析提取目标数据→ ③ 存储落库落盘→ ④ 调度更多 URL？回①

数据藏在三个地方，找数据的本质就是判断它在哪：

位置特征对策
初始 HTML 里右键源代码能搜到requests + 解析库（02/03 章）
XHR/Fetch 接口里源代码没有，Network 有接口直连（05 章）
JS 变量/加密参数里接口都要带 token/signJS 逆向（08 章）或浏览器自动化（05 章）

用 requests 复刻浏览器行为的的最小闭环长这样（02 章展开讲透）：

first_spider.py
import requests

url = "https://httpbin.org/get"
headers = {"User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64)"}
resp = requests.get(url, headers=headers, timeout=10)
resp.raise_for_status()          # 状态码不是 2xx 就抛异常，好习惯
print(resp.status_code)          # 200
print(resp.headers["Content-Type"])
print(resp.text[:200])           # 文本内容；二进制用 resp.content

1.4 会话和 Cookies 对齐教材 2.4

HTTP 本身无状态：服务器记不住"你是刚才那个人"。Cookie + Session 是补丁：服务器发给你一枚凭证（Cookie），你之后每次请求都带上，服务器就知道 continuity。

Cookie 的关键属性

属性作用爬虫注意
Domain / Path生效范围跨域请求不会自动带，抓包时注意哪个 Cookie 是关键
Expires / Max-Age有效期过期即失效——爬虫挂掉先查 Cookie 是不是过期了
HttpOnly禁止 JS 读取JS 摸不到但 HTTP 照带；用抓包工具/requests 照样拿
Secure仅 HTTPS 发送http 测试地址带不上，别奇怪
SameSite跨站限制（CSRF 防护）自动化跨站跳转时可能丢 Cookie

Session 的原理： sensitive 数据不放在 Cookie 里，服务器只发一个 sessionid，状态存在服务器端。所以"保持登录态"的本质 = 持有并续用有效 sessionid。requests 用 Session 对象自动完成"收 Cookie → 存 → 回带"：

session_demo.py
import requests

s = requests.Session()
s.headers.update({"User-Agent": "Mozilla/5.0"})

s.get("https://httpbin.org/cookies/set/token/abc123")  # 服务器发 Cookie，自动收下
r = s.get("https://httpbin.org/cookies")                # 后续请求自动带上
print(r.json())   # {'cookies': {'token': 'abc123'}}

# 也可以手动注入已有登录态（浏览器 F12 → Application → Cookies 抄过来）
s2 = requests.Session()
s2.cookies.update({"sessionid": "从浏览器抄来的值"})
最实用的保命技：遇到难啃的登录（验证码/扫码/风控），人肉在浏览器登录一次 → F12 抄全部 Cookie 给 Session → 代码直接带着登录态跑。Cookie 失效了再抄一次，成本几乎为零（第 06 章系统化讲登录）。

1.5 代理基本原理 对齐教材 2.5

代理 = 你和目标服务器之间的"中转站"：请求先发给代理，由代理代你去访问目标，目标看到的是代理的 IP。它解决两个问题：隐藏真实 IP 与 突破频率/IP 封锁（第 07 章实战代理池）。

维度分类说明
方向正向代理替"客户端"出面（爬虫用的就是它）
反向代理替"服务器"出面（Nginx/CDN，目标站的前排盾牌）
匿名度透明代理目标能 Via/X-Forwarded-For 看到你真实 IP——白用
匿名代理知道你是代理，但不知道你是谁
高匿代理看起来就是个普通用户——爬虫标配
协议HTTP / HTTPS / SOCKS5SOCKS5 更底层、通吃流量；requests 需装 requests[socks]
proxy_demo.py
proxies = {
    "http":  "http://127.0.0.1:7890",
    "https": "http://127.0.0.1:7890",   # https 走的隧道也用 http 代理承载
}
requests.get("https://httpbin.org/ip", proxies=proxies, timeout=10)
新手五大坑：① 只看 Elements 不看 Network，对着实时 DOM 白费劲；② 用 GET 请求带请求体、POST 参数塞 URL；③ 忘了 timeout，爬虫挂死一整夜；④ 429/403 一直无脑重试，把封禁升级成永久；⑤ 把 HttpOnly 当成"拿不到"——JS 拿不到不等于 HTTP 层拿不到。

Q1为什么说"HTTP 是无状态协议"？Session 和 Cookie 分别解决了什么？概念

考点：对齐教材 2.4，408 计网经典考点。

HTTP 每次 请求-响应 相互独立，服务器不保留上下文，这叫无状态。Cookie 是客户端存储、随请求回传的凭证；Session 是服务器端的状态存储，只把 sessionid 通过 Cookie 发给你。

参考解析：无状态简化了服务器设计（连接即用即弃），但业务需要"记住登录者"。方案：服务器登录后生成 session，把 sessionid 放进 Set-Cookie；客户端后续每个请求自动带 Cookie: sessionid=…，服务器据此查到会话。爬虫视角：保持登录态 = 持有并续用有效 sessionid（requests.Session 自动化这件事）。
Q2一个列表页的数据，右键"查看源代码"里搜不到，但页面上明明有。数据可能在哪里？如何确认？分析

考点：1.3 的"数据三藏处"判断力。

参考解析：三个候选：① JS 动态塞进 DOM 的（源代码没有、Elements 有）；② XHR/Fetch 接口返回的 JSON；③ 内嵌在 <script> 的 JS 变量里。确认方法：F12 → Network → 筛选 XHR/Fetch → 刷新页面 → 逐条看 Response：找到含目标数据的 JSON 即接口直连目标；若 XHR 都没有而 Elements 有，则是前端渲染，走第 05 章两条路。
Q3transparent（透明）代理为什么对爬虫毫无意义？高匿代理"高匿"在哪？概念

考点：对齐教材 2.5，代理匿名度分级。

参考解析：透明代理转发请求时会带上 X-Forwarded-For/Via 头暴露你的真实 IP——目标站既知道你用了代理、又知道你是谁，封你等于封真身。高匿代理两者都不带：目标看到的请求与普通用户无差别，无法从报文层面识别代理存在。"匿名度"衡量的是目标服务器能否看穿代理链。
Q4动手：打开任意一个你常用的网站，F12 找到"列表数据来自哪个请求"，把该请求 Copy as cURL，指出其中 User-Agent、Referer、Cookie 三个头的值，并判断数据在 HTML 还是 XHR 里。动手

考点：本章终极目标——"看得懂请求"。

操作路径：F12 → Network → 勾选 Preserve log → 刷新 → 找列表出现时刻新增的请求（优先筛选 XHR/Fetch）→ 点开看 Response 是否含目标数据 → 右键该请求 Copy → Copy as cURL (bash) → 观察 -H 'User-Agent: …'、-H 'Referer: …'、-H 'Cookie: …'。若在 document 类型请求的 Response 里能直接搜到数据 → 静态；在 xhr 请求里 → 接口。把 cURL 留存，第 02 章会把它转成 requests 代码。
