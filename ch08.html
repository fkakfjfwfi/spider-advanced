08 · JS 逆向专题

接口带着每次都变的 token/sign，删掉就 403——这一章教你把"看不懂的加密参数"变成"我自己生成的参数"。三板斧定位、指纹识别算法、扣代码补环境、webpack 与混淆还原：所有逆向都逃不出这套固定动作。

🔗 连接你已有的知识（考研 408 · 密码学 / 数据结构 / 编译原理）

· 加密参数 = 408 密码学的直接应用：对称加密（AES/DES）、非对称加密（RSA）、哈希（MD5/SHA 系列）——你背过的"对称快、非对称可逆、哈希不可逆"在这里全部落地成真实代码；
· 调用栈回溯 = 数据结构的栈：函数调用压栈、返回弹栈，断点冻结的就是栈顶现场；"从下往上跟"就是从入口帧往栈顶找嫌疑人；
· AST 抽象语法树 = 编译原理前端：词法分析 → 语法分析 → AST → 变换 → 目标代码，ob 混淆还原就是把编译原理当武器用；
· 你不需要懂数论，但需要认得出"这是哪种算法"——本章教的正是"识别 + 验证 + 还原"这门手艺。

8.1 加密参数的世界 教材外拓展

第 05 章你已经学会直连 XHR 接口。但你会很快撞上一堵墙：有些接口的请求参数里躺着一串每次刷新都会变的字符串，删掉它、或者随便改一个字符，接口立刻回你 403。这串东西就是加密参数——服务端用来判断"这个请求是不是由我的合法页面、走正常流程发出来的"的凭据。JS 逆向的全部目标只有一个：在 Python 里生成出和浏览器一模一样的参数。

⚠️ 合法边界（先立规矩再动手）：逆向技术的学习与练习，仅限授权平台与学习用途——猿人学 match、Scrape Center 等专门供人练习的授权站点。不要在未授权的真实站点上练手，不要碰账号数据与隐私信息，不要干扰目标业务正常运行。技术能力越强，越要先想清楚"我能不能这么做"。

加密参数的三大常见形态

形态常见名字长相与特征典型生成方式
tokentoken / ticket / access_token随会话或随请求变化，hex 或 Base64 串哈希（MD5/SHA）、服务器下发后本地续签
signsign / signature / sig请求参数的"签名"：任何一个参数变了它就变MD5(参数拼接 + 盐)、HMAC、AES
加密串m / enc / data / mst整段密文，Base64 或长 hex，长度稳定AES/DES 加密请求体、RSA 加密密码

怎么判断"这是加密参数"

三招判断法，30 秒出结论：① 刷新三次看变化——每次请求都变，基本是加密参数（注意区分"时间戳"这种每次都变但不校验的伪加密）；② 删掉重发——Copy as cURL 后删掉该参数重放，返回 403/自定义错误码即坐实；③ 固定值重放——把上一次的完整参数原样重放，若提示过期，说明参数绑定了时间戳或一次性随机数。三招都命中，才值得进入 8.2 的定位流程。

先想后做：遇到加密参数，第一反应不是"这好难"，而是按流程走：定位（8.2）→ 识别（8.3）→ 还原（8.4~8.6）。90% 的站倒在 8.3 这一步就结束了——因为大部分站用的就是 MD5 拼接这种简单组合。

前置：读懂混淆代码要掌握的六个 JS 机制

很多人卡在"代码每个字都认识，连起来看不懂"。真正的原因是JS 的几个特性被混淆器拿来当武器了。这六个机制不搞懂，后面所有技巧都是空中楼阁。

机制混淆器怎么用你该看什么
闭包把所有变量藏进一个立即执行函数的作用域里，外部断点看不见断点打在 IIFE 内部，作用域链里翻
IIFE(function(a,b){...})(x,y) 形成独立作用域，还能靠形参"洗白"变量名形参就是实参的别名，值在调用处
原型链在中间层覆写同名原生方法（如 valueOf），让你的判断拿到假值用 hasOwnProperty 确认是不是自有属性，断点里看清来自哪一层
this 指向五种绑定 + 隐式丢失，改一个调用方式结果就变别猜，断点里直接看 this
call / apply / bind强制改 this 指向，把函数"借"给别的对象用看到这三个就说明 this 被换过了
charCodeAt + 偏移字符串拆成数字数组 + 统一偏移量，肉眼完全读不出先找到字符串表，还原后再看代码
最容易被骗的是"原型链中间层覆写"。obj.valueOf() 返回的结果可能是假的——因为混淆器在原型链的某一层塞了个同名函数。判断方法：用 obj.hasOwnProperty('valueOf') 看是不是自有属性；不是的话，断点里顺着 __proto__ 一层层看到底在哪一层被换掉的。
还有一个直接能用的判据：如果你看到"页面卡顿 + 同一个接口被请求两次 + 首次响应返回一段诡异的 JS"，三个信号同时出现，基本可以断定有前置 cookie 加密（刷新型反爬）。反过来，如果"重放成功但模拟请求失败"，那不是加密问题，是指纹或 TLS问题——两条完全不同的排查路线。

8.2 浏览器调试三板斧（核心一） 核心一 · 定位

逆向的第一步永远是定位：在几万行被打包、压缩、混淆过的 JS 里，找到"生成这个参数"的那几行代码。所有高手用的都是同一套动作，我们叫它三板斧——按命中率从高到低，每一斧都值得练成肌肉记忆。

第一斧 · Sources 全局搜索（Ctrl+Shift+F）

DevTools 的 Sources 面板左下角有个全局搜索（快捷键 Ctrl+Shift+F），能搜站点加载的所有 JS 文件。搜索策略有讲究：先搜长而特殊的，再搜短的——搜 "sign" 会有几百个结果，但搜 "ydsecret"、"mst-token" 这类自定义命名往往一击命中。可搜的东西依次是：参数名本身、参数的 URL 前缀（如 sign=）、加密相关的关键字（encrypt / md5 / sha / aes / JSEncrypt）、接口路径片段。搜到后点进去下断点，让代码自己跑过来。

第二斧 · XHR 断点 + DOM 断点

全局搜不到怎么办？换"守株待兔"：XHR 断点——Sources 面板右侧 XHR/fetch Breakpoints 加一条 URL 片段（如 /api/list），再触发一次请求，页面会冻结在请求发出前的一瞬间，此时调用栈里就藏着生成参数的完整链条。DOM 断点解决另一种情况：某个值"突然出现在页面上"，在 Elements 里对目标元素右键 → Break on → subtree modifications，JS 一改这棵子树就会停，谁改的谁现行。

第三斧 · 调用栈回溯（Call Stack 从下往上跟）

断点命中后，右侧 Call Stack 是一列函数帧。它是栈：栈顶是当前正在执行的函数，栈底是最早的入口。回溯要"从下往上"看：底下几帧通常是框架代码（axios/jQuery 发请求），往上经过业务函数（在拼参数）、最终停在某个加密函数上。经验法则：谁在拼参数、谁在调加密库，谁就可疑。配合右侧 Scope 面板看每一帧的局部变量值，比硬读源码快十倍。上一斧的 XHR 断点 + 这一斧的栈回溯，是逆向的黄金组合。

Console 查看变量与 Hook

Console 不只是打日志的地方，它是逆向的现场实验室：断点冻结时直接在 Console 里输入变量名看值、调用函数试输出。更进一步是 Hook（钩子）——在页面代码运行之前，把某个全局函数替换成"先打印、再执行原函数"的包装版。Hook JSON.parse 最经典：很多站把加密数据解密成 JSON 后再处理，劫持它等于在"解密出口"蹲守：

Console · Hook JSON.parse（Object.defineProperty 劫持）
// 粘到 Console 回车：之后每次 JSON.parse 都会先喊一声"谁在调用我"
(function () {
  var raw = JSON.parse;
  Object.defineProperty(JSON, 'parse', {
    value: function (text) {
      console.log('[Hook] JSON.parse ← ', text);
      debugger;                     // 命中后看 Call Stack：解密者现行
      return raw.apply(this, arguments);
    }
  });
})();

另一个必备场景是过无限 debugger：很多站用"定时器循环执行 debugger 语句"做反调试，你一开 DevTools 就被按在地上。两种过法：① "Never pause here" 右键法——停在 debugger 那一行后，在 Sources 里对该行行号右键 → Never pause here，从此这行永不暂停，最优雅；② 重写定时器法——在 Console 里把 setInterval 换掉，拦掉含 debugger 的回调：

Console · 重写 setInterval 过无限 debugger
(function () {
  var _si = setInterval;
  setInterval = function (fn, t) {
    if (fn && fn.toString().indexOf('debugger') !== -1) return;  // 拦掉含 debugger 的定时器
    return _si(fn, t);              // 正常定时器照常放行
  };
})();
// 补充姿势：给 debugger 行下"条件断点"填 false；或临时用 Ctrl+F8 全局禁用断点

Overrides（本地映射）是很多人不知道的一招：对着 Sources 左侧资源树右键 → Override content → 选本地文件夹授权 → 改完 Ctrl+S 刷新生效。相当于浏览器内置的 AutoResponder——在 Fiddler 抓不到包（http2/QUIC、证书锁定）时，这是唯一应急方案。

Fiddler：改包比抓包更有用

抓包只是第一步，真正省时间的是改包。三个动作：

① AutoResponder（替换响应）——勾 Enable rules + Unmatched requests passthrough（不勾会把所有流量拦死），Add Rule 上行填匹配、下行指向本地文件。

规则一定要加 regex: 前缀，否则会误伤同域的其他请求，表现为"页面越改越坏、整个站都打不开"。这是最常见的翻车点。

三种用法：整包替换（抓下来改完回注）、直接删掉反调试代码（把含 debugger 的 JS 替换成空文件，无限 debugger 当场消失——这也是过反调试最顺手的一招）、改响应体验证前端逻辑。

② 响应后断点改包——Rules → Automatic Breakpoints → After Responses。必须选 After：选 Before 的话你改完的内容会被真实响应覆盖回去。

③ Composer / Replay——把请求拖进 Composer 改参数重发，验证服务端到底强校验了哪个字段；Replay 可以批量发 N 次，测频控和幂等。

抓包排障的定式：先重放，再对比。
重放成功 → 直接照抄 cURL 构造请求；重放失败 → 对比"浏览器的成功请求"和"你的失败请求"：请求头（数量/顺序/UA/自定义字段）、cookie（有没有 Set-Cookie、哪个 cookie 是关键）、参数（有没有动态值）、顺序（是否依赖前置请求）。
讲者遇到过的两个真实案例：① 单独重放数据接口返回 403，把前置接口 + 数据接口一起重放就成功——服务端在建立状态；② 重放返回一段 JS 烟雾弹，最后发现服务端校验请求头的排列顺序，Python 侧要用 session.headers = headers 整体赋值才能保住顺序（传 headers= 参数会被 requests 重排）。

8.3 加密算法指纹识别（核心二） 核心二 · 识别

定位到加密函数后，下一步是识别它用的什么算法。好消息是：密文会自报家门——输出长度和字符集就是最可靠的指纹。MD5 永远输出 32 位十六进制，SHA256 永远 64 位，RSA 公钥永远以 MIIB 开头。把下面这张表背下来，你就能做到"瞄一眼密文就报算法"。

算法长相特征（指纹）JS 里的标志Python 对应
MD5恒定 32 位十六进制（0-9a-f）CryptoJS.MD5(...)hashlib.md5
SHA1恒定 40 位十六进制CryptoJS.SHA1(...)hashlib.sha1
SHA256恒定 64 位十六进制CryptoJS.SHA256(...)hashlib.sha256
Base64长度是 4 的倍数，常以 = 结尾btoa() / atob()base64.b64decode
AESCryptoJS 默认结果以 U2FsdGVk 开头（即 "Salted__" 带盐标记）CryptoJS.AES.encryptpycryptodome，或直接扣代码
RSA超长 Base64，公钥常以 MIIB 开头JSEncrypt / setPublicKeyrsa / pycryptodome
时间戳10 位纯数字 = 秒，13 位 = 毫秒Date.now()int(time.time()*1000)

CryptoJS 调用特征

国内站点八成用 CryptoJS 或它的变种。在 Sources 里看到下面这些调用模式，基本等于看到了答案：函数名（MD5/AES）直接暴露算法，enc.Utf8.parse(key) 说明 key 是明文字符串，mode.ECB + pad.Pkcs7 说明填充方式，toString() 输出的前缀帮你二次确认。

Sources 里常见的加密调用模式
CryptoJS.MD5(raw).toString()                      // → 32 位 hex，八成是 MD5 签名
CryptoJS.AES.encrypt(data, key).toString()        // → U2FsdGVk… 开头（默认 OpenSSL 带盐）
CryptoJS.enc.Utf8.parse(key)                      // key 是 UTF8 明文字符串
CryptoJS.AES.encrypt(data, key, {
  mode: CryptoJS.mode.ECB,                        // 模式：ECB / CBC
  padding: CryptoJS.pad.Pkcs7                     // 填充方式，还原时要对齐
});
new JSEncrypt().setPublicKey(PUBLIC_KEY)          // RSA：先加密密码再提交
atob(x) / btoa(x)                                // Base64：只是编码不是加密

闭环：识别 → Console 验证 → 还原

① 识别长度+前缀对号入座→ ② Console 验证同输入是否同输出→ ③ 还原Python 复刻或扣代码

识别只是猜想，必须验证：把加密函数的输入参数抄下来，在 Console 里手动跑一遍（或调用该函数），确认输出与请求里的密文逐字符一致——一致才算分析闭环。然后才进入还原：算法简单（纯哈希拼接）直接用 Python 的 hashlib 复刻；涉及 AES/RSA 或复杂拼接，走 8.4 的扣代码。跳过验证直接还原，错了都不知道错在哪。

8.4 扣代码与补环境（核心三） 核心三 · 还原

验证闭环后到了还原环节。算法简单（如 MD5 拼接）用 Python 的 hashlib 几行就复刻了；但遇到 AES 带盐加密、自研魔改算法、多层嵌套拼接，用 Python 手写复刻的成本急剧上升——这时更聪明的做法是扣代码：把浏览器里那段加密 JS 原样拷出来，在本地用 Node 执行。核心逻辑一句话：浏览器能算的，Node 就能算。

hook：两个公式 + 一条铁律

抠代码之前通常要先 hook 一次找到入口。hook 一定生效——JS 的最终解释权在客户端，服务端只能提高你被发现的成本，挡不住你改写任何可写属性。

所有 hook 都是同一个三步：找 hook 点（我要观察什么）→ 写 hook 逻辑（打印/断住/改值）→ 在 hook 里往上追栈。落成代码只有两个公式。

公式一：函数 hook（备份 → 重写 → 伪装）
// ① 备份
var eval_bk = eval;

// ② 重写，保持原逻辑
eval = function (code) {
    console.log('[hook eval]', code);   // 或 debugger;
    return eval_bk(code);
};

// ③ 伪装原生 —— 不做这步会被反爬识别
eval.toString = function () {
    return 'function eval() { [native code] }';
};
第 ③ 步不能省。重写后 eval.toString() 返回的是你的源码，而原生函数返回 "function eval() { [native code] }"。反爬只要判断 toString().indexOf('native code') === -1 就知道被 hook 了，然后走蜜罐分支——给你一份"能算出结果但结果是错的"参数。表现是请求 200、格式完全正确、服务端就是不认。遇到"参数看着对但过不了"，先怀疑 hook 被识别。
公式二：对象属性 hook（以 document.cookie 为例）
var desc = Object.getOwnPropertyDescriptor(Document.prototype, 'cookie')
        || Object.getOwnPropertyDescriptor(document, 'cookie');
var cookie_bk = desc.get.call(document);

Object.defineProperty(document, 'cookie', {
    configurable: true,        // ★ 不给 true，二次 hook 必抛错
    get: function () { return cookie_bk; },
    set: function (val) {
        debugger;                // ★ 在这断住 → 往上翻栈 = 加密入口
        cookie_bk = val;
    }
});

属性 hook 的两个高频错误：① 只写 get 不写 set——网站写 cookie 时静默失败，页面逻辑崩了，你还以为是 hook 没生效；② 不写 configurable: true——默认 false，之后任何 defineProperty 都抛 Cannot redefine property。

很多站是两层壳：第一层 JS 只是外壳，真正的逻辑在 eval(第二层字符串) 里。这时 hook cookie 只能看到最外层，直接 hook eval 一步到位——断住之后栈上就是"谁把这段字符串拼出来的"，往上翻一层就是二层入口，不用格式化、不用扒壳。

用油猴让 hook 可复用：Console 里敲的 hook 一刷新就没了。油猴脚本只有一个字段要记——@run-at document-start，它是唯一能赶在页面 JS 之前注入的选项。默认的 document-end 一定失效（页面 JS 早跑完了）。

execjs：Python 指挥 Node 跑 JS

PyExecJS 是最常用的桥梁：Python 侧装它，本机再装 Node.js（execjs 只负责"指挥"，真正干活的是 Node）。三步走：抠出 JS 存成 .js 文件 → execjs.compile 编译 → ctx.call 调用函数。下面是完整可跑的示例——为什么选 AES 做例子？因为 CryptoJS 的默认 AES 是 OpenSSL 带盐格式（还记得 U2FsdGVk 开头吗），纯 Python 复刻要自己实现 EVP_BytesToKey 密钥派生，非常费劲；扣代码则一行不用改：

安装（终端）

encrypt.js —— 从浏览器 Sources 原样抠出来的加密函数
var CryptoJS = require('crypto-js');

// 这两行就是从站点 JS 里抄出来的核心逻辑（变量名保持原样更方便排查）
function getToken(page, ts) {
  var raw = 'page=' + page + '&ts=' + ts;
  return CryptoJS.AES.encrypt(raw, 'ydsecret#2024').toString();
  // 默认带盐 → U2FsdGVk 开头；纯 Python 复刻很费劲，扣代码最划算
}
run_js.py —— Python 调 Node 执行
import execjs

with open("encrypt.js", "r", encoding="utf-8") as f:
    ctx = execjs.compile(f.read())          # 编译整段 JS

token = ctx.call("getToken", 1, 1730000000) # 调用函数、传参、拿返回值

补环境三步：报什么补什么

抠出来的代码经常一跑就报 document is not defined——因为原代码里检测了浏览器环境（window/document/navigator），Node 里没有这些全局对象。这就是补环境：自己伪造一个"最小可用的浏览器骨架"喂给它。标准三步：① 跑一次，记下第一个报错；② 在 JS 文件顶部伪造报错提到的那个全局对象（报什么补什么，绝不画蛇添足）；③ 循环 ①② 直到跑通。绝大多数站补 window/document/navigator/location 四件就够了：

env.js —— 最小伪环境骨架（放在加密代码之前）
var window = this;
var document = {
  cookie: '',
  referrer: '',
  createElement: function () { return { style: {}, setAttribute: function () {} }; },
  getElementsByTagName: function () { return []; }
};
var navigator = { userAgent: 'Mozilla/5.0 (Windows NT 10.0; Win64; x64)' };
var location = { href: 'https://target.example/', protocol: 'https:' };
var screen = { width: 1920, height: 1080 };
补环境纪律：只补报错的，不补想象的。多补一个属性就可能改变加密结果（有些代码真的会拿 navigator 的值参与运算），也可能触发更深的环境检测。补到"能算出与浏览器一致的结果"即停，验证标准仍然是 8.3 那句话：逐字符一致。

8.5 Webpack 打包站 webpack

你会在很多站上发现：全局搜索参数名，一无所获。别慌，多半是遇到了 webpack 打包站——前端工程把源码切成几十上百个模块，用一个加载器按需拼装，再整体压缩。模块号和真实业务名对不上，所以直接搜参数名搜不到。

结构识别：加载器 + 模块表

webpack 产物有固定骨架：一个自执行函数接收模块表（编号 → 函数的对象），内部定义 __webpack_require__ 加载器按编号取模块并缓存。识别特征：全局搜 __webpack_require__ 或 webpackChunk 命中；或看到"一个大函数包着一堆 编号: function(...) {}"的结构。理解了骨架，"扣模块"就有了路标：

webpack 产物的最小骨架（还原后）
(function (modules) {                          // ← 模块表作为参数传入
  var cache = {};
  function __webpack_require__(moduleId) {     // 加载器：按编号取模块、缓存 exports
    if (cache[moduleId]) return cache[moduleId].exports;
    var module = cache[moduleId] = { exports: {} };
    modules[moduleId].call(module.exports, module, module.exports, __webpack_require__);
    return module.exports;
  }
  return __webpack_require__(88);              // 入口模块编号 88
})({
  88: function (module, exports, __webpack_require__) {   // 模块 88：业务层
    var sign = __webpack_require__(129);      // 依赖编号 129 的加密模块
    module.exports = function (raw) { return sign(raw); };
  },
  129: function (module, exports) { /* …加密实现… */ }
});

② 整包抠出本地跑把加载器+模块表整体拷成 .js，本地 Node 执行（配合 8.4 补环境）离线可跑、最稳；代价是依赖模块多时抠起来费劲
③ 运行时 Hook不还原代码，Console 里直接 hook 加载器或加密函数，拿输入输出最快出结果；拿到的是"黑盒输入输出"，适合先验证猜想

② 只留加载器：把模块表清到只剩目标模块，辅助函数（n.d / n.r / n.o / n.n）和业务代码全删。报错再一个个补回来——缺什么补什么，别一上来就全留着。

③ 找入口：XHR 断点断住，看调用栈里"参数生成前/生成后"的那一帧，它通常长这样 n(454)(...)。

8.6 ob 混淆与 AST（拓展） 拓展

再往上走，你会遇到 ob 混淆（javascript-obfuscator 工具的产物）：代码能跑，但人读不懂。三大特征一眼可辨：① 大数组 + 位移函数 + 解密函数——文件开头是一个巨大的字符串数组、一个自执行位移函数（打乱数组顺序）、一个解密函数，全文所有字符串都变成 _0x1c88(0x1f) 形式的调用；② 控制流平坦化——把顺序逻辑打散成 while(true) { switch(顺序号) {...} }，阅读顺序与执行顺序脱钩；③ 死代码注入——塞进大量永远不会执行的 if 分支干扰判断。

混淆还原的标准顺序（顺序反了全白干）：先把"大数组 + 位移函数 + 解密函数"三件套原样搬到文件最前（它们必须最先执行）→ 在 Console/Node 里把全部字符串解密替换回明文 → 再用 AST 去控制流平坦化（switch 还原成顺序结构）→ 最后删死代码。每做一步验证一次：结果不变才继续。

AST：把代码当数据改

手工还原几千行混淆代码不现实，工业化做法是 AST（抽象语法树）：源码先解析成树（编译原理的"前端"），你遍历树、改写节点，再从树生成源码。Babel 三件套各司其职——parse 负责"源码 → AST"，traverse 负责"遍历 + 改写节点"，generator 负责"AST → 源码"。下面这个最小例子把编译期可确定的字符串加法折叠成一个字面量——真实还原脚本就是把这类"访问器"写上几十个：

ast_demo.js —— Babel 三件套最小示例
// npm i @babel/parser @babel/traverse @babel/generator
const parser = require('@babel/parser');
const traverse = require('@babel/traverse').default;
const generator = require('@babel/generator').default;

const code = 'var _0x1f2a = "hello" + " " + "world";';
const ast = parser.parse(code);              // ① parse：源码 → AST
traverse(ast, {                               // ② traverse：遍历 + 改写节点
  BinaryExpression(path) {
    const l = path.node.left, r = path.node.right;
    if (l.type === 'StringLiteral' && r.type === 'StringLiteral') {
      path.replaceWith({ type: 'StringLiteral', value: l.value + r.value });
    }
  }
});
console.log(generator(ast).code);            // ③ generator：AST → 源码
// 输出：var _0x1f2a = "hello world";
🌐 多源视角 · 夜幕团队 NightTeam：JSVMP 与"值得吗"判断

混淆之上还有一档：JSVMP（JS Virtual Machine Protect）。它把业务 JS 预先编译成自定义虚拟机的字节码，页面里只剩一个通用"解释器 + 一大段字节数组"，运行时逐条取指、译码、执行——你在 Sources 里看到的不再是加密函数，而是一台"软件 CPU"。这正是上方 K哥套路表的第⑥类，也是目前最强的 JS 保护之一：字符串搜不到（全在字节码里）、断点下不准（没有"算法那一行"）、硬啃要把解释器的每条自定义指令映射回语义——逆向成本陡增一到两个数量级。

夜幕团队的文章里反复强调一个思路：动手之前先算账——"逆向的预期时间"与"直接渲染 / 换数据源的成本"哪个划算？这道判断题的答案集：

处境建议路线
字节码几千条、核心逻辑还按周轮换、数据量不大直接 Playwright 渲染（5.4），让浏览器自己跑 VM
数据量大、接口稳定、值得长期投入值得硬啃：对解释器插桩记录执行 trace，把高频指令映射回语义
有替代数据源（镜像站 / 官方 API / 其他平台）换数据源——一秒钟都不用逆向，这永远是最优解
学习目的挑个小的啃一遍：JSVMP 是 JS 逆向的"毕业设计"，啃完豁然开朗

记住这个判断本身就是高手能力的一部分："放弃"也是一种策略。工程目标永远是"稳定拿到数据"，逆向只是手段之一——把时间花在刀刃上，是一线逆向团队和新手最大的区别。延伸阅读见章末"多源精读"的 NightTeam 入口。

ob 还原流水线

obfuscator.io 的产物结构是固定的四段：大数组 → 数组移位 → 解密函数 → 真正的业务代码。所以还原也是固定的五步：

①解字符串
数组→ ②字符串
合并→ ③还原
十六进制→ ④还原对象
成员表→ ⑤控制流
删死码

第一步的关键在"让解密函数活起来"：字符串是算出来的，只看静态解不出。做法是把前三段语句抽出来、compact: true 压成一行、eval 一遍，让 $B() 真实存在，然后用 eval 逐个算出结果替换成字面量。

第一步的骨架
// ① 抽出前三段（数组 / 移位 / 解密函数），压成一行
let helper = '';
for (let i = 0; i < 3; i++) {
    helper += generate(ast.program.body[i], { compact: true }).code;
}
eval(helper);                      // 让 $B 真的存在

// ② 遍历调用表达式，逐个换成字面量
traverse(ast, {
    CallExpression(path) {
        const { callee, arguments: args } = path.node;
        if (!t.isIdentifier(callee) || callee.name !== '$B') return;
        if (args.length !== 2) return;
        if (!t.isStringLiteral(args[0]) || !t.isStringLiteral(args[1])) return;

        let str;
        try { str = eval(`${callee.name}(${JSON.stringify(args[0].value)}, ${JSON.stringify(args[1].value)})`); }
        catch (e) { return; }         // 算不出来就跳过，别让脚本挂
        if (typeof str !== 'string') return;

        path.replaceWith(t.stringLiteral(str));
        path.skip();
    },
});

// ③ 前三段已经没用了，直接砍掉
ast.program.body.splice(0, 3);
判断条件写多严都不算多。上面每个 return 都是一道保险——判断越少，误伤越多。这是讲者反复强调的：宁可漏还原几个，也不要改错一个。
三个最容易翻车的地方：
① 嵌套还原只成功一半：$B($B('0x2','x3'), 'x4') 只有内层被还原。原因是 traverse 深度优先、enter 先触发——处理外层时实参还是未还原的节点，条件不通过就跳过了。解法：把逻辑放进 leave，让内层先处理完、外层再处理。这是整组课最值得记的一个技巧。
② 还原十六进制时手拼 raw：单双引号混用会生成非法代码。正确做法是直接删掉 node.extra，让 generator 自己重新生成。
③ 误删死代码：判断"这个变量还有没有人用"要宁多不少，删错一个 a3，报错会指向 a1.xxx is not a function，跟真因隔了十万八千里。

8.8 完整推演：Google 翻译 tk 的破与立 新 · 案例复盘

五、算法的骨架：两个输入，一个输出

过了混淆那一层，剩下的逻辑其实很简单：

W 函数的逻辑结构（伪代码）
b = TKK.split('.')[0]              // 取 TKK 的整数段
for (每个字符 c in 待翻译文本) {
    b += c.charCodeAt(0)          // 累加字符的 ASCII 码
    b = 位运算混合(b, b)            // ← 一堆 << >> ^ ，原样抄

tk = b + '.' + (b ^ Number(TKK.split('.')[1]))

两个输入：待翻译的文本（q）+ 页面的全局变量 TKK。一个输出：形如 753.123456 的字符串。这就完美解释了实验 A——换个词，b 变了，tk 跟着变。

关于那段位运算：具体移多少位、跟哪个常量异或，每个版本都可能不同，必须从你当下抓到的 JS 里原样抄。网上搜到的旧文章里的常量十有八九已经过期，抄了算出来的 tk 一定是错的。本节给的是"怎么找到它、怎么读懂它"的方法，不是可以直接复制粘贴的算法。

六、落地：Python 重写时最容易翻的车

把位运算抄进 Python，会遇到一个语言层面的陷阱：JS 的位运算强制 32 位，而 Python 的整数是任意精度。

表达式JS 结果Python 直接写是否一致
-1 >> 1-1-1✓ 一致
-1 >>> 12147483647无此运算符✗ 要自己写
(2**31) | 0-21474836482147483648✗ 溢出行为不同

所以要先准备两个工具函数，把 JS 的语义模拟出来：

jsbits.py —— 模拟 JS 的 32 位整数语义
def to_int32(x):
    """模拟 JS 位运算：结果截为 32 位有符号整数"""
    x &= 0xFFFFFFFF
    return x - 0x100000000 if x >= 0x80000000 else x


def rshift(x, n):
    """模拟 JS 的 >>>：无符号右移，高位补 0"""
    return (x & 0xFFFFFFFF) >> n

写的时候纪律是：每一个位运算后面都套一层 to_int32，遇到 >>> 换成 rshift。漏一个，结果就从中间某一步开始偏，最后算出来的 tk 看着像模像样，服务端就是不认——这种错误最难查，因为没有报错，只有 403。

另一条路是 8.4 的 execjs 直接跑 JS。对这个案例要改两处：把 window.TKK 换成传进来的字符串参数（Node 里没有 window），以及把 W 依赖的其他函数定义一起贴进去。

七、一个容易忽略的时效问题

TKK 是页面初始化时写进全局的，每次刷新页面都会变。所以它既不能硬编码，也不能只在启动时抓一次就跑一整天——实际做法是每次会话从 HTML 源码里正则提取：

从页面源码里取 TKK
import re

m = re.search(r"TKK\s*=\s*'([\d.]+)'", html)
if not m:
    raise RuntimeError("TKK 没抓到——页面结构变了，或者被风控了")
tkk = m.group(1)

这个 case 也说明一件事：逆向的产物是有保质期的。今天算得对，不代表下个月还算得对。所以工程上一定要做"算不出来时能快速发现"的兜底——请求返回 403 就重抓 TKK 重试一次，还不行就告警，而不是让爬虫闷头跑一整晚全是 403。

这个案例为什么值得完整走一遍

因为它把逆向的全部要素都串了一遍，一个不缺：用控制变量把问题问清楚（两个实验）→ 用断点定位而不是硬读（XHR 断点）→ 沿调用栈回溯找源头（六层栈）→ 识破轻量混淆（ASCII 拼串）→ 跨语言重写（32 位语义）→ 处理时效性（TKK 会变）。任何一道 JS 逆向题，拆到底都是这几步的排列组合。

五个坑：① 单步调试前不刷新页面——TKK 已经在全局里了，初始化分支被跳过，你会以为那段代码根本不执行；② 把网上的 tk 算法直接抄——版本一变常量就差，必须从当前 JS 里抄；③ Python 重写漏了 32 位截断——没有报错，只有 403，排查成本极高；④ TKK 硬编码——刷新就失效，必须实时提取；⑤ 把 fromCharCode 那段当成加密算法研究——它只是在拼字符串，真正干活的在后面。

8.9 反调试对抗：三种干扰与它们的破法 新 · 实战

前面八节讲的是"怎么找到加密入口"。但真到现场，按 F12 的那一刻可能就卡住了——页面不停停在 debugger、一开控制台就跳首页、一格式化代码浏览器就崩溃。反调试是你和加密之间的一堵墙，不拆掉，后面所有技巧都用不上。

实战里只有三类，每种都有明确的现象和解法。

一、无限 debugger

现象：打开 DevTools 就不断停在同一个 debugger；点继续立刻又停；有时连格式化都会卡死。

先认清一点：debugger 只有三种注入形态，任何网站都逃不出这三类。

形态长什么样怎么找
① 关键字debugger;明文，全局搜就到了
② evaleval("debugger") / eval(atob("..."))字符串被编码了，但 eval 的参数里一定有它
③ Function 构造Function("debugger")()
[]["filter"]["constructor"]("debugger")()		匿名函数只在内存里，调用栈看不到名字

再认清第二点：「无限」不是死循环，是定时器。真正的 while(true){debugger} 一放开就把主线程锁死、整页崩，反而没法用来干扰你。所以实战里都是高频重复：

    return _Function.apply(this, arguments);
};
不要用核弹版 Function.prototype.constructor = function(){}——它会让页面上所有函数构造失效，正常业务也跟着崩。只在确认业务不用动态构造时才这么干。判定依据：代码里出现大量 constructor + ['constructor'] 这种下标取字符拼函数名，基本就是 OB 的无限 debugger。

方案 6 的两个细节（讲者自己翻过车）：一是如果函数被赋过别名（D = C），必须连别名一起重写，否则改了 C 而 D 还指向旧引用；二是同一站点可能有多个无限 debugger，干掉一个要重新全局搜一遍。

还有一个判断能省时间：debugger 在加密逻辑之后（先出 cookie 再挂 debugger），它纯粹是干扰，直接 script 断点 + 首行断点从头调，无视即可；在加密逻辑之前或全局，就必须先绕过。

二、控制台检测

现象：右键没反应、F12 没反应；或者一打开 DevTools 页面立刻跳首页 / 弹窗 / 加遮罩。

第一层是障眼法：JS 监听 contextmenu 和 keydown（keyCode 123 = F12），preventDefault 掉而已。它禁不掉菜单入口——走 ⋮ → 更多工具 → 开发者工具，或者先开 DevTools 再把 URL 粘进地址栏回车。

第二层才是真检测，利用的是 Chrome 的一个特性：console.log(domNode) 时，如果控制台是打开的，Chrome 会去读这个节点的 id 属性。于是把 id 定义成 getter，就能反推出控制台是否打开：

埋点：只有控制台开着才会走到 get 里
var x = document.createElement('div');
Object.defineProperty(x, 'id', {
    get: function () {
        window.location.href = '/';    // 跳首页 / 死循环 / 弹窗
    }
});
console.log(x);                   // 埋点
一个能省半小时的验证技巧：Firefox 没有这个特性。遇到"一开控制台就跳"的站，先换 Firefox 打开——能正常跑就说明是 Chrome 独有的检测，直接在 Firefox 里调，不用拆它。

要拆的话：script 断点进去 → 跳过第三方包（m3u8、统计 SDK 基本不干这事）→ 全局搜 window.open / location.href / location.replace → 找到后置空或删掉那一行。注意可能绑定了多处，得都置空。

整节最容易踩的坑：重写必须「先定义后重写」。如果在网站自己 function open(){} 定义之前就重写，随后它的定义会把你的空函数覆盖掉——你以为在绕过它，实际是被它覆盖，行为完全反了。唯一有效的时机是函数定义之后、调用之前。

三、内存爆破

现象：正常浏览一切正常；一打开 DevTools、一下断点、或者把代码格式化，内存曲线直线飙升，页面假死，最后浏览器崩溃。

原因：OB 类混淆在检测"代码有没有被格式化"。两种写法——正则匹配格式化后的特征（/function\s*\(\)\s*\{/.test(fn.toString())），或直接比 fn.toString() 是否等于原始字符串。一旦判定被格式化，就把执行流推进一个数组无限膨胀的循环：

数组涨得比计数器快，永远出不来
while (i < arr.length) {
    arr.push(arr.join('') + something);
    i++;                          // 但 arr.length 涨得更快
}

怎么绕过：

① 不要格式化——这是最重要的习惯。OB 代码拉到本地后别按格式化按钮，直接读。

② 已经格式化了：把检测处的换行/空格还原，或者把 if (isFormatted) 改成 if (false)。

③ 定位爆破点：直接搜正则字面量（一道题里可能有 5 处），逐个下断点，断在 .test() 附近看返回值，就能确认哪一处是检测。

内存爆破没有通解，这一点和无限 debugger 完全不同——你无法预知雷埋在哪，只能对拍：浏览器和本地 Node 在同一位置打点输出，比对中间值，逐步缩小范围。
另外记住一个逻辑：爆破在正常访问时一定是无效的，否则正常用户也会崩。所以一旦你"什么都没改就炸了"，说明你暴露了某个特征——代码被格式化了、调试时间差太长、或者指纹不对。
五个坑：① 格式化 OB 代码 = 直接踩雷，本地阅读也别按格式化；② 重写函数时在定义之前动手，等于没写；③ 置空函数时忘了同步别名（D = C），改了一个另一个还活着；④ 只处理了一个 debugger 就以为完事，同一站可能有多个；⑤ 把 3MB 全混淆代码导致的卡死当成内存爆破——那是内存不足，调试层面无解，加内存或换机器。

8.10 浏览器指纹与 Node 指纹 新 · 进阶

前面九节都在讲"怎么算出参数"。但有一类站，参数算得完全正确，服务端就是不认——返回 200、格式没问题，就是不给数据。这不是算法错了，是环境不对。这一节讲服务端怎么认出"你不是浏览器"。

一、方法论只有一条：拿两个字典求差集

"浏览器指纹"这个词听着玄，实际做法很笨：把 MDN 的 Web API 索引当字典逐条筛，把 Node.js 文档当另一个字典，凡是两边对不上的地方，就是检测点。

筛选规则：标了"实验性"的跳过、标了"已废弃"的跳过、只有 Chrome 才有的私有属性（chrome.*）一般不作检测对象——剩下的全都可能被拿去当指纹。

采集面典型项能不能补
全局window、innerHeight/Width、outerHeight/Width能，但宽高要和 UA/设备自洽
文档document、referrer、document.all能（document.all 是"浏览器有、Node 没有"的经典项）
环境navigator.*、screen.*、location.*、history.length检测最密集，但也最好补
存储cookie、localStorage、sessionStorage能
请求XMLHttpRequest、fetch、Worker、WASM补不了，见下
三类"补不了"的东西，别硬补：
① XHR / fetch / Worker——它们不是数据对象，是"行为"。补个假 XHR 只能骗过 typeof，骗不过"它真的发了请求并拿到响应"。正确做法是往下跟：看它请求了什么、拿到什么、用响应干了什么，然后把结果硬编码。
② WASM——上手成本太高，遇到就扒它导出的函数、把调用结果拿下来。
③ DOM 节点——一律"向下跟，取结果"，不要试图造节点。判断分支：不参与计算就整个删掉，参与计算就把那一段结果写成常量。

二、Node 侧：哪些地方会露馅

用 Node 跑抠出来的 JS 时，下面这些差异就是破绽。不用全记，记住"哪些必须改"更重要：

维度浏览器Node 默认怎么补
window存在，不可 delete没有，只有 global，可 deleteObject.defineProperty(global,'window',{value:global,configurable:false})
navigator几十个属性Node 18+ 有残缺版（只有 userAgent 之类）整体覆盖成普通对象，UA 必须和请求头一致
setTimeout 返回值数字 idTimeout 对象包一层，自己维护递增 id
require / module / Bufferundefined全都有跑完 delete，或用 vm 隔离
时区跟随系统常为 UTC启动时 TZ=Asia/Shanghai
Error.stack浏览器帧格式含 node:internal、file:///截断或替换
fs 和 child_process 不是指纹问题，是安全事故。
讲者现场演示过：混淆代码里藏一句 require('child_process').exec('shutdown -s -t 1000')，在浏览器里跑只是抛 require is not defined，在 Node 里跑就是 1000 秒后电脑关机。混淆之后它混在正常逻辑里，肉眼完全看不出来——你"习惯性粘到本地跑一下排个错"就中招了。
纪律：跑任何来路不明的 JS 之前，先禁掉 require('child_process') 和 require('fs')——用 vm 沙箱、或干脆在虚拟机里跑。

三、服务端到底怎么判断"你是爬虫"

信号说明
参数重放失败同参数第二次被拒 → 有一次性的因子（时间戳 / nonce）
参数能算但被判废投毒——算法没错、环境不对，服务端直接不认
指纹内部不自洽UA 说 Chrome 120，navigator.plugins 却是空数组
时区 / IP 不一致时间戳落在 UTC，请求却来自东八区 IP
行为特征翻页间隔恒定、无鼠标轨迹、请求顺序机械

"参数对但不认"时，排查顺序：先查 hook 是否被识别（toString 伪装漏了）→ 再查环境缺项 → 最后才怀疑算法。顺序反了会白改一整天。

8.11 新型反爬与 jsRPC 新 · 前沿

8.1 到 8.10 覆盖的是"加密参数"这条主线。但近几年的反爬早就不只在参数上做文章了——有的不加密，改字体；有的不上 JS，上 WASM；有的不看你算什么，看你握手时像不像浏览器。这一节把这几种手段和它们的边界讲清楚，最后补一条"不逆向也能拿结果"的路。

一、CSS 反爬与动态字体

思路是数据在页面上看得见，但你复制下来是错的：<span>1</span> 在 CSS 里被映射成字形"8"，人看到 8、程序抓到 1。四类做法：

类型手法识别
CSS 偏移用负 margin / 伪元素把真实字符移出可视区，塞个假字符进去对比 DOM 文本和肉眼所见
雪碧图数字做成图片，靠 background-position 定位元素没有文本，只有背景
SVG 映射把字符画成 SVG pathDOM 里是 <svg><path>
动态字体每次请求换一套 @font-face，字形和码点的对应关系随机返回值里出现 &#x 十六进制实体

动态字体是目前最主流的一种。应对只有一条路：字体文件比对——拿基准字体和目标字体做字形轮廓相似度匹配，建一张"码点 → 真实字符"的映射表。数字准确率能到 99.9%，汉字 95% 左右，前提是标注一批样本训练好。

判断依据很好记：接口返回里出现 &#x 开头的十六进制实体，基本就是动态字体，不用再猜别的。

二、WASM 与 Worker

WASM 相当于前端的 .so——C/C++ 编译成 .wasm 放前端，JS 直接调。分两档：

档位特征应对
简单档直接加载 wasm 调导出函数就能出结果把导出函数包一层调用即可
困难档内部揉了大量 JS 操作（视频站、wasm 做的游戏）目前没有成熟方案，只能按二进制逆向硬啃

出现原因常常是"顺手"——视频站本来为了性能上 wasm，后来往里塞了加密逻辑。

Worker 的唯一实际痛点是断点打不上。解法是用 AutoResponder 把远程 worker 脚本本地映射，在改过的副本里插 debugger，就能正常断住。

三、TLS 指纹：不看你算什么，看你握手像不像

这是讲者最看好的一项，因为它推广成本极低——HTTPS 本来就都走 TLS，指纹只是握手的副产品。

原理：TLS 握手的 ClientHello 里，cipher suites 的顺序、TLS 版本、扩展、椭圆曲线这些组合起来，构成一个可哈希的指纹。浏览器和 requests 的指纹完全不同——这就是"浏览器能打开、脚本返回 405"的根因。Akamai 一类商业防火墙已经在用。

典型拦截页长这样
405  +  "由于你访问的 URL 可能会对网站造成威胁，你的访问已被阻断"  +  一个请求 ID

当前还是黑名单制：特征命中黑名单哈希、或访问频率异常才拦。所以"只要不像已知爬虫"就能过。三级应对：

级别做法说明
临时改 urllib3 的 ssl_.py 里的 DEFAULT_CIPHERS，换成宽集合（如 ALL）指纹哈希立刻变，黑名单失效。前提是 requests 版本够新——网上教程"改了没用"九成是版本太老
升级每次请求随机选一组 cipher 组合，让指纹呈分布而非固定值固定成一个新指纹照样会被收集拉黑，必须随机化
源码级追到 ssl_wrap_socket，往握手层补 UA、把 HTTP/1.0 改成 1.1、抹平 Connection 差异讲者实测有效：同一站从"返回乱码/拦截页"变成正常出数据

观察方法：抓包工具要先打开 CONNECT 隧道显示，才能看到 TLS 握手层。握手层里 random、session id 每次都变不用管，要看的是 cipher 列表和扩展。

讲者的趋势判断值得记住：TLS 指纹一旦被安全团队集中投入，黑名单会变成白名单——届时"不在白名单内"就是原罪，大量请求库会直接失效。更狠的想象是叠加校验「握手期 UA == 正式请求 UA」「两次请求 IP 一致」，任一不满足即杀。这条一旦落地，对纯协议爬虫是致命打击。

四、jsRPC：不想逆向时的另一条路

上面这些越做越深，但业务上经常是"两天工期就得出数据"，根本没时间逆向。这时候的正确选择不是硬啃，是 RPC：把浏览器当成一个函数服务器，Python 远程调用它算出来的结果。

Sekiro 是目前最省事的一个实现。原理很朴素：浏览器插件在页面里注册一个 WebSocket 客户端，服务端收到 Python 的调用请求后，让浏览器执行目标函数、把返回值传回来。

步骤做法
服务端JDK 1.8 环境，双击 sekiro.jar 启动
浏览器装 Sekiro 插件，填服务端地址，路径写 /business-demo
Python调 invoke 接口，传 group / action / 参数
四个坑，全是配置问题：① demo 版路径必须写 business-demo，写 business 会一直连不上且不报错；② 本地没证书就别用 wss://，多一个 s 直接握手失败；③ group 和 action 在注册端和调用端必须完全一致，大小写错一个字符都是空返回；④ 注入时机——目标 JS 还没执行完就注入，注册会被覆盖，表现是"第一次一定失败、之后成功"，等页面跑完再注入。
什么时候该选 RPC 而不是逆向：工期紧（一两天）、目标是一次性采集、或者加密逻辑深到性价比不划算。代价是依赖浏览器在线、单线程、慢——所以它适合"先拿到数据交差"，不适合长期跑量。

手段判断
CSS 反爬始终存在但不会扩大——严重影响体验（错误显示、无法复制），只会在个别页面用

Q1拿到一串 32 位十六进制（如 e10adc3949ba59abbe56e057f20f883e），如何判断它最可能是什么算法？请再列出其他常见长度/前缀指纹。概念

考点：8.3 加密算法指纹表——"密文自报家门"的识别能力。

参考解析：32 位十六进制是 MD5 的指纹（MD5 输出恒 128 bit → 32 个 hex 字符）。顺带一提示例串是 "123456" 的 MD5。其余指纹：40 位 hex = SHA1；64 位 hex = SHA256；长度为 4 的倍数、常以 = 结尾 = Base64（编码非加密）；U2FsdGVk 开头 = CryptoJS 默认 AES（"Salted__" 带盐）；超长 Base64 且 MIIB 开头 = RSA 公钥；10 位纯数字 = 秒级时间戳，13 位 = 毫秒级。识别后仍需 Console 验证同输入同输出才算闭环。
Q2打开 DevTools 后页面不断弹出 debugger 断点，删掉那行代码也照样弹，页面几乎卡死。可能是什么机制？给出至少两种过法。分析

考点：8.2 反调试与无限 debugger 的应对。

参考解析：这是典型的无限 debugger 反调试：常见实现有 ① setInterval 定时循环执行 debugger 语句（所以删掉一处还会再弹）；② Function('debugger')() 或 eval 构造动态断点；③ 检测 DevTools 打开状态后持续触发。过法：① 首选 Never pause here 右键法——停在 debugger 行后对行号右键选 Never pause here，该行永不暂停；② 重写 setInterval，拦掉 toString 中含 "debugger" 的回调；③ 对 debugger 行下条件断点并填 false；④ 临时 Ctrl+F8 全局禁用断点（副作用是自己的断点也失效）。实战中常需组合使用。
Q3动手：服务器 token = MD5('page=' + page + '&ts=' + ts + 'SALT')，ts 为秒级时间戳。请先用 execjs + Node 实现（写 encrypt.js 与 Python 调用），再写纯 Python 版本对照，两者输出必须一致。动手

考点：8.4 扣代码标准流程：抠 JS → execjs.compile → ctx.call。

参考解析：Node 侧 encrypt.js：var crypto = require('crypto'); function getToken(p, ts){ var raw = 'page=' + p + '&ts=' + ts + 'SALT'; return crypto.createHash('md5').update(raw).digest('hex'); }。Python 侧：import execjs; ctx = execjs.compile(open('encrypt.js', encoding='utf-8').read()); token = ctx.call('getToken', 1, str(int(time.time())))。纯 Python 版：import hashlib, time; raw = f"page=1&ts={int(time.time())}SALT"; hashlib.md5(raw.encode()).hexdigest()。注意两点：同一 ts 下两者输出逐字符一致才算通；真实请求里 ts 要用当下的秒级时间戳并同步传给接口。
Q4综合分析：某接口 POST /api/data，参数 m = "U2FsdGVkX1+8yGx1Bq3zRk9w…"（每次都变），请求头 X-Sign 是 64 位 hex。请给出完整逆向路线：定位、两个参数分别是什么、如何验证、还原方案怎么选。综合

考点：8.2 三板斧 + 8.3 指纹识别 + 8.4 还原决策的综合运用。

参考解析：① 指纹判断：m 以 U2FsdGVk 开头 → CryptoJS 默认 AES（带盐）；X-Sign 64 位 hex → SHA256。② 定位：Sources 全局搜 "X-Sign" / "m"（或对 /api/data 下 XHR 断点）→ 调用栈从下往上跟，找到拼参数与加密的函数帧。③ 验证：断点冻结时抄下加密函数输入（明文与 key），Console 手动调用，输出与请求里逐字符一致才闭环。④ 还原决策：X-Sign 用 Python hashlib.sha256 复刻即可；m 是 CryptoJS 带盐 AES，纯 Python 复刻成本高（要实现 OpenSSL 密钥派生）→ 选扣代码：加密函数抠到 encrypt.js，npm 装 crypto-js，execjs 调用；若代码深度依赖 window/document，再按补环境三步伪造最小骨架。⑤ 全程记录五段式笔记。
